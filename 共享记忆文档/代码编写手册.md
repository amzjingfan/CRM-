# CRM 智能聊天系统代码编写手册

## 1. 手册定位

本手册是项目所有 Agent 编写或修改代码前必须阅读的统一规范。它适用于：

- Python 后端、AI Agent、数据处理和脚本。
- Java 后端及其领域服务、接口和基础设施代码。
- TypeScript/JavaScript 前端、Next.js 页面和组件。
- 数据库迁移、配置、定时任务、测试代码和部署脚本。

**任何 Agent 未阅读本手册，不得开始编写或修改代码。**

## 2. 编码前强制流程

每次编写代码前必须按以下顺序执行：

1. 读取 `共享记忆文档/` 文件清单。
2. 阅读与任务相关的 PRD、接口文档、任务拆解、MVP 范围与验收标准、团队职责和 `测试报告索引.md`；需要测试细节时继续读取 `测试工程师/` 中的权威报告。
3. 阅读本手册，并阅读 `开发工具/skills/` 中与当前任务匹配的 Skill。
4. 明确模块编号、需求边界、接口契约、数据结构、依赖关系、验收标准和风险。
5. 先写实现计划或接口/类型设计，再开始代码实现。
6. 每完成一个可验证的小步骤就执行格式检查、类型检查或测试，不允许一次性堆积大量未经验证的代码。

如果需求、接口、架构或验收标准存在冲突，必须暂停编码，提交架构师确认。

## 3. 项目代码归属和目录规范

- 正式产品代码只能放在 `CRM智能聊天系统/`。
- `AI agent 开发工程师/` 存放 AI 方案、Prompt 说明和 Agent 设计文档，不存放正式产品代码。
- `全栈开发工程师/` 存放开发说明和交接记录，不存放正式产品代码。
- `架构师/` 存放架构方案、技术选型和决策记录。
- `测试工程师/` 存放测试用例、测试报告和缺陷记录。
- `开发工具/` 存放 Skill、脚本、模板和工具说明，不存放业务代码。
- `共享记忆文档/` 存放需求、接口、架构、任务、验收和项目知识。

建议代码库内部按职责拆分为：

```text
CRM智能聊天系统/
├─ backend/       # 后端服务、业务模块、接口和基础设施
├─ frontend/      # 前端页面、组件、状态和接口调用
├─ ai/            # AI Agent、Prompt、RAG、模型和工具编排
├─ migrations/    # 数据库迁移
├─ tests/         # 单元、集成、端到端和评测测试
├─ scripts/       # 可重复执行的工程脚本
└─ docs/          # 仅存代码相关技术说明，项目事实优先同步共享记忆文档
```

如果当前代码结构不同，不得未经架构师确认擅自大规模迁移目录。

## 4. 总体代码质量原则

### 4.1 可读性优先

- 代码首先服务于维护者和 Agent，其次才是追求代码量少。
- 一个函数只负责一个清晰的业务动作。
- 一个模块只负责一个稳定的业务职责。
- 优先使用有意义的名称，不使用 `data`、`obj`、`temp`、`foo` 等无语义名称。
- 复杂逻辑拆成命名明确的小函数，不使用超长函数隐藏业务分支。
- 禁止复制粘贴业务逻辑；应抽取共享服务、策略或工具函数。

### 4.2 业务规则显式化

- 状态值、角色值、平台值、错误码和动作类型必须使用枚举、常量或类型定义。
- 不在业务代码中散落魔法数字、魔法字符串和隐含阈值。
- 关键业务规则必须通过函数名、类型名、注释或文档明确表达。
- 置信度阈值、分页大小、重试次数、超时时间必须集中配置并说明单位和依据。

### 4.3 小步提交和可验证

- 每次修改尽量只解决一个明确问题。
- 先实现最小可运行链路，再逐步补充异常、性能和边界能力。
- 每个新接口至少配套参数校验、正常路径和主要异常路径测试。
- 任何“应该可以”的结论都必须通过命令、测试、页面或日志验证。

## 5. 中文注释规范（强制）

### 5.1 注释目标

本项目要求**详细、准确、面向业务的中文注释**。注释不是翻译代码，而是解释“为什么这样做、业务规则是什么、边界在哪里、失败后怎么办”。

### 5.2 必须写中文注释的代码

- Agent 状态流转、Prompt、RAG、置信度和转人工逻辑。
- 订单、退款、优惠券、营销、会话和权限等业务规则。
- 第三方平台适配、Webhook 签名、重试、限流和幂等逻辑。
- 数据库事务、缓存一致性、异步任务和并发控制。
- 不直观的算法、正则、数据转换和兼容性处理。
- 临时 workaround、已知限制和待移除代码。

### 5.3 注释写法

推荐使用“背景 + 规则 + 原因 + 边界”的结构：

```python
def should_transfer_to_human(confidence: float, customer_emotion: str) -> bool:
    """
    判断当前会话是否需要转人工。

    业务规则：
    1. AI 置信度低于 0.70 时，不能继续自动回复；
    2. 客户情绪为 angry 时，即使置信度足够也需要优先转人工；
    3. 返回 True 只表示需要创建转人工任务，具体分配由会话服务完成。

    参数：
        confidence: 模型对当前答案的置信度，取值范围为 0 到 1。
        customer_emotion: 客户情绪标签，例如 normal、angry。

    返回：
        True 表示需要转人工，False 表示可以继续 AI 处理。
    """
    # 低置信度答案可能产生错误承诺，必须优先保护客户体验。
    if confidence < 0.70:
        return True

    # 情绪激烈场景需要人工介入，避免 Agent 与客户持续争执。
    return customer_emotion == "angry"
```

### 5.4 禁止的注释

禁止只重复代码含义的无效注释：

```python
# 给 total 加 1（无效：代码本身已经表达了含义）
total += 1
```

禁止编写与实际行为不一致、过期、夸大或无法验证的注释。代码变更时必须同步更新受影响注释。

### 5.5 注释密度

- 公共类、公共函数、接口、Agent 节点和工具必须有完整中文文档字符串。
- 关键业务分支至少有一条解释业务原因的中文注释。
- 前端复杂状态、权限判断、异步竞态和降级逻辑必须有中文注释。
- 不要求给每一行简单赋值写注释；要求对每个复杂决策写清楚原因。

## 6. 命名规范

### 6.1 通用命名

- 类、组件、枚举类型使用 PascalCase。
- 函数、方法、变量使用 snake_case（Python）或 camelCase（TypeScript/Java）。
- 常量使用全大写加下划线，例如 `MAX_RETRY_COUNT`。
- 布尔值使用 `is_`、`has_`、`can_`、`should_`、`enable_` 等前缀。
- 时间字段必须带单位或语义，例如 `timeout_seconds`、`created_at`、`expires_at`。
- ID 字段明确实体含义，例如 `session_id`、`customer_id`，禁止笼统命名为 `id` 传遍多个层级。

### 6.2 领域术语

统一使用接口文档和 PRD 中的术语：`session`、`customer`、`message`、`knowledge_entry`、`agent`、`transferred` 等。发现术语不一致时，先更新共享记忆文档，不在代码中自行创造同义词。

## 7. Python 后端规范

- 使用类型注解描述函数参数、返回值和重要数据结构。
- API 请求和响应使用明确的 DTO/Schema，不直接把数据库模型暴露给前端。
- 路由层只负责协议适配和参数校验，业务规则放在 service/domain 层。
- 数据库访问集中在 repository 或数据访问层，不在路由中拼接 SQL。
- 外部 API 调用必须设置超时、错误转换、重试上限和日志上下文。
- 异步函数中不得执行未经确认的阻塞操作。
- 使用结构化异常，不返回裸字符串作为业务错误。
- 资源必须正确关闭，事务边界必须明确。

示例：

```python
async def get_session_messages(
    session_id: str,
    page: int = 1,
    page_size: int = 20,
) -> SessionMessagePage:
    """获取会话消息，分页参数由接口层完成范围校验。"""
    # 消息查询必须按时间倒序返回，保证客服工作台优先看到最新消息。
    return await message_repository.list_by_session(
        session_id=session_id,
        page=page,
        page_size=page_size,
        order="desc",
    )
```

## 8. Java 后端规范

- Controller 只处理 HTTP 协议，不承载复杂业务逻辑。
- Service 负责业务编排，Repository/Mapper 负责数据访问。
- DTO、Command、Query、Entity、VO 的职责必须清晰，不混用。
- 使用明确的异常类型和统一错误码，禁止吞掉异常。
- 事务注解必须放在正确的业务边界，并说明事务原因。
- 并发、幂等、重试和消息消费必须有中文注释说明。
- 公共方法、复杂业务方法和领域状态转换必须有 Javadoc 中文说明。

## 9. TypeScript/前端规范

- 禁止使用 `any` 绕过类型设计；确有必要时必须说明原因并限制范围。
- 页面组件负责展示和交互，接口请求、缓存和业务转换放在清晰的 hooks/service 层。
- 组件状态必须有明确的加载中、空数据、错误和成功状态。
- 所有用户可见错误都要转换为友好中文提示，不能直接显示接口路径、堆栈或内部错误。
- 异步请求必须处理取消、重复提交、竞态和组件卸载后的状态更新。
- 主题、多语言、响应式和无障碍属性不得因新增功能被破坏。
- 复杂交互必须使用中文注释说明状态流转和交互原因。

## 10. AI Agent 代码规范

- Prompt 必须版本化，说明目标、输入、输出格式、约束和失败策略。
- 模型输出必须进行结构化解析和字段校验，不能直接信任模型文本。
- RAG 必须记录检索条件、Top-K、分数阈值、来源和无结果处理策略。
- 工具调用必须校验参数、权限、幂等性和执行结果，禁止让模型直接拼接 SQL 或执行任意命令。
- 低置信度、知识库无结果、模型超时、工具失败时必须有明确降级或转人工逻辑。
- 日志不得记录完整客户隐私、密码、Token、密钥或不必要的原始对话内容。
- Agent 节点必须可单独测试，状态输入输出必须有类型定义和中文说明。

## 11. API、数据库和安全规范

- API 路径、方法、请求参数、响应结构和错误码必须与接口文档一致。
- 分页、排序、筛选和时间格式必须统一。
- 所有写操作考虑重复请求、幂等键、事务和失败补偿。
- 数据库字段、索引、外键和迁移必须说明业务用途；禁止无计划直接修改生产数据。
- 用户输入必须校验、清洗和限制长度；禁止 SQL 注入、命令注入和路径穿越。
- 认证、RBAC、资源归属和敏感操作权限必须在服务端校验。
- 密钥只能通过环境变量或安全配置注入，禁止提交到代码或日志。

## 12. 日志和错误处理规范

- 日志必须包含时间、级别、模块、关键实体 ID 和可追踪请求 ID。
- `INFO` 记录正常关键业务节点，`WARNING` 记录可恢复异常，`ERROR` 记录需要处理的失败。
- 异常处理不能只写 `except Exception: pass`。
- 对外返回稳定、简洁、可理解的错误码；内部日志保留足够诊断信息但不泄露敏感数据。
- 不使用 `print` 作为正式服务日志。

## 13. 测试规范

每个功能至少覆盖：

- 正常路径。
- 参数为空、格式错误和边界值。
- 未认证、无权限和资源不存在。
- 第三方接口超时、失败、重复回调和异常响应。
- 数据库事务失败、并发和重复提交（适用时）。
- AI 无知识、低置信度、模型失败、工具失败和转人工（AI 功能适用时）。

测试命名必须表达“条件 + 行为 + 结果”。大范围测试报告遵循：

```text
{模块编号}-{模块名称}-{测试类型}-{三位序号}.md
```

阶段性测试报告遵循：

```text
Phase{阶段号}-{任务编号}-{被测主责Agent}-{模块编号}-{模块名称}-{测试类型}-{三位序号}.md
```

详细规则以 `测试工程师/测试报告命名规范.md` 为准。
