## 3. 目标、范围与非目标

### 3.1 实施目标

- 把 TK-US 物流/履约、退换退款、商品刊登三类场景转换为可供内容负责人审核的公司自编陈述准备稿。
- 固定逐内容版本的来源、哈希、适用性、审批、冲突、撤销和回滚字段。
- 建立 K1 独立测试计划，并把 KB-G0 从抽象“待评审”推进为逐角色联合签署清单。

### 3.2 实施范围

- `company_shared` 的三类公开政策/指南候选内容准备。
- 八领域覆盖矩阵与三条来源页面日期的低敏同步。
- K1～K4 的治理负向测试设计和 KB-G0 会前材料。

### 3.3 非目标

- 不采集、保存、复制、快照、向量化或展示官方正文。
- 不生成已批准内容版本，不运行 K2/K3 服务，不接真实 Token、店铺、订单、客户或 SKU 数据。
- 不替产品、全栈、AI、测试或权利角色签署，不修改 ADR 为已接受。
- 项目内部文档不进入 RAG 语料。

## 5. 实施方案

### 5.1 方案说明

采用“准备稿—确定字节版本—逐版审批—冻结测试—K3 导入”的门禁链。当前只完成第一步和审批/测试模板，不越过 K1 进入内容导入。商品刊登规则保留在 `company_shared`；任何实际 SKU 规格只能在 K4 证据和 API Data 权利齐全后进入绑定 `shop_ref` 的 `shop_private`。

### 5.2 依赖关系

- 前置依赖：七条公开来源受限使用审批、首批 US 与三类场景确认、已有来源和覆盖数据模型。
- 后续依赖：内容负责人定稿并签署；产品/全栈/AI/测试/权利角色完成 KB-G0；K2/K3 代码级计划；K4 私有来源证据闭环。

### 5.3 风险控制

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 公司自编草案被误当正式语料 | 未审批内容对内传播 | 文档首部和每个版本标 `draft_spec`，无哈希、无批准状态，明确永久排除项目文档 |
| 静态政策冒充实时业务事实 | 错误订单、物流或退款结论 | 为三类场景固定条件变量、`no_evidence` 和转人工边界 |
| 商品刊登政策冒充 SKU 规格 | 跨店数据污染或模型臆造 | 将具体 SKU 限定在获批 `shop_private`，当前保持关闭 |
| 联合签署被误报完成 | K2/K3 未经评审提前实施 | 保持 ADR 与 ARCH 状态“延期/评审中”，逐角色记录待签状态 |
