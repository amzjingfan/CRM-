## 5. 实施方案

### 5.1 方案说明

- 在任何 `await` 之前保存 `event.currentTarget` 对应的真实表单节点，成功后通过稳定引用执行 `reset()`。
- 分类和 FAQ 创建期间使用独立提交状态禁用按钮，避免用户在请求完成前重复提交；成功提示使用可见的 `role=status` 区域并通过 `aria-live` 播报。
- 营销活动表单同步采用稳定表单引用和保存中状态，消除相同隐患。
- API 客户端抛出携带 HTTP 状态和业务码的 `ApiError`；认证守卫仅对 401 安静跳转，网络和服务端异常继续输出诊断日志。
- 页面自身的用户初始化 Promise 显式处理拒绝，401 交由 AppShell 跳转，其他错误进入页面错误状态。

### 5.2 依赖关系

- 前置依赖：Phase 2 HttpOnly Cookie 认证、`/auth/me` 和 `/auth/browser/refresh`；Phase 3 知识库与营销 API。
- 后续依赖：测试工程师针对 DEF-P3-011/012 执行定向浏览器复测和 Phase 3 M03 验收回归。

### 5.3 风险控制

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 异步后 React 事件目标失效 | 服务端成功但前端进入失败提示，用户可能重复提交 | 提交前保存表单节点，成功后使用稳定引用重置 |
| 用户连续点击创建按钮 | 生成不同幂等键并重复创建 | 请求期间禁用对应提交按钮 |
| 将所有认证请求错误都静默处理 | 真实网络或服务故障不可观察 | 使用带状态的 `ApiError`，只静默处理 401，其他错误保留日志或页面提示 |

- API：HTTP 接口契约不变；前端内部错误从普通 `Error` 增强为 `ApiError`。
- 数据库：不适用，无迁移和数据结构变化。

- AI：不适用，未修改 AI 工程师负责范围。

### 6.3 关键实现说明

- 表单节点在事件处理函数同步阶段保存，避免 React 在异步边界后清理合成事件属性。
- 分类与 FAQ 分别维护提交状态，互不阻塞；按钮文案在请求期间显示中英文保存中状态。
- 成功提示既在页面可见，也通过 `aria-live` 对辅助技术播报；成功后的 `load()` 立即刷新树或 FAQ 列表。
- 401 是受保护布局的预期分支，不写控制台；非 401 的用户状态校验失败仍使用 `console.error` 保持可观测性。
