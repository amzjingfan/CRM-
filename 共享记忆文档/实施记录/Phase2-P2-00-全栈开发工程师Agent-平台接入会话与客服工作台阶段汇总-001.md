## 3. 目标、范围与非目标

### 3.1 实施目标

- 建立 TikTok、Shopee、Amazon 的统一平台适配契约和 Webhook 入站链路。
- 建立店铺、客户、会话、消息、订单和审计的数据基础。

## 5. 实施方案

### 5.1 方案说明

平台入站采用统一 `PlatformAdapter` 契约，将原始 Webhook 在验签后持久化到 `webhook_events`，再由独立 Worker 通过 `FOR UPDATE SKIP LOCKED` 认领处理，标准化为客户、会话、消息和订单数据。浏览器认证改用 HttpOnly Cookie，并通过 Origin 与双提交 CSRF 防护写请求。所有资源访问在 Repository 层附加允许店铺集合，跨店铺查询统一返回 404。

### 5.2 依赖关系

- 前置依赖：Phase1 认证、RBAC、数据库、Redis、统一响应、日志和 Compose 基础设施。
- 后续依赖：AI Agent 可读取会话、消息、客户和订单服务契约；知识库、智能回复、营销和看板可复用平台与店铺数据。

### 5.3 风险控制

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 平台验签和发送仍为 Mock | 无法证明生产平台可用 | 获得官方应用、凭证和沙箱后逐平台真实联调 |
| Webhook 重复投递 | 重复创建消息和订单事件 | 事件 ID/请求体哈希、数据库唯一约束和重复返回 200 |
| 跨店铺越权 | 客户和订单数据泄露 | Repository 层店铺过滤，资源不可见统一返回 404 |
| Worker 并发重复处理 | 数据重复或状态冲突 | `FOR UPDATE SKIP LOCKED`、有限重试和状态字段 |
| 敏感日志泄露 | 暴露客户、Token 或平台凭证 | 审计只记录必要元数据，不保存完整消息和凭证 |

- AI：未实现 Agent、Prompt、RAG、模型调用或 `/suggest`，前端只保留禁用入口。

### 6.3 关键实现说明

- Webhook 限制 1 MiB，基于原始请求体验签；无事件 ID 时使用请求体 SHA-256 生成稳定 ID。
- Worker 失败最多重试三次，成功载荷超过保留期后清空正文但保留哈希和状态。
- 人工消息先保存 `processing`，再根据平台 Mock 发送结果更新为 `sent` 或 `failed`。
- 同一幂等键携带不同内容时返回冲突，避免错误覆盖。
- 会话按 `last_message_at DESC, id DESC` 稳定排序；查询消息不会隐式修改未读数。
- 本次同步仅整理实施记录，不修改产品代码和代码注释。
