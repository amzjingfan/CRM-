## 5. 实施方案

### 5.1 方案说明

连续多轮缺陷反复出现的根因是旧实现始终在同一个一维文本分类器上迭代：

1. 最初依赖退款结果动词黑名单，未收录的批准或资金移动同义词会漏放。
2. 后续改成通用完成态扫描后，只要退款主题和“已/has + 完成动作”在同一句共现就阻断，没有判断完成动作实际作用于资金还是页面、按钮和文档，造成系统性误杀。
3. 否定、政策和条件被当作整段白名单，通过连接词切分控制作用域；连接关系属于开放集合，因此更换“并且、况且、nevertheless、notwithstanding”等表面表达即可改变结果。
4. 固定评测样本和实现词表同步扩展，只能证明已知字符串通过，不能证明规则边界稳定。

本次将判定拆成两个正交步骤：

```text
归一化
→ 识别完成态候选
→ 校验候选是否绑定退款申请、审批、资金、账户或可信业务主体
→ 校验否定、条件、可能性、拒绝或引用警示是否直接支配该候选
→ 未受直接控制的业务结果失败关闭
→ 非业务完成对象和合法政策关系进入后续依据复核
```

作用域不再依赖连接词清单，而是依据标点命题边界、主语/业务对象绑定和控制词到候选之间允许的语法成分。报告 010 样本只进入独立回归测试，不扩大同版 234 条固定评测集来伪造泛化证据。

### 5.2 依赖关系

- 前置依赖：Phase 4 现有 `ReplySafetyPolicy`、`UNAUTHORIZED_COMMITMENT` 原因码和人工接管路径。
- 后续依赖：测试工程师执行 011 号独立复测；架构师继续评审结构化业务声明契约是否进入后续版本。

### 5.3 风险控制

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 结果动词属于开放集合 | 新同义词绕过 | 完成态必须绑定稳定业务论元，不以结果动词词表作为唯一边界 |
| 非业务完成对象误杀 | 正常 FAQ 和操作说明被清空 | 页面、按钮、文档、FAQ、表单等对象不满足业务论元约束 |
| 新连接词改变极性 | 前置否定掩盖后置资金事实 | 只承认直接支配候选的控制关系，不枚举连接词作为安全边界 |
| 重叠正则产生冲突 | 同一结果被不同分支给出相反结论 | 所有生效候选统一走同一作用域函数，删除旧旁路和死规则 |
| 文本规则能力上限 | 仍无法证明覆盖全部自然语言 | 三项自动能力继续关闭，并保留结构化业务声明契约架构评审项 |

### 6.3 关键实现说明

- 中文候选要求退款业务对象、资金/账户论元或可信业务主体与完成态直接绑定；英文候选采用相同边界，并补充 `repaid` 等不规则过去分词形态。
- 页面、按钮、帮助文档、流程图、FAQ、表单、入口和说明等非业务对象不会因完成态被判为退款执行事实。
- “无法确认退款”只有直接控制其后的业务候选时才放行；候选前出现另一主语或非语法关系时不会继承否定。
- 条件、引用警示和证据否定按方向关系判定，不把同一句中的任意安全词当作全句通行证。
- 删除仅剩定义、没有调用的旧硬结果、通用完成态、作用域词表和连接词边界，保持单一生效路径。
- 所有新增测试通过 `ReplySafetyPolicy.evaluate` 公共入口，不依赖私有正则实现。
