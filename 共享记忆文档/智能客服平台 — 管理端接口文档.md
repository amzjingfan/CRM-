**版本**：V1.0
**Base URL**：`https://api.yourdomain.com/v1`
**认证方式**：Bearer Token (JWT)
**响应格式**：JSON
**字符编码**：UTF-8

## 1. 认证与用户

## 4. 会话管理

### 4.1 获取会话列表

**触发位置**：会话管理页面 → 页面加载 / 状态筛选

**GET** `/sessions`

**请求参数：**

| 参数      | 类型   | 必填 | 说明                                                     |
| :-------- | :----- | :--- | :------------------------------------------------------- |
| status    | string | 否   | `new` / `active` / `resolved` / `transferred` / `closed` |
| platform  | string | 否   | `tiktok` / `shopee` / `amazon`                           |
| keyword   | string | 否   | 搜索关键词（客户名/订单号）                              |
| page      | int    | 否   | 页码                                                     |
| page_size | int    | 否   | 每页数量                                                 |

**响应：**

json

```
{
  "code": 0,
  "data": {
    "total": 156,
    "list": [
      {
        "id": "sess_001",
        "customer_name": "张女士",
        "customer_avatar": "张",
        "platform": "tiktok",
        "shop": "店铺A",
        "last_message": "我的订单显示已签收...",
        "last_time": "2026-08-17T14:30:00Z",
        "unread_count": 2,
        "status": "active",
        "assigned_to": "张经理"
      }
    ]
  }
}
```



------

### 4.2 筛选会话状态

**触发位置**：会话管理 → 点击状态筛选标签（全部/未读/进行中/已解决/已转人工）

**GET** `/sessions?status={status}`

**参数说明：**

| 标签     | 对应status值                         |
| :------- | :----------------------------------- |
| 全部     | 不传或 `all`                         |
| 未读     | `unread`（需配合`unread_only=true`） |
| 进行中   | `active`                             |
| 已解决   | `resolved`                           |
| 已转人工 | `transferred`                        |

**响应：** 同4.1

### 11.4 AI 工程师交接边界

- Phase 4 已实现 Agent 运营配置 CRUD、脱敏运行日志、公开 `/suggest` 和 POST SSE；模型、Prompt、Embedding/Reranker 和阈值仍只读。AI 已补齐店铺回复策略、中英翻译契约以及弃单/中差评文案生成，但新能力均默认关闭且不放宽真实平台写边界。
- 已实现内部 FAQ AI 契约：`build_agent_workflow(session, settings)` 构建工作流，`workflow.run(session, command)` 返回 `AgentWorkflowResult`。
- `AgentWorkflowCommand` 由可信全栈服务组装，包含店铺、会话、触发消息、当前消息、最多 10 条历史、语言、`trace_id`、可选 `tool_context` 和可信 `reply_profile`。工具上下文只接受可信资源 ID、可用工具、权限和已批准写操作。
- `AgentWorkflowResult` 包含运行 ID、终态、意图、引用、草稿、工具需求、低敏工具调用摘要、`transfer_performed`、三项置信度、最终动作、识别/回复语言、可选翻译关联结果、安全原因码、Token、耗时和固定的 `send_performed=false`。
- FAQ 发布后由 Jobs Worker 原子认领并通过本地 BGE-M3 生成 1024 维向量；正式检索执行 Dense/词法双路召回、RRF 融合和 Reranker，最终只返回当前店铺 `published + ready + current version` 的 Top 5 片段。
- `auto_reply` 仅表示工作流达到 `AUTO_REPLY_READY`。Phase 4 全栈层只在显式开关、启用配置、真实平台写能力和白名单工具同时满足时才发送；当前 Mock 适配器会在发送前阻断。
- AI Agent 通过 `AgentToolService → SqlAlchemyToolExecutor` 执行七个白名单工具。工具执行器属于全栈 `tools` 边界，统一负责店铺隔离、权限、参数、超时、幂等、`tool_calls` 和 `audit_logs`；Agent 不直接访问平台 SDK，也不绕过工具层写业务表。
- 查询工具只使用可信 `order_id/customer_id`；写工具必须匹配 `ApprovedToolAction` 的精确参数和幂等键。转人工可作为安全接管自动执行，但必须由可信上下文开放且具备 `workspace.transfer`。
- 工具失败、超时、权限拒绝、幂等冲突、非法引用或安全复核失败均转人工且不得暴露成功话术；平台写超时记录 `unknown`，Mock 结果最高进入人工复核。
- 所有资源查询都执行店铺级过滤；跨店铺资源统一返回 `40401`。

### 11.5 本地 BGE 全栈运行面增量（2026-08-21）

- `/health/ready` 必须检查 PostgreSQL、Redis、MinIO；`EMBEDDING_ENABLED=true` 时还必须校验内部模型服务返回 BGE-M3 1024 维契约。
- 基础 Compose 保持 AI 关闭；启用 BGE 时叠加 `docker-compose.ai.yml`，确保 backend/jobs 等待 `retrieval-model-service` 健康后再启动，避免启动竞态把待回填 FAQ 标记为失败。
- 模型服务内部 Token 不进入前端、公开 API、日志或状态响应。知识库状态接口只返回低敏模型标识、维度和队列计数。
- 迁移 `014_bge_hybrid` 负责模型维度与混合检索索引；后续 `015` 只补充向量队列认领和店铺状态统计索引，不改变 AI 检索算法。

### 11.7 REAL-FS-02 TikTok OAuth 接口增量（2026-08-25）

| 接口 | 方法 | 权限 | 说明 |
| --- | --- | --- | --- |
| `/settings/channels/tiktok/oauth/start` | GET | `settings.channels` + 店铺访问权 | 为指定内部店铺生成一次性卖家授权地址 |
| `/integrations/tiktok/oauth/callback` | GET | 已登录用户 | 原子消费 `state`，交换 Token、验证卖家/Scope/真实店铺并保存授权 |

`start` 查询参数：

- `store_id`：必填内部店铺 UUID，Repository 和服务层均执行租户访问校验。
- `return_to`：可选，当前只允许 `/settings/channels`，禁止外部或任意站内开放重定向。

成功响应只返回 `authorization_url` 和 `expires_in`，不返回 App Secret、Access Token、Refresh Token 或凭证引用。随机 `state` 默认 600 秒有效，在 Redis 中以 SHA-256 哈希键保存并绑定发起用户、内部店铺和回跳地址；callback 使用 `GETDEL` 原子消费，因此过期、缺失和重复 `state` 都返回统一校验错误，用户不匹配返回权限错误。

callback 接收 TikTok 返回的 `state`、可选 `code` 和可选 `error`。服务端执行以下固定顺序：

```text
原子消费 state
→ 校验发起用户和内部店铺权限
→ 使用 auth_code 交换 Token
→ 校验卖家 user_type、必需 Scope 和过期时间
→ 调用 Get Authorized Shops 读取唯一真实店铺
→ 校验外部店铺未绑定其他租户
→ AES-256-GCM 加密 Access/Refresh Token
→ 更新 channel_accounts
→ 写入 audit_logs
→ 303 回跳 /settings/channels?oauth=tiktok&status=connected
```

首期只允许一次授权唯一对应一个 TikTok 店铺。凭证密文使用内部店铺、外部店铺和凭证类型作为认证上下文，不在数据库中保存明文；`channel_accounts.metadata_json` 只保存低敏店铺摘要、Open ID 哈希、Refresh Token 过期时间和密文格式。授权失败先回滚渠道账号变更，再记录稳定错误码，不保存平台原始错误或半成品账号。

Token 刷新是内部服务能力，不新增公开 Refresh API。刷新成功更新密文、过期时间、Scope、最后同步时间和审计；解密、平台刷新或契约校验失败时状态变为 `expired`。现有 `DELETE /settings/channels/{channel_id}` 对真实 TikTok OAuth 渠道执行本地撤销：销毁本地 Token 可用性、状态变为 `disconnected` 并保留生命周期审计，不物理删除授权证据。

通用 `POST /settings/channels` 只接受 Shopee/Amazon 契约级 Mock 渠道，服务端禁止通过该接口创建 TikTok 记录。一个内部店铺只允许绑定一个 TikTok 渠道，该规则由 `019_tiktok_channel_unique` 数据库部分唯一索引强制保证。

OAuth 回调配置固定为 `https://www.hophorsefit.com/v1/integrations/tiktok/oauth/callback`。integration、staging 和 production 在应用启动阶段要求完全一致；OAuth start/callback 在业务入口再次校验 HTTPS 和固定路径。HTTP、其他主机、其他路径、query 或 fragment 均返回低敏第三方配置错误，且不得创建 Redis `state`、交换 Token 或写入渠道。TikTok 实际重定向地址由 Partner Center 管理，因此发布门禁还必须人工核对平台后台配置；应用不把该地址作为未定义参数拼入卖家授权 URL。

Jobs Worker 默认每 5 分钟扫描 Access Token，并在到期前 24 小时提前刷新；渠道认领使用 PostgreSQL `FOR UPDATE SKIP LOCKED`，避免多个 Worker 重复刷新。刷新成功前必须确认新 Token 的 `open_id` 与原授权主体一致，并重新调用 Get Authorized Shops 确认唯一外部店铺仍为当前 `external_store_id`。主体、店铺、Scope、卖家类型或过期契约不一致时保留旧密文、将渠道标记为 `expired` 并写入低敏失败审计。

前端渠道页只显示连接状态、店铺名称、Scope 摘要和最后同步时间。TikTok 不再接受浏览器手工输入凭证；Shopee/Amazon 的契约级 Mock 表单保持不变。REAL-FS-02 不开启真实只读、Webhook、普通消息写入、高风险写入、AI 回复或营销开关。

### 11.9 REAL-AI-01 Provider 三态 DLP 门禁增量（2026-08-26）

- Agent 内部稳定错误被收敛为公开数字错误：模型/Embedding 限流为 `42901`；模型、Embedding 或 Reranker 超时及依赖异常为 `50003`；配置、鉴权、权限或非法请求使用 `50003,retryable=false`；未知工作流异常为 `50001`。公开事件不返回内部错误名、供应商响应正文、Prompt、密钥或客户原文。
- 认证、权限、Origin/CSRF、请求限流和用户并发门禁在流建立前执行，失败继续返回统一 HTTP JSON 401/403/429。只有流已接受后的 Provider/依赖失败使用 SSE `error + done`，避免以 HTTP 200 掩盖未认证请求。
- 运行日志新增 `chat_stream_completed`、`chat_stream_timeout`、`chat_stream_disconnected` 和 `chat_stream_agent_failed` 低敏事件，仅记录标准 UUID trace/run ID、稳定错误码、首个安全输出耗时和总耗时。模型名、Prompt 版本、Token 和脱敏摘要继续由 `agent_runs` 既有链路记录，不保存原始模型响应。
- `/health/ready` 增量返回 `llm_provider=disabled|ok|error`。`ok` 仅表示服务端 Provider 配置完整，不主动调用收费接口，也不代表 DeepSeek 实时可用；响应不返回 Base URL、模型名或密钥。
- 前端 SSE 客户端要求收到 `done` 才视为协议完整，支持显式取消并保留服务端安全错误信息；意外 EOF 显示可重试错误。建议仍只填入人工输入框，不自动触发平台发送。
- 生产灰度使用 `docker-compose.deepseek-sse.yml`。只有 backend 可通过 `LLM_ENABLED` 开启内部草稿；jobs、agent-worker、AI 翻译、AI 营销和自动回复固定关闭。真实模型 50 授权客户端 P99、首输出和连续五日 99.5% 稳定性必须由测试工程师独立验证后才可申请后续放行。
- 用户并发槽使用唯一 Redis 租约令牌，租约时长固定由 `CHAT_STREAM_TIMEOUT_SECONDS + 60 秒清理余量` 推导；过期清理、容量判断和加入必须原子执行，释放时只能删除当前请求的令牌。单机 50 客户端测试必须在隔离环境显式叠加 `docker-compose.sse-load-test.yml`，将本次 IP 窗口限额提高到 60，并向压测脚本声明同一值；`SSE_LOAD_TEST_ENABLED=true` 只允许在 integration/staging，其他环境启动失败。性能指标按 50 个完整样本的 P99 计算：首个安全 `delta` 必须严格 `<3000ms`，总耗时必须严格 `<5000ms`；等于阈值、样本不足、请求失败或缺失首个安全 `delta` 均失败。CLI 阈值只允许收紧架构上限，JSON 证据必须记录实际毫秒阈值、`strictly_less_than` 比较语义和门禁结果，失败时进程以非零状态退出。
