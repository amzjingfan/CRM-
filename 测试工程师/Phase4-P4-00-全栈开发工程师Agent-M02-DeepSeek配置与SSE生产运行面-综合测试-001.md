## 2. 结论摘要

REAL-FS-05 的确定性工程主体已经具备：`/v1/chat/query` 的 SSE 生命周期、流前 HTTP 错误、流内错误收敛、心跳、断开取消、前端取消与异常结束处理、DeepSeek 服务最小密钥隔离、低敏运行记录、Compose 配置和压测脚本均有实现，专项自动化 96 项、默认后端 1234 项、隔离 PostgreSQL 1246 项、前端 32 项以及前后端构建和静态检查均通过。

但独立审查发现 3 个 P1 缺陷：生产配置接受空白 DeepSeek API Key 且就绪检查误报 `ok`；并发租约固定 180 秒而流超时可配置到 600 秒；文档化的单机 50 客户端压测会被默认同 IP 10 次限流拦截 40 次。这些问题分别破坏配置失败关闭、并发资源门禁和正式性能验收有效性。

此外，本轮没有使用真实客户数据，没有主动触发真实 DeepSeek 付费请求，也没有执行 50 个授权客户端真实模型并发和连续五日稳定性观察。现有 `llm_provider=ok` 只能证明配置形态被当前代码接受，不能证明模型可用、质量合格或生产门禁通过。

因此：

- REAL-FS-05 当前不通过，不建议签署工程验收。
- `AI_PUBLIC_REPLY_ENABLED`、`AI_MARKETING_CONTENT_ENABLED`、`AI_AUTO_REPLY_ENABLED` 应继续保持关闭。
- 真实模型 50 客户端首输出、P99 和五日 99.5% 稳定性门禁不得引用本报告中的合成测试作为替代证据。
- 待 3 个 P1 修复后，应先做独立确定性复测，再由具备授权凭证和成本预算的目标环境执行真实模型性能与稳定性测试。

## 6. 关键场景明细

### 6.1 SSE 协议与错误收敛

以下场景通过自动化和代码审查：

- 鉴权、Origin、CSRF 和限流失败在建立 SSE 前返回统一 HTTP JSON 错误。
- 正常事件序列支持 `accepted/status/delta/result/done`。
- 心跳使用注释帧，不污染业务事件。
- Provider 限流、超时、依赖错误和未知错误转换为规定的统一错误码。
- 流内失败先发 `error`，再发带结束原因的 `done`。
- 客户端断开或取消触发后端取消路径，不把未交付结果伪装为成功。
- 前端区分正常结束、取消、异常 EOF 和服务端错误；“使用建议”只填充输入框，不自动发送。

### 6.2 数据与日志边界

以下场景通过：

- DeepSeek Key 未进入前端可读配置。
- DeepSeek Compose 叠加层只向需要调用 Provider 的后端服务注入密钥。
- jobs 和 agent-worker 的翻译、营销、自动回复开关保持关闭。
- SSE 只传输必要事件，数据库和运行记录使用摘要、模型、Prompt 版本、耗时和状态，不以测试日志输出完整密钥或完整客户数据。

### 6.3 页面冒烟

使用已有本地已登录管理员会话访问工作台：

- 工作台布局、会话列表、聊天区域和 AI 建议区域正常渲染。

## 7. 缺陷

### DEF-REAL-FS05-001：空白 DeepSeek Key 被生产配置和就绪检查判定为有效

| 项目 | 内容 |
| --- | --- |
| 优先级 | P1 |
| 状态 | Open |
| 类型 | 安全配置、失败关闭、健康检查 |
| 影响范围 | 生产启动、`/v1/ready`、运维放行、首次模型请求 |
| 是否阻断 | 是 |
| 建议负责 Agent | 全栈开发工程师Agent |

复现步骤：

1. 以 `APP_ENV=integration` 或 production 构造启用 DeepSeek 的 Settings。
2. 设置 `LLM_ENABLED=true`、Provider/Model 为有效值，并将 `DEEPSEEK_API_KEY` 设置为空字符串或纯空格。
3. 实例化 Settings 并调用 `check_llm_provider_configuration`。

实际结果：

- Settings 接受空字符串和纯空格。
- 空字符串长度为 0 时仍被就绪检查判定为 `true/ok`。
- 生产 Compose 使用 `${DEEPSEEK_API_KEY:-}`，因此空值可真实进入该路径。

代码依据：

- `backend/app/shared/config/settings.py:367` 仅判断 `deepseek_api_key is None`。
- `backend/app/shared/health.py:85` 仅判断 `deepseek_api_key is not None`。

预期结果：

- 启用 DeepSeek 时，空字符串和 `strip()` 后为空的密钥必须使生产配置启动失败。
- 就绪检查必须使用同一校验规则并返回 `llm_provider=error`，不得误报 `ok`。
- 增加空字符串、空格、换行和合法非空 Secret 的独立测试。

### DEF-REAL-FS05-002：并发租约 TTL 短于可配置的最长 SSE 流时长

| 项目 | 内容 |
| --- | --- |
| 优先级 | P1 |
| 状态 | Open |
| 类型 | 并发控制、资源保护、成本控制 |
| 影响范围 | 长响应、用户并发上限、模型成本、资源容量 |
| 是否阻断 | 是 |
| 建议负责 Agent | 全栈开发工程师Agent |

复现步骤：

1. 将 `CHAT_STREAM_TIMEOUT_SECONDS` 设置为允许范围上限 600 秒。
2. 调用 `acquire_chat_stream` 并检查 Redis `expire` 参数。
3. 保持第一个 SSE 请求运行超过 180 秒，再由同一用户发起第二个请求。

实际结果：

- Settings 接受 600 秒总超时。
- `backend/app/shared/database/redis.py:59` 把并发键 TTL 固定为 180 秒。
- 第一个流仍运行时并发键可先过期，后续请求可能重新获得名额，绕过 `CHAT_USER_CONCURRENCY`。
- 默认总超时同为 180 秒时也存在过期与取消/释放竞态窗口。

预期结果：

- 租约 TTL 应大于实际总超时并包含清理余量，且从同一配置来源计算。
- 释放操作应绑定本次租约，避免旧请求释放新请求的名额。
- 增加 180 秒边界、600 秒配置、租约续期/释放竞态和异常退出测试。

### DEF-REAL-FS05-003：默认同 IP 限流使文档化 50 客户端压测无法形成 50 个成功样本

| 项目 | 内容 |
| --- | --- |
| 优先级 | P1 |
| 状态 | Open |
| 类型 | 性能测试有效性、限流配置、验收工具 |
| 影响范围 | 50 授权客户端门禁、首输出/P99 样本、生产放行证据 |
| 是否阻断 | 是 |
| 建议负责 Agent | 全栈开发工程师Agent、测试工程师Agent |

复现步骤：

1. 使用 50 个不同用户 ID 模拟压测脚本中的 50 组授权凭证。
2. 所有请求从同一压测机 IP 发出。
3. 使用默认 `CHAT_QUERY_LIMIT=10` 调用 `consume_chat_query`。

实际结果：

- 用户维度均未超限，但 IP 维度计数共享。
- 50 次请求仅 10 次被接受，40 次被拒绝。
- 当前 README 的单机 50 凭证示例没有同步要求提高压测窗口的 IP 限额或使用分布式来源 IP。
- 因此按当前默认文档执行无法取得 50 个真实成功样本，首输出和 P99 统计不具备门禁效力。

预期结果：

- 提供隔离的性能测试 Profile，明确保持鉴权启用但将 IP 限额设置为不低于计划并发量，并记录完整限流参数。
- 或使用经批准的分布式来源 IP，保证每个授权客户端均可进入真实 SSE 流。
- 压测工具应在运行前检查凭证数、并发上限和 IP 限流容量；成功样本不足 50 时直接判门禁失败。
- HTTP 429 不得计入成功样本，也不得用合成 Provider 结果替代真实模型性能数据。

## 8. 既有风险与观察

### 8.1 前端生产依赖风险仍未关闭

### 8.2 自动化回归数量增加不是生产性能证据

1234/1246 项后端测试和 32 项前端测试证明当前确定性功能无明显回归，但不包含真实 DeepSeek 网络延迟、供应商限流、余额不足、真实首输出时间、P99 或五日可用性。生产放行必须使用独立目标环境证据。

### 8.3 文档迁移版本需在后续交接中同步

当前空数据库实际升级到 `023_marketing_review_idempotency`。若实施记录或运行说明仍引用较早 head，应在后续文档维护中标注历史时间或更新当前值，避免运维误判；本项不影响 REAL-FS-05 产品代码结论。

## 9. 回归与验收建议

### 9.1 修复后必须执行的独立复测

1. 验证空字符串、空格、换行 Key 均无法通过生产 Settings 和 ready 检查。
2. 验证租约 TTL 始终大于实际 SSE 总超时，并覆盖旧流释放新租约的竞态。
3. 使用 50 个不同用户、同一压测机执行预检，确认 50 个请求都能越过限流和用户并发门禁。
4. 重跑 REAL-FS-05 专项、后端全量、隔离 PostgreSQL、前端全量、Compose 和依赖审计。
5. 保持真实平台写操作、公开 AI、营销和自动回复关闭。

### 9.2 确定性复测通过后的生产门禁

1. 由授权人员在目标环境提供 50 组有效、不同用户的短期测试凭证，凭证不得进入仓库和测试报告。
2. 明确本次 DeepSeek 调用成本预算和测试时间窗口。
3. 使用真实 DeepSeek Provider，记录 50 个成功样本的首输出 P50/P99、总耗时 P99、错误率和取消恢复。
4. 验收阈值按 ADR 执行：首输出小于 3 秒、P99 小于 5 秒；指标定义应在测试前冻结。
5. 连续运行五日并验证可用性不低于 99.5%，覆盖超时、429、余额不足、断线和恢复。
6. 测试工程师生成单独的性能与稳定性正式报告，架构师完成最终放行记录。
