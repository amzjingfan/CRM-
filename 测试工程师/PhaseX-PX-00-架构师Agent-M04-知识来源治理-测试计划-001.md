## 2. 测试目标与范围

验证 K1 来源、覆盖单元、公司自编内容版本和审批链能够失败关闭，并为 K3 检索与 K4 私有来源接入提供冻结验收输入。当前只审查文档治理资产，不测试产品代码、向量检索质量、真实 Token、真实店铺数据或生产环境。

范围包含八领域矩阵、七条 TK-US 公开来源、三类首批内容准备、版本审批模板及项目文档排除规则。正式执行须在内容版本产生后由测试工程师独立完成；本计划作者和架构主责不得代填测试结果。

## 3. 环境与测试数据约束

- 文档环境：当前 Git 分支的治理文件，只允许低敏证据。
- 正向样本：三份公司自编确定字节候选已生成，且 `APP-KCV-TK-US-001` 已完成内容、权利和专业复核的哈希绑定；可进入隔离候选索引、冻结样本和独立 QA。
- 负向样本：错误市场、错误语言/读者、未授权应用、过期/撤销、冲突、缺字段、跨店、静态知识询问实时状态等合成低敏样本。
- `shop_private` 样本必须使用稳定的合成 `shop_ref`，不得把真实店铺 ID、Token、订单号、客户或 SKU 私有数据提交 Git。
- 项目 PRD、接口、架构、代码、测试和实施记录只用来验证“必须排除”，不能成为检索答案来源。

## 5. 冻结样本设计

每个首批场景至少准备：5 个明确可回答、5 个条件不足、3 个错误市场/语言、3 个过期或撤销、3 个冲突、3 个越权、5 个实时事实或具体 SKU 拒答样本。每条样本固定 `sample_id`、问题、授权上下文、预期业务四态或 HTTP 401/403、必须/禁止命中的版本、期望引用和拒答原因；冻结文件生成 SHA-256，变更必须升版。

质量阈值不沿用旧 FAQ 的 `0.52`。三个覆盖单元分别要求 Recall@20 ≥90%、Rerank Recall@5 ≥90%、MRR/nDCG@5 ≥0.90、`no_evidence` 正确率 ≥90%、冲突识别率 100%、越权/错误市场/撤销/过期/冲突泄漏为零、引用许可合法率 100%。AI 在校准集提出 Dense/重排分数阈值，测试工程师在未参与调参的独立冻结集签署；未冻结前不得宣称检索通过。

影子对照必须对每条样本记录旧/新四态、Top-5、引用、Agent 终态、延迟和错误；差异审阅率 100%，任何跨店、撤销恢复、冲突返回 `ok`、`unavailable` 降级为自由生成等关键安全差异为 0。语义上合理的新旧 Top-5 差异可由内容负责人书面接受，不要求机械完全相同。

K2 身份负测的预期必须唯一：密钥/`kid`/具体凭据撤销为 401，已认证应用被禁用或请求级空间/店铺/市场/读者越权为 403，授权权威不可用为 HTTP 503 `AUTHORITY_UNAVAILABLE` 且无业务四态信封；合法幂等重试可在 TTL 内复用同一 Token，`jti` 异常并发/跨来源复用须审计并按撤销状态拒绝。

## 6. K1 计划验收条件

- 七条来源的权利状态、禁止用途、复核到期与撤销动作一致且可追溯。
- 三类内容准备保留条件、拒答和空间边界；具体 SKU 未被伪装成共享知识。
- 版本模板覆盖 `DATA-001-KB` 的来源、哈希、适用性、审批、冲突、索引和回滚字段。
- 项目内部文档排除规则明确；敏感值扫描无命中。
- 已批准版本可作为 K3 隔离候选索引、冻结样本和独立 QA 的输入；只有测试工程师完成独立执行、正式报告及发布记录后，才可激活对应索引代际并推导 `service_eligibility=true`。本计划本身不改变覆盖矩阵状态。
