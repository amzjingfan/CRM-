## 1. 目标与已确认边界

建设供公司内部多个系统共用的跨境电商知识服务。知识分类从一开始覆盖跨境电商业务全链路；各领域实际资料按来源、市场和质量门禁分批收录，不能把“分类已建立”描述成“内容已完备”。TikTok Shop（下称 TK）是首个真实业务平台接入与端到端验收对象，不限制知识架构将来支持其他平台。

本方案在本轮需求沟通中已确认以下边界；产品负责人和项目架构评审仍需签署正式文件：

- 项目内部 PRD、代码、接口、实施记录、测试报告和运维材料只用于建设时确定需求，不进入本知识库语料。
- 公司共享领域知识与店铺私有知识分开授权。共用服务不意味着任何内部系统或员工能读取全部知识。
- 客户订单、物流、退款、地址、优惠等当次实例事实由可信业务接口查询，不以静态文档或历史对话替代。
- 知识服务提供可追溯检索证据；CRM Agent 或其他消费系统负责生成、展示和业务动作。知识发布不授予自动对买家发送消息的权力。
- 采集可以自动化，但每个实际内容版本必须通过适用的分类、权限和审批门禁后才进入正式检索。

本文件是待评审设计，不改变现有 ADR、公开接口、数据库、生产开关或放行状态。若评审接受跨系统数据边界和部署方式，再形成相应 ADR 与实施计划。

## 2. 现状与依赖

现有 CRM 使用 FastAPI、PostgreSQL/pgvector、MinIO、异步 Jobs、本地 BGE-M3 1024 维 Embedding 与 `bge-reranker-large`。当前 FAQ 检索采用 Dense Top 20、`pg_trgm` 词法 Top 20、RRF 候选 20 和重排 Top 5。旧 FAQ 的 `knowledge_documents.store_id`、`approved_by` 均直接引用 CRM 表，不能把公司共享知识放进一个伪造店铺，也不能允许第二系统直接读该表。当前 `0.52` Dense 门禁仅由固定 FAQ 评测集校准，不可作为全领域统一阈值。

现有知识语义类型、逐版本审批、店铺隔离和“最多内部人工复核”的安全规则以 ADR-005 为准。v0.1 仍是 TK 人工辅助范围；真实店铺授权、同步和生产 AI/稳定性需独立证据，不能由本设计或已有 Mock 测试替代。

主要前置依赖：

| 依赖 | 用途与约束 |
| --- | --- |
| PostgreSQL/pgvector、MinIO | 结构化元数据、向量与受控原始资料；采用逻辑独立的数据所有权和备份边界 |
| 本地 BGE 服务 | 复用模型与资产校验；新增语料、切分或负载变化须重新评测容量和阈值 |
| CRM 认证与店铺授权 | 由 CRM 适配器把可信主体和店铺授权传给知识服务，不信任浏览器自报的店铺 ID |
| TK 官方接口与店铺授权 | 仅在实际 Scope 和官方契约允许时同步相应店铺资料；现有订单/物流读取不等于已获商品同步权限 |
| 内容负责人和测试工程师 | 审批来源、市场适用性、时效、复测及质量门禁 |

## 3. 路线比较与选型

| 路线 | 收益 | 代价与结论 |
| --- | --- | --- |
| 在 CRM 现有 FAQ 表上继续扩展 | 变更短期最少 | 与 CRM 店铺/用户外键耦合，跨系统授权和公司共享空间难以自洽；不选 |
| 独立知识服务、复用现有模型和基础设施 | 数据及接口归属清楚，CRM 和后续系统都是消费者；保留已验证检索资产 | 需要明确旧 FAQ 迁移与双链路回归；推荐 |
| 直接采用完整 RAG 平台 | 文档解析和管理功能现成 | 会引入第二套审批、身份、存储和运行体系；只借鉴组件或体验，不直接替换现有安全链路 |

推荐在同一仓库内建立独立知识服务应用和内部 API，作为现有 Compose 中可单独运行的服务；可共享 PostgreSQL 集群、MinIO 与 BGE 推理服务，但知识数据由该服务独占写入，其他系统不得直连其表。是否后续拆分基础设施由实际容量和第二消费系统接入结果决定，不预设微服务集群、知识图谱或多 Agent 工作流。

开源参考以官方仓库为准：[pgvector](https://github.com/pgvector/pgvector) 延续现有向量/混合检索；[Docling](https://github.com/docling-project/docling) 可作为复杂 PDF、Office 文档解析的候选适配器，须先通过格式、依赖和资源基准；[RAGFlow](https://github.com/infiniflow/ragflow) 和 [Dify](https://github.com/langgenius/dify) 用于对照切片预览、引用、运营体验。引入任何新组件前需核对版本、许可证、依赖安全和部署成本，不能把候选视作已批准依赖。

## 4. 知识范围、空间与权威来源

### 4.1 全链路知识目录

一级领域固定覆盖：平台开店与运营规则、商品与选品、定价促销与营销、支付风控与订单、仓储物流与清关、售后退换与争议、客服沟通与服务流程、市场税务与合规。每一领域下按平台、国家/地区、卖家类型、语言和目标读者建立覆盖矩阵，允许明确标记“资料待获取”“待审批”“已生效”“已过期”“不适用”，禁止用空分类冒充有效覆盖。

知识形态沿用项目 A/B/C/D 概念，但不强制按形态决定检索权限：A 为获准原始资料，B 为经确认的业务规则，C 为 FAQ，D 为脱敏且获准的典型案例。商品规格等结构化资料保留字段和权威来源，不能只把表格展平成自由文本。法律、税务、合规和平台限制类资料标记高风险；知识服务只提供来源证据，具体操作或对外表述由具备相应权限的人员确认。

### 4.2 知识空间

- `company_shared`：经公司授权共享的跨境电商领域知识，可对具备该空间权限的内部应用开放；仍受平台、市场、语言、读者和时效过滤。
- `shop_private`：商品、售后、物流、话术等某店铺资料，仅对获授权应用及该店铺主体开放。不同店铺不能凭相同查询或向量相似度互见。
- 其他系统如确需部门私有空间，应通过正式需求和权限评审后新增类型；本次不预置任意复杂层级。

每条文档至少保留空间、来源类型及 URL/对象键、使用许可、平台、市场、语言、店铺范围、业务领域、风险级别、适用起止时间、不可变版本与内容哈希、审批主体和审批时间、当前状态。新服务使用稳定的内部主体标识，不在其知识表中引用 CRM 的 `users` 或 `stores` 外键。当前有效版本是查询权威；切片元数据只是副本，检索时须与权威版本再次比较。

### 4.3 来源优先级和冲突

允许的输入为人工维护的 FAQ/规则、商家授权上传的资料、已核对权利的官方或授权页面快照，以及通过实际授权接口获得的 TK 店铺静态业务资料。网页自动抓取只创建待审草稿，不自动发布；不默认抓取任意第三方站点或把平台内容完整再分发。历史会话只有在取得合法使用依据、去标识化并逐条审批后才能进入 D 层。

检索先按平台、市场、店铺和有效期筛选，再考虑相关性。已在审核中登记的来源冲突，或检索结果中明确出现相反的适用规则时，不通过分数大小擅自裁决；输出冲突状态及来源供人工确认。系统不承诺自动识别所有自然语言矛盾；发现未登记冲突时应允许运营人员补录并撤销相关知识。无准确适用范围的高风险资料不得对外作结论。

## 5. 组件、接口与数据流

| 单元 | 职责 | 主要依赖 |
| --- | --- | --- |
| 来源与采集适配器 | 上传、受控网页快照、TK 授权数据同步；登记许可、来源与同步游标 | MinIO、官方接口及权限 |
| 解析与治理 | 格式校验、解析、去重、脱敏、分类、风险标记、人工审核、版本和失效 | 文档元数据、审批身份 |
| 索引 Worker | 只认领获批当前版本，切片并调用本地 BGE，原子替换派生索引 | pgvector、BGE 模型服务 |
| 检索核心 | 校验应用身份和空间授权，执行有效性过滤、Dense/词法召回、重排与证据组装 | PostgreSQL、BGE、Reranker |
| 管理面 | 来源清单、待审队列、版本差异、索引状态、冲突与反馈 | 知识服务管理 API |
| CRM 与其他消费系统 | 传递可信业务上下文，使用证据生成本系统允许的建议或业务流程 | 内部检索 API；各自的身份和安全策略 |

正式链路：来源进入隔离待审区 → 解析/脱敏/去重 → 人工确认语义类型、适用范围、许可和精确版本 → 发布为内部检索可用 → Worker 构建当前版本索引 → 调用系统带可信身份查询 → 服务端执行空间、店铺、平台、市场、时效和审批过滤 → 本地混合召回与重排 → 返回来源、版本、片段、状态和稳定追踪 ID → 消费系统决定呈现、人工复核或拒答。

最小跨系统契约为受控 `POST /internal/v1/knowledge/search`：请求包含查询文本和可选的业务筛选条件，应用身份、可访问空间及店铺授权由服务端凭证与可信适配器确定，不能由请求正文自行授予。响应为 `ok | no_evidence | conflict | unavailable` 之一及类型化证据列表；每条证据至少含文档/切片 ID、当前版本、来源、适用范围、审批准入信息、检索分数和可展示片段。该 API 不执行 LLM 生成、发券、改地址、平台发送或自动回复。管理写入、审批、撤销、索引状态和审计由独立授权接口承载；确切 DTO 与错误码在接口设计任务中固定，不由本草案直接改写现有公开 API。

## 6. 发布、失效与异常处理

文档生命周期为 `draft → reviewed → published/pending → ready`，正文、语义分类或适用范围发生变化即生成新版本并撤销旧版本的当前批准资格。撤销、过期或授权失效须在权威查询条件中立即生效，不以异步删除向量完成为前提；旧切片可随后清理，但不得再被返回。Worker 对内容哈希和版本做幂等检查，失败保留可审计的稳定状态，不能把部分索引标记 `ready`。

模型超时、OOM、权重校验失败、检索候选不一致、来源元数据损坏或权限服务不可用时返回稳定 `unavailable`；权限认证失败在建立检索前拒绝请求；只有正常完成检索且无合格证据时才返回 `no_evidence`。消费系统对此转人工或显示待核实，不退回无知识的自由生成。网页解析失败和 TK 权限不足保留草稿/同步失败状态，不静默产生空政策或假商品。日志只记录低敏 ID、状态、耗时和错误码，不保存完整客户查询、正文、向量、密钥或平台响应。

沿用 ADR-005 的 `approved_for_internal_review` 门禁：即使来源获批，CRM 也最多形成内部人工复核建议，`automatic_delivery_allowed=false`。如未来要开放公共自动回复，必须另立审批语义、评测集、正式测试与生产开关决策。

## 7. 分解、负责人及验收

| 子项目 | 核心交付 | 主责与协作 | 出口条件 |
| --- | --- | --- | --- |
| K1 范围与来源治理 | 全链路目录、覆盖矩阵、许可与风险规则、首批真实市场/来源清单 | 架构师主责；AI、全栈、测试协作 | 每个宣称覆盖的单元都有来源、状态、责任人和复核日期；空白显式标记 |
| K2 独立知识底座 | 空间/版本/审批/审计、内部检索与管理契约、旧 FAQ 兼容迁移方案 | 全栈主责；架构师、AI、测试协作 | 无伪店铺、无跨系统直连表；旧链路未验证前不下线 |
| K3 内容与检索 | 文件/页面解析、切分索引、BGE 混合检索、来源引用和失效 | AI 主责检索；全栈主责采集/管理；测试独立评测 | 当前版本可追溯，过期/撤销/未审批均不可命中，模型故障失败关闭 |
| K4 TK 真实接入 | 按实际授权 Scope 同步可用店铺静态资料并联通 CRM 内部建议 | 全栈主责平台；AI 主责建议；测试独立验证 | 真实店铺授权、正确店铺隔离、幂等同步和人工确认链路有证据；缺 Scope 时不宣称已打通 |
| K5 跨系统复用 | 第二个实际内部系统通过 API 消费证据 | 架构师定义边界；接入系统负责人实施；测试验证 | 不复用 CRM 数据表或 JWT 假身份，权限与审计独立通过 |

K1～K5 各自形成详细设计/实施计划和独立验收；不得以 K2 服务上线代替 K1 全域内容治理，也不得以 TK 联调代替跨系统复用验证。未选定真实的第二消费系统前，只能宣称“提供可复用 API”，不能宣称“已被多系统验证复用”。

通用安全门禁：跨店铺、未授权应用、草稿、撤销、过期、版本漂移、损坏安全元数据均须在独立负向测试中零越权命中；所有正式返回证据应可指向当前有效权威来源。质量门禁：按领域、平台、市场、语言分别冻结有答案与无答案样本，测试 Recall@5、排序质量、无答案拒判和引用合法率；由测试工程师在首批语料上确定阈值并出具报告后才可启用相应单元，不能沿用 FAQ `0.52` 作为通用结论。性能门禁：在实际 Compose/GPU、真实文档量和授权并发条件下复测检索与端到端建议延迟；现有 BGE 容量报告不等于新服务的全链路 SLA。生产门禁继续沿用 v0.1 人工辅助规则和现有 G0～G8 适用项，不因本设计改变。

## 8. 主要风险与评审结论边界

| 风险 | 应对 |
| --- | --- |
| 现有 FAQ 数据外键绑定 CRM，迁移时可能破坏店铺隔离 | 新旧索引分离、版本化映射、双读对照与回滚演练；经独立测试后才切流 |
| “全领域”范围无限扩大、资料时效不同 | 覆盖矩阵和来源负责人常态维护；每次只对已批准且已评测的单元作可用声明 |
| 平台/市场政策冲突或过期 | 权威来源快照、生效区间、冲突状态与人工确认；不以模型分数裁决 |
| 外部资料许可和案例隐私 | 来源使用权审查、最小片段、去标识化、可撤销和审计 |
| 8 GB GPU 与新解析/重排负载竞争 | 解析异步排队，推理并发/批量限流；新增模型或 OCR 前先测显存和延迟 |
| TK 实际 Scope、真实店铺或外部接口未满足 | 以真实授权契约和独立测试为准；缺失时保留手工导入，不伪装自动同步 |

本文件仅提交待评审设计。跨系统知识空间模型、内部服务部署与旧 FAQ 切换属重大数据和模块边界变化，须经架构评审形成 ADR 后实施；产品负责人确认首批可用市场和资料来源，测试工程师确定正式评测集和验收报告。未完成这些门禁前，不声明公司级知识库生产可用或领域知识已完整覆盖。
