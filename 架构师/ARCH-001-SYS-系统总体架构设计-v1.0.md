## 1. 架构目标

构建面向跨境电商的统一智能客服平台，统一接入 TikTok Shop、Shopee 和 Amazon，将平台消息转换为内部标准消息，再通过 AI Agent、知识库和业务工具完成自动回复、人工接管和主动营销。

核心目标：

- 支持多平台消息统一接入和统一客服工作台。
- AI 覆盖物流、退换货、尺码、价格、通用问题 5 类 MVP 意图。
- 支持 RAG 问答、工具调用、置信度判断和低置信度转人工。
- 支持弃单挽回、中差评跟进和数据看板。
- 优先保证可验证、可追踪、可回滚，再逐步扩展规模。

## 2. 总体架构原则

1. **模块化单体优先**：MVP 使用单体部署，但代码按模块隔离；真实出现性能或组织边界后再拆服务。
2. **AI 与业务解耦**：AI Agent 负责决策，业务工具负责执行，第三方适配器负责外部平台通信。
3. **先落库后处理**：平台消息先持久化，再进入 AI 或异步任务，避免消息丢失。
4. **统一领域模型**：业务模块不直接依赖 TikTok、Shopee、Amazon 的原始数据结构。
5. **人工是安全兜底**：低置信度、敏感问题、工具失败和异常场景必须支持转人工。
6. **所有关键动作可审计**：发券、自动发送、转人工和平台授权必须记录操作日志。
7. **配置与代码分离**：模型、Prompt、平台密钥、阈值和运行参数通过配置管理，不硬编码。

## 3. 技术选型

| 层级 | MVP 选型 | 选型理由 |
| :--- | :--- | :--- |
| 管理端 | Next.js + TypeScript + Tailwind CSS | 适合快速构建管理后台和流式交互 |
| 后端 | Python + FastAPI | 与 AI Agent、RAG 和模型 SDK 结合紧密 |
| ORM/迁移 | SQLAlchemy + Alembic | 支持异步访问和可追踪数据库变更 |
| 主数据库 | PostgreSQL | 保存业务数据、会话、消息、订单和指标 |
| 向量检索 | pgvector | MVP 阶段减少独立向量库运维成本 |
| 缓存/队列 | Redis | 会话缓存、限流、幂等和异步任务基础设施 |
| Agent 编排 | LangGraph 或同类 Python 编排框架 | 支持状态、节点、重试和人工接管 |
| 模型 | OpenAI/Claude 兼容模型层 | 支持模型替换、路由和成本控制 |
| 文件存储 | MinIO 或对象存储 | 保存导入文件、原始文档和测试附件 |
| 部署 | Docker Compose，后续 Kubernetes | MVP 简化部署，后续支持水平扩展 |

Java 暂不作为 MVP 主后端，但保留作为后续订单、交易、权限或已有中台服务的独立服务选项。任何引入 Java 服务的决定必须通过 `ADR` 文档确认，避免过早引入跨语言通信成本。

## 4. 分层结构

```text
Next.js 管理端
        ↓ REST / SSE
FastAPI API 层
        ↓
应用服务层
  ├─ 认证与权限
  ├─ 消息与会话
  ├─ 知识库
  ├─ AI Agent
  ├─ 营销流程
  └─ 数据看板
        ↓
领域与工具层
  ├─ 统一消息模型
  ├─ 订单/物流/优惠券工具
  ├─ 平台适配器
  └─ 任务调度器
        ↓
PostgreSQL + pgvector + Redis + 对象存储
```

## 5. 后端模块边界

```text
app/
├─ auth/              # 登录、JWT、RBAC
├─ users/             # 员工、角色和权限
├─ stores/            # 店铺和平台授权
├─ integrations/      # TikTok/Shopee/Amazon适配器
├─ messages/          # 消息接收、发送、状态和幂等
├─ conversations/     # 会话状态和分配
├─ customers/         # 客户画像
├─ knowledge_base/    # FAQ、文档和向量索引
├─ agent/             # AI Agent工作流和Prompt
├─ tools/             # 查订单、物流、发券、转人工
├─ marketing/         # 弃单挽回和中差评跟进
├─ dashboard/         # 指标聚合和查询
├─ jobs/              # 定时任务和异步任务
└─ shared/            # 配置、数据库、日志、异常和公共类型
```

模块规则：

- `agent/` 不能直接调用外部平台或直接修改业务表。
- `tools/` 必须经过权限、参数、幂等、超时和审计处理。
- `integrations/` 只负责外部平台协议转换，不承载客服业务规则。
- `dashboard/` 只读统计模型，不参与消息处理主链路。
- `messages/` 先保存原始消息和标准消息，再触发后续处理。

## 6. AI Agent 架构

```text
客户消息
  ↓
加载会话上下文
  ↓
意图识别
  ↓
判断是否需要业务工具
  ├─ 否 → RAG检索
  └─ 是 → 调用受控工具 → RAG/业务结果整合
  ↓
生成候选回复
  ↓
安全检查与综合置信度判断
  ├─ ≥ 0.80：自动回复
  ├─ 0.60-0.80：回复并标记人工复核
  └─ < 0.60：转人工
```

MVP 采用单 Agent、有限工具、显式状态的工作流，不引入多 Agent 协同和 A2A 分布式协议。

每次 Agent 运行必须记录：模型、Prompt 版本、输入、检索结果、工具调用、置信度、最终动作、延迟和错误原因。

## 7. 多平台消息模型

平台适配器统一转换为内部模型：

```text
PlatformMessage
├─ platform
├─ store_id
├─ external_message_id
├─ external_conversation_id
├─ customer_id
├─ message_type
├─ content
├─ language
├─ sent_at
└─ raw_payload
```

必须实现：Webhook 验签、外部消息 ID 幂等、消息入库、失败重试、发送状态同步、令牌刷新和平台限流。

## 8. 核心数据实体

```text
User / Role / Permission
Store / ChannelAccount
Customer / Conversation / Message
Order
KnowledgeDocument / KnowledgeChunk
AgentRun / ToolCall
MarketingCampaign / MarketingEvent
MetricDaily / AuditLog
```

关键数据规则：

- 所有业务数据必须能追溯到 `store_id`，保证多店铺隔离。
- 消息以外部平台 ID 建立唯一约束，防止重复消费。
- Agent 运行、工具调用和外部写操作必须可审计。
- MVP 先实现 FAQ 问答对，后续再扩展商品文档、业务规则和历史案例。

## 9. 异步任务

以下任务不阻塞用户请求：

- AI 回复生成和平台消息发送。
- 知识库导入、切分和向量化。
- 弃单扫描和中差评扫描。
- 指标聚合和报表计算。
- 失败重试、令牌刷新和状态同步。

MVP 使用 Redis 加任务调度器；任务量增加后再评估 Celery、消息队列或独立 Worker 服务。

## 10. 核心链路

### 10.1 客户消息链路

```text
平台Webhook
 → 验签
 → 幂等检查
 → 原始消息落库
 → 标准化消息
 → 创建/更新会话
 → Agent异步处理
 → 生成回复或转人工
 → 平台发送
 → 更新消息状态和指标
```

### 10.2 主动营销链路

```text
定时扫描
 → 识别弃单/中差评
 → 规则判断
 → Agent生成话术
 → 人工策略/权限校验
 → 调用发券或平台发送工具
 → 记录营销事件
 → 统计转化和GMV
```

## 11. 实施顺序

1. 工程地基：FastAPI、Next.js、Docker、PostgreSQL、Redis、迁移、日志、配置、JWT 和 RBAC。
2. 消息闭环：平台 Webhook、统一消息模型、会话、消息入库和客服工作台。
3. AI 闭环：5 类意图、FAQ RAG、Agent 编排、置信度和人工接管。
4. 工具与营销：查订单、物流、发券、转人工、弃单挽回和中差评跟进。
5. 数据与稳定性：看板、指标、重试、限流、性能、灰度、监控和验收。

## 12. 主要风险与控制

| 风险 | 控制措施 |
| :--- | :--- |
| AI 直接执行危险操作 | 白名单工具、权限校验、参数校验和审计 |
| 平台消息丢失或重复 | 先落库、外部 ID 唯一约束、幂等和重试 |
| 多店铺数据串联 | 所有查询携带店铺上下文，业务层和数据库层双重校验 |
| AI 幻觉和错误回答 | RAG 引用、综合置信度、敏感问题拦截和转人工 |
| 过早微服务化 | 先模块化单体，按真实瓶颈拆分 |
| 外部平台限流或不稳定 | 适配器隔离、退避重试、熔断和状态监控 |

## 13. 验收标准

- 本地可以通过 Docker Compose 启动依赖服务和应用。
- 三个平台消息可以转换为统一内部消息并完成入库。
- 客服工作台可以查看会话、发送人工回复和接收流式 AI 回复。
- 5 类意图识别测试集准确率达到 85% 以上。
- RAG 返回 Top-5 检索结果并保留 score 或引用依据。
- 低置信度、工具失败和敏感问题能够正确转人工。
- 工具调用、平台发送和营销动作可查询、可审计、可重试。
- 核心链路具备单元、集成、端到端和性能测试报告。

## 14. 后续架构变更规则

以下变化必须新建 `ADR` 或升级本架构文档版本：

- 从模块化单体拆分为微服务。
- 引入 Java 独立服务或替换 Python 主后端。
- 替换数据库、向量库、消息队列或 Agent 编排框架。
- 引入多 Agent、A2A 或新的模型路由体系。
- 修改统一消息模型、核心 API 或租户隔离方式。
- 修改生产部署、权限、安全和数据保留策略。
