## 1. 背景与决策范围

公司希望让多个内部系统复用跨境电商知识，TK 为首个真实平台，CRM 为首个消费系统。现有 CRM `knowledge_documents` 和 `knowledge_chunks` 依赖 CRM 的 `stores` 外键，审批人依赖 `users` 外键；把公司共享知识塞入伪店铺或让第二系统直读这些表，会混淆权威、授权和迁移责任。现有 FAQ 的 BGE 分数门禁只对 FAQ 评测，不构成新领域放行依据。

本 ADR 确认独立服务、数据归属、应用身份、空间授权、旧 FAQ 兼容和失败关闭边界。内部 DTO、令牌格式、部署/迁移和回滚基线已分别由 `API-001-KB`、`SEC-001-KB`、`DEP-001-KB` 固定；K2/K3 仍须按这些契约实施和验证。本决策不改现有公开 API 或 ADR-005/006，也不构成内容发布或生产放行。

## 2. 提议决策

### 2.1 服务与数据所有权

在同一仓库中建设可单独启动的 FastAPI 知识服务。推荐同一 PostgreSQL 集群内使用独立数据库、专用最小权限角色和独立迁移历史；MinIO 使用独立受控命名空间与服务凭据。知识服务独占自身权威表的写入，CRM 和未来系统仅经内部 API 消费，禁止对知识表直连、共享数据库角色或建立指向 CRM `stores/users` 的外键。现有 BGE-M3/重排推理服务和 pgvector 可复用，但服务必须独立评测并设并发限额；备份/恢复按知识数据边界单独演练。

部署起点为现有受控 Compose 中的独立服务，不预设 K8s、知识图谱或完整第三方 RAG 平台。若独立数据库的现有备份/迁移工具无法无新增风险支持，评审可选择“同库独立 schema + 专用角色”，但必须证明权限、备份与恢复边界等价；不得退回 CRM FAQ 表扩展方案。

### 2.2 空间、来源和消费系统授权

初始空间只定义 `company_shared` 与 `shop_private`。`shop_private` 必须绑定稳定、低敏的内部店铺代号；没有代号和权威授权关系时不得创建正式私有覆盖单元。知识使用许可是第二层限制：来源即使位于 `company_shared`，仍可限制哪些内部应用、市场、语言、读者和片段形式可消费；未知许可不得默认全公司可见。TK API 店铺资料默认只作为对应店铺私有候选，不因进入共用服务而转换为公司共享资料。

每个消费系统注册独立服务主体和授权策略，浏览器不得直接调用知识服务。服务端请求必须验证短时有效且针对本服务的应用身份证明；店铺私有查询还需验证可信业务系统签发的受委托店铺/用户上下文，并与知识服务侧注册的应用和店铺授权取交集。查询正文提供的 `shop_id`、空间或应用名仅是筛选条件，绝不授予权限。证书、签名算法、签发者轮换和撤销机制在 K2 接口/安全设计中定稿；不得直接复用 CRM 前端 JWT 作为第二系统通行证，也不得用一个全能共享密钥替代每应用授权。

### 2.3 内容、检索和消费边界

来源、内容版本、审批和索引状态分离。正文、语义类型、适用范围或许可变化时形成新版本，旧版本失去当前批准资格；撤销、过期、授权失效和来源冲突在权威查询条件中立即生效，不等待异步向量清理。新服务检索只返回 `ok | no_evidence | conflict | unavailable` 与可追溯证据，不负责 LLM 答案、发券、改地址、平台发送、自动回复或订单实例事实。认证失败在检索前拒绝；权限服务/模型/元数据故障失败关闭，不解释为正常无答案。

项目 PRD、代码、接口、实施记录、测试和运维资料永不作为业务语料。当前客户的订单、物流、退款等实例事实仍走可信业务接口。CRM 使用新证据后仍受 ADR-005 的 `approved_for_internal_review` 与 `automatic_delivery_allowed=false` 约束，v0.1 的 TK 人工辅助边界和生产 G0～G8 不变。

### 2.4 旧 FAQ 迁移与回滚

K2/K3 先构建新库与只读适配器，再把可合法使用、已人工分类且当前版本获批的旧 FAQ 做显式映射；旧记录绝不自动升级审批或共享空间。CRM 先影子查询/双读对照，独立 QA 覆盖权限、版本、Top-5、拒答、引用和延迟，再按授权店铺小范围切流。切流开关必须能立即退回旧 FAQ 路径；旧表/索引在回滚演练和正式批准前保留，禁止迁移时原地改写或删除用户数据。

## 3. 备选方案与理由

| 方案 | 结论 |
| --- | --- |
| 继续在 CRM FAQ 表增添共享标记或伪店铺 | 拒绝；现有店铺/用户外键和 CRM 权限假设与跨系统共享冲突，越权风险难以测试封闭 |
| 独立服务、独立数据所有权、复用已有 PG/MinIO/BGE 基础设施 | 推荐；隔离知识权威和消费端动作，保留已验证基础设施，按实际负载升级 |
| 直接部署完整 RAGFlow/Dify 并以其审批取代现有门禁 | 暂不采用；会引入另一套身份、审批、运行和数据权威。可借鉴解析/运营体验，但引入前另做许可、安全与成本评估 |
| CRM JWT 或单个静态共享 Token 让所有内部系统调用 | 拒绝；无法形成独立应用权限、店铺范围与可撤销审计 |

## 4. 影响、门禁和未决评审项

- 全栈需证明独立数据库/角色、MinIO 权限、备份恢复和 Compose 隔离可在现有 staging 安全落地；若选 schema 替代，必须补充等价性论证。
- 架构/安全需固定签发者、受众、短时证明、店铺授权权威和撤权传播时限；未确认前 K2 不实现可访问真实私有数据的接口。
- AI 与测试需对新语料重新冻结召回/无答案/引用/冲突/显存与延迟指标，现有 FAQ `0.52` 不直接复制。
- 用户已指定首批 TK-US 市场及物流/履约、退换退款、商品信息/规格三个业务场景，并指定架构师Agent统筹来源治理。`RGT-TK-US-PUBLIC-001` 已形成七条公开页面的公司内部受限使用审批，只允许来源元数据、获批公司自编内容、官方链接和内部受控检索，不允许官方正文、快照、原文向量化或片段展示。`APP-KCV-TK-US-001` 已对三个公司自编精确版本完成内容、权利和内部合规签署，但独立 QA、索引代际和发布记录仍未完成，`service_eligibility=false`。`AUTH-TK-US-001` 支持当前 US 店铺的应用授权存在性与应用级 Scope，`AUTH-TK-US-002` 只支持受控配置指向同一应用；稳定 `shop_ref`、平台受控原件、具体店铺令牌 `granted_scopes`、真实只读调用、CRM 运行态绑定及独立测试仍未取得，不能据此放行 `shop_private` 或 API Data 摄取。
- [TikTok Shop 美国卖家条款](https://seller-us.tiktok.com/university/essay?default_language=en&identity=1&knowledge_id=1331308753078058) 对 API 及 API Data 的授权范围和转交限制有专门条款。公开页面可访问不等于允许抓取、复制或在多个内部系统任意再分发；平台/API 资料的具体 RAG 处理和消费范围必须经有权人员审查，不能由本 ADR 代替法律或平台授权结论。

KB-G0 已于 2026-09-15 按 `架构师/验收-001-KB-KBG0联合架构评审结论-v1.0.md` 完成产品、架构、AI、全栈、测试及来源权利/安全角色的记录化签署。K2 可按已确认的 API、安全和部署契约开始实现；K3 可接收已批准版本进入隔离候选索引和冻结评测。K2/K3 实现、独立 QA、真实 `shop_private`/API Data 和生产放行仍是独立门禁。本 KB-G0 与生产 G0 是两个不同门禁。
