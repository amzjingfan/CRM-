# 客服主管管理部门知识库

日期：2026-11-03  
目标分支：`origin/main`  
状态：用户已批准（2026-11-03）

## 目标与范围

客服主管可以管理其所属客服部负责的全部有效店铺的知识库，包括分类、FAQ、文件导入、编辑、审核、发布、撤销与删除。普通客服仍只可按现有权限查看知识；系统管理员保持现有权限。此变更不授予 Agent 配置、其他部门店铺、消息发送或店铺授权权限。

## 当前实现

知识库写接口要求 `knowledge.manage`，主管角色目前只有 `knowledge.view`。现有通用店铺查询会扩展主管的部门店铺，但知识库服务使用的访问校验没有绑定到本次操作的权限码。因此只增加角色权限会让拥有多种店铺角色的账号出现跨店铺权限并集风险。

## 方案

1. 用一条可回滚的权限数据迁移，把已有的 `knowledge.manage` 授予客服主管角色；不修改普通客服或管理员角色。
2. 在统一的店铺权限查询中，为 `knowledge.view` 和 `knowledge.manage` 扩展主管所属部门的有效店铺。扩展须同时满足：账号仍是该部门成员、在该部门至少一家店铺有主管角色、目标店铺仍由该部门负责且有效。角色或部门关系撤销后，下一次请求立即失去对应权限。
3. 知识库所有写路径按**目标资源所属店铺**与 `knowledge.manage` 一起校验；列表与详情按 `knowledge.view` 校验。资源 ID 路径先查授权店铺集合，再查资源，跨店铺仍返回 404。沿用现有 CSRF、幂等、审计及审批约束。对已有的知识库管理界面只调整必要的权限判定，不新增独立主管页面。
4. 用行为测试覆盖管理员、主管、普通客服，部门内多店铺、部门外店铺、撤销主管角色、撤销部门成员资格及多角色混用；验证 UI 可进入且服务端拒绝越权写入。

## 验收

- 主管可在部门负责的每家有效店铺完成知识新增与管理，普通客服不能写。
- 部门外店铺、无效店铺与撤权后的写入均被拒绝；跨店资源不泄露。
- 知识库现有读取、导入审核、幂等与审计行为保持有效；Agent 管理权限不扩大。

## 其他权限优化建议（另列任务）

后续把接待策略、自动化策略和店铺级工具设置统一到“操作权限码 + 目标店铺 + 资源归属”的服务端检查，避免页面权限与后端权限口径不一致。此设计只实施知识库授权，不顺带改变其他模块的写权限。
