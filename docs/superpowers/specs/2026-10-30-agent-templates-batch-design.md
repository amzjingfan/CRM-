# Agent 模板、批量应用与差异更新设计提案

日期：2026-10-30。父任务：MVP-AGENT-TEMPLATE-BATCH-DESIGN-001。

**状态：设计提案，待用户确认完整文档。** 用户已选择“模板＋批量应用”及“查看差异后选择店铺批量更新”；其余默认行为在本文标明为设计建议。本文件的保存或合并只交付提案，不表示已批准实施、迁移、修改现有 Agent 或部署。

## 1. 目标、范围与取舍

解决相似 Agent 在多个店铺重复填写模型、七段提示词、职责和工具，以及后续逐店维护的问题。使用者可将配置保存成模板，一次选择多店创建；以后统一查看差异，按店铺和字段决定更新内容。各店仍有自己的 Agent、知识范围、发布版本、运行记录与会话记忆。

已比较：

| 方案 | 收益 | 代价 | 决定 |
|---|---|---|---|
| 批量复制已有 Agent | 创建改动较小 | 没有模板来源和后续升级能力 | 作为“保存为模板”的来源功能纳入 |
| 模板＋每店独立实例 | 同时解决创建、差异和升级，可复用现有运行架构 | 增加模板版本及应用记录 | 用户已选择 |
| 一个运行 Agent 直接绑定多店 | 集中配置 | 改变现有店铺归属、权限、发布与运行契约 | 首期不采用 |

首期包含：模板创建/编辑/发布/归档；从已有 Agent 提取模板；批量创建；明确关联已有 Agent；三方差异及本店覆盖；知识需求映射；逐店校验/保存/发布；持久批次、失败重试、取消与恢复；历史追溯和逆向更新。

首期不建设：跨店公共知识库、自动分发/复制知识文件、任意脚本/表达式式模板引擎、自动实时同步、模板市场、跨平台新接入、新权限平台或新 Worker 服务。不会开启自动回复、平台写入、营销或主动物流外发。

## 2. 当前实现及接入原则

核对基线：origin/main `b21f59a76adce8775eb5f9d61993e3b42886d72a`。

- `AgentConfig` 必须有单个 `store_id`，同店有效配置编码唯一，当前前端新建仅填写基础字段，模型/提示词/工具/知识后续配置。
- `AgentConfigVersion` 已保存名称、描述、类型、模型、七段提示词、工具、文件和发布信息；运行从已发布版本读取。
- 文件绑定只接受当前店铺可用的 `KnowledgeFile`；检索还有当前有效版本及审批校验。
- 路由器读取当前店铺启用 Agent 的描述，模型选择参与者；工具经现有 `@tool` function call 目录调用。
- 当前管理服务自行 commit；不能直接在批量外层调用多个带 commit 的服务并假称事务原子。

新增能力仅管理配置。**应用模板时将配置实际写入店铺 Agent；运行时不再动态合并或读取模板。** 因而模板草稿、模板发布、模板归档均不直接改变店铺回答；只有店铺 Agent 新版本发布后才生效。

## 3. 核心对象与状态

| 对象 | 职责 | 建议状态/规则 |
|---|---|---|
| Agent 模板 | 名称、用途、可编辑草稿、当前发布版本 | 草稿；有发布版本；归档。允许发布后继续编辑草稿 |
| 模板版本 | 一次不可变的通用配置快照 | V1/V2…；旧版本长期可追溯，不原位覆盖 |
| 店铺 Agent | 本店实际配置与运行入口 | 沿用启用/停用及草稿/已发布版本 |
| 模板关联元数据 | 标识来源、逐字段基线、本店覆盖、知识槽映射 | 一份模板在一个店铺默认关联一个有效 Agent |
| 应用批次与逐店项目 | 保存预览、确认内容、处理状态及结果 | 可恢复、可核对；按店铺独立成功或失败 |

一模板一店一有效实例是**首期建议**，防止重复点击不断创建相同 Agent。用户需要两个相似 Agent 时可新建另一个模板或独立 Agent，不通过模糊名称匹配覆盖现有配置。

模板归档后不接受新的应用或升级批次；现有已发布 Agent 继续运行。归档前已预览、尚未执行的项目须重新校验并阻止新写入。历史模板版本不做产品硬删除。提供管理员“恢复模板”操作，恢复只让模板重新可选，不改变店铺配置；已归档模板需恢复后再执行基于旧版本的逆向应用。

## 4. 模板内容与各店配置边界

### 4.1 模板管理字段

| 字段 | 首次应用 | 后续更新粒度 |
|---|---|---|
| 默认 Agent 名称、建议编码 | 新建时填写；允许逐店改名/选合法编码 | 创建专用，首期不批量重命名/改编码 |
| Agent 类型 | 复制当前支持的服务类/经营类 | 一个整体字段 |
| 职责描述 | 复制；作为店铺路由描述 | 一个整体字段 |
| 模型 Provider＋模型名 | 使用当前已配置的模型 | 成对选择，不能只改 Provider 留旧模型名 |
| 七段式系统提示词 | 完整复制 | 每段单独比较、选择、覆盖或手工合并 |
| 工具清单 | 从现有工具目录选取 | 作为集合比较；显示新增/移除，顺序变化不算差异 |
| 知识需求定义 | 定义用途槽位及是否必需 | 独立审阅，实际文件由各店映射 |

七段顺序固定：身份与职责边界；服务范围；工具使用规则；升级触发条件；语言与输出格式；合规红线；澄清策略与异常兜底。内容由使用人员编辑，遵循现有编译、模型语义复核和发布契约，不增加按业务词正则判断的门禁。

模板可选当前已注册的全部工具，不固定只开放订单/物流等四项；是否可用仍由目标店铺授权和工具执行器决定。`search_knowledge` 沿用现有根据实际文件绑定暴露的规则，不通过勾选工具扩大文件范围。

### 4.2 保持店铺独立的内容

店铺 ID、实际知识文件 ID、平台凭证、客户/订单、会话、记忆、运行日志、启停状态不成为模板内容。源 Agent 的历史、审批状态和发布编号不会复制成另一店铺的历史。

回复偏好 `reply_profile`（品牌、语言偏好等）首期保持现有本店配置，不作为模板管理字段，不复制源店设置。新 Agent 沿用现有默认值；提示词推荐使用“当前店铺”“跟随当前买家语言”等通用表达，各店特殊话术可覆盖对应段。首期不增加占位符表达式引擎，避免引入另一套变量来源和运行时继承。

模板批量应用不修改店铺授权、普通发送范围或部署开关。选择某工具只表示 Agent 可请求调用，不表示已经取得对应业务权限。

## 5. 创建、首次应用及关联现有 Agent

### 5.1 建立模板

两种入口：模板中心“新建模板”；现有 Agent 操作菜单“保存为模板”。后者明确选择已发布版本，或明确选择当前草稿；不能把两者混为同一配置。

只提取4.1所列通用字段。源店文件只转换为用户确认的“知识需求”，不携带文件 ID、正文或实际审批结果。提取后为模板草稿；维护者检查是否存在店铺专属话术，再通过现有七段提示词/模型/工具校验发布 V1。模板发布不是店铺启用。

### 5.2 批量应用向导

1. 选择模板及明确的发布版本；草稿不可作为批量运行依据。
2. 勾选有管理权限的目标店铺，分页/搜索选择，保留跨页勾选。
3. 逐店预检：是否已有本模板 Agent、编码冲突、模型可用性、工具授权、知识映射、是否有未发布草稿。
4. 集中调整差异：目标 Agent、知识文件、本店覆盖。复制某行配置到其他店只复制可共享字段；文件 ID 不跨店复制。
5. 选择动作并确认准确快照：保存草稿；或校验并发布。**新 Agent 默认停用**；如需发布后启用，单独勾选并在确认摘要明确显示。
6. 显示逐店结果，成功项可直接打开 Agent，失败项可重试或重新预览。

新建且只保存草稿：创建停用配置，不产生运行版本。新建并发布但未勾启用：可在当前 Agent 范围调试，不能进入店铺正式路由。明确发布且启用后进入该店路由；不改候选数或工具调用数量规则。

### 5.3 已有配置的处理

- 已有关联本模板的 Agent：默认标“已存在”，可切换到差异更新；不重复创建。
- 仅名称或编码相似：标冲突，不自动认定为同一个 Agent。
- 用户可明确选择同店现有、尚未关联其他模板的 Agent，先看完整差异，再决定哪些字段采用模板、哪些保留本店。
- 关联动作不自动发布或启用，也不重置知识文件。已有 Agent ID、运行/记忆历史及业务归属保持。
- 首次关联以选定模板配置为模板基线；选择保留的不同字段标记为本店覆盖，而非伪报已同步。

## 6. 差异更新：三方比较与覆盖规则

模板 V2 发布后只显示“有新版本”，不更新任何店。操作者选择店铺、目标模板版本和字段后才执行。

每个管理字段比较：A＝该店上次接受的模板基线值；B＝当前店铺草稿值；C＝目标模板版本值。

| 情况 | 展示 | 默认建议，仍须批次确认 |
|---|---|---|
| A=B=C | 无变化 | 跳过写入 |
| B=A、C≠A | 仅模板有变化 | 建议采用模板 |
| B≠A、C=A | 仅本店有变化 | 保留本店 |
| B=C | 已经一致 | 可仅核对并更新来源元数据，不重复发布 |
| 三者不同 | 双方均修改 | 冲突；必须明确保留本店/采用模板/手工编辑 |

工具按集合比较，模型按二元组比较，提示词按七个完整段分别比较。界面可展示行级增删，但程序不自动把两段提示词逐行拼接；模板差异也不由 LLM 直接决定覆盖。

逐字段保存 `baseline_value`、`applied_template_version`、`local_override`、`last_reviewed_template_version`。这些元数据位于店铺 Agent，不改变其运行读取方式：

- 采用模板：写入 C，更新该字段基线与来源版本，取消本店覆盖。
- 保留本店：保留 B，标本店覆盖，并记录已查看当前目标版本；模板下次有新变化仍提示，但默认保留本店。
- 手工编辑：写入用户确认的新值，标本店覆盖；不声称完全等于模板。
- 未勾选/未处理字段：不推进其接受或审阅版本，仍显示待更新。
- “恢复跟随模板”：重新展示当前模板值，明确确认后才取消覆盖并应用；不能因切开关悄悄覆盖正文。

不使用单个“已更新到 V2”标签掩盖部分更新。摘要显示：目标 V2、已一致字段数、本店覆盖数、待处理数；只有管理字段实际与目标版本一致时才显示“与 V2 一致”。保存草稿与已发布生效分别显示。

### 6.1 已有未发布草稿

保存模板差异可与明确审阅的当前草稿合并。发布会发布整份配置，因此如果预览时已有其他未发布修改，默认阻止该行批量发布，不能把其他草稿顺带上线。

需要在向导中展开“当前运行版本→完整目标草稿”的全部差异，并显式勾选“包含已有草稿一起发布”；确认快照必须包含全部字段及精确 revision。不同意时可只保存草稿或跳过该店，不要求覆盖他人修改。

## 7. 知识需求映射

模板只能声明槽位，例如“物流说明”“售后政策”“商品说明”。每个槽位有稳定 key、名称、用途、必需/推荐标记；默认推荐，不能擅自把所有 Agent 都改成必须绑定文档。

批量表中，每家店单独选择本店文件，可一槽多文件或多槽复用同一文件；实际绑定 ID 去重。已有有效映射可预填。

- 发布模式：所选文件须仍存在、同店、未归档/软删，当前版本 ready 且可用于内部建议。必需槽位缺失阻止该行发布。
- 可选槽位无文件：允许工具型 Agent 发布，沿用无知识时仅工具、缺依据澄清的行为。
- 所选文件尚未就绪/审批：可保存草稿；发布前必须等待或明确取消该绑定，不能静默跳过却报告 RAG 就绪。
- 模板新增槽位：提示各店补映射；不会按文件名或相同分类自动绑定。
- 模板移除槽位：默认将原文件保留为本店额外绑定，提示操作者决定；只有明确勾选解绑才移除关联，绝不删除文件。
- 手工绑定的额外文件默认保留。模板槽位和手工绑定共同引用同文件时，移除一个来源不能移除另一来源仍需要的文件。

保存映射时再次核对当前 Agent 的实际绑定；本店手工取消过的绑定显示差异，不凭旧映射静默加回。文件后续审批撤销、有效版本切换等继续遵循现有 RAG 现时校验，不因模板记录而越权。

首期不复制任何文件、向量或审批。若以后需要一次上传多店分发，应作为知识库独立需求设计。

## 8. 批次执行、并发和恢复

### 8.1 首期执行方式（设计建议）

采用**持久批次＋前端自动逐店推进**：用户一次确认后，页面自动调用后端 advance，服务端每次领取一个待处理项目并完成该店操作。批次和快照都在数据库，不存在浏览器内存里。

这是配置管理请求，不运行 Agent、不发送买家消息；不启用现有 jobs/agent-worker 的模型或自动回复开关，也不新增服务。每个项目复用正常发布的模型语义校验与请求预算，不能把二十家店塞进一次长 HTTP 请求。

关闭页面停止发起后续项目，已开始的请求可能完成；重开任务列表后查询真实结果，明确“继续执行”即可恢复。此为首期取舍，**不承诺关闭页面后持续后台跑完**；若用户需要后台无人值守，再另行接入既有任务执行服务并明确其模型权限。

### 8.2 准确确认和失效

预览冻结模板版本、选中店铺/字段、完整目标配置、知识映射、动作模式、精确 Agent revision 和当前发布版本、权限/目录校验结果。确认请求只提交预览 ID 与确认标记，不能夹带未显示的配置。预览本身用批次表的 preview 状态持久化，preview_id 就是该批次 ID，未确认时不会生成或修改店铺 Agent；确认激活同一批次，不另建一份执行计划。

确认时和执行每项时重查权限及依赖。Agent 草稿或发布版本变化、启停变化、目标文件/模板归档、模型目录/工具定义变化影响该项时，要求重新预览。模板新发布 V3 不会把已确认的 V2 项目悄悄改为 V3。

同一确认 Idempotency-Key 重复返回同一批次；相同 key 不同内容拒绝。每个项目以批次＋店铺唯一；不同批次同时创建同店同模板时再由数据库有效关联唯一约束防重。

### 8.3 每店原子提交

一个项目的草稿更新、模板基线、知识映射、可选发布版本/启用状态、逐店成功结果及审计在一个数据库事务内提交。发布失败则本项不留下半份更新，其他已成功店铺不回滚。记录调用消耗与错误类别，但不记录完整 Prompt、私密正文或凭证。

模型语义校验先针对冻结配置执行，之后短事务内重新授权、加锁、核对 revision/依赖和准确配置 hash 后提交；避免持锁等待外部模型。校验过程配置变化则拒绝旧快照。普通管理接口仍保留既有行为；内部提取不自行 commit 的配置写入/发布辅助逻辑，由普通接口或批量项目各自拥有事务，不叠加多次服务 commit。

逐店项目持久租约和唯一执行 token，过期先查事务结果；已成功项目直接返回原结果。旧执行者的迟到结果必须因 token/revision 不匹配而拒绝。网络超时只查询项目状态，不换新 key 重建 Agent；如果事务已提交，以同事务的结果台账判成功，否则过期后允许显式重试。外部模型可能重复产生一次校验费用，不会重复发布同一已成功项目。

### 8.4 结果、重试和取消

项目状态：待处理、执行中、成功、失败、需重新预览、跳过、取消。批次显示总数、已完成、失败、待处理；全部成功/有失败完成/未完成/已取消分别展示。

权限变化、草稿冲突、知识缺失等不盲目自动重试；修正后重做对应行预览，再显式确认新的修订项目。上游临时故障只允许以相同目标配置 hash 重试原失败行；已成功行不重新执行。需要修改映射、字段或版本时重新预览并创建关联原批次的续接批次，只选未成功店铺；原成功和失败记录均保留，不原位改写已确认快照。

取消只停止未开始项，已经提交的成功项保持。当前执行项可完成或因取消中断后查询实际事务结果，不声称全批次已经回滚。

## 9. 页面与操作反馈

沿用现有 CRM/Agent 视觉风格，在 Agent 管理增加“店铺 Agent / Agent 模板 / 批量任务”入口，不重做工作台。模板中心不受顶部“当前店铺”过滤；店铺Agent页仍受该选择约束。批量向导跨店勾选仅限当前操作者有权限的店铺，不改变调试区的当前店铺。

| 页面/区域 | 应有内容 |
|---|---|
| 模板列表 | 名称、职责、类型、已发布/草稿版本、关联店铺数、有更新数、归档状态 |
| 模板编辑 | 复用模型选择、七段提示词和工具分类；配置知识需求；区分保存草稿/发布模板 |
| 批量应用 | 模板版本、目标店铺、目标 Agent、新建/关联/更新、知识映射、错误与动作 |
| 差异审阅 | 按店铺展开A/B/C三列；按字段勾选；冲突必须解决；额外草稿单独醒目标识 |
| 批次进度 | 每店结果、Agent链接、原/新发布版本、失败原因、重试/重新预览/继续/取消 |
| 店铺 Agent 详情 | 来源模板、当前运行版本、草稿是否变化、本店覆盖、模板更新提示、脱离模板 |

“脱离模板”只解除后续同步关系，保留 Agent 当前配置、启停、知识及运行历史。需要重新关联时重新审阅；不自动覆盖。

批量确认摘要必须明确新建/更新/发布/启用的店铺数量、已解析冲突、缺少配置、哪些店仍只保存草稿。键盘、焦点、空列表、分页、加载、权限不足及失败状态与现有组件一致。

## 10. 权限与数据边界（设计建议）

模板库在当前项目内共享，不建设跨项目/租户平台。建议只有现有管理员可新建、修改、发布、归档通用模板；发布动作明确表示将通用配置提供给项目内有 Agent 管理权限的人员使用，不把保存源店草稿直接当作共享发布。

查看已发布模板需 `agent.view`；应用、更新和推进批次需 `agent.manage`；目标店铺逐一走 `allowed_store_ids/ensure_store_access` 等现有服务端检查。非管理员不读取模板草稿、源店私有配置或无权店铺映射。知识选择仍要求 `knowledge.view`，工具保持各自权限。

批次只允许创建者或管理员恢复/取消；按实际当前操作者重新核对每个目标店权限，审计分别记创建者与执行者。权限撤销后不再返回该店详细 Prompt/文件名，仅提供可见范围内的状态和脱敏原因；已有成功不赋予其他店的权限。

全部写操作仍需 CSRF、幂等和审计。模板内容是配置，不是授权令牌；工具目录中的真实代码、范围验证和参数说明不接受模板上传替换。运行上下文/记忆继续绑定店铺、买家和会话，模板不共享记忆。

## 11. 建议数据结构、接口和代码位置

此节是待实现设计，不宣称下列表/接口已存在。

### 11.1 最少持久结构

新增四表：

1. `agent_templates`：id、稳定编码、名称/用途、draft_revision、draft_config_json、published_version、archived_at、创建/更新者及时间。
2. `agent_template_versions`：template_id＋version 唯一，不可变 config_json、config_hash、发布者/时间；含通用字段与知识槽位定义，不含实际店铺文件。
3. `agent_template_batches`：template/version、创建者、预览/确认快照hash、幂等键、parent_batch_id、动作模式、取消标记、总体状态/计数/时间；返回体分页展示逐店项目。
4. `agent_template_batch_items`：batch＋store 唯一、目标Agent、精确预期revision/发布版本、字段选择/完整目标快照/映射、执行token/lease、状态/错误、结果版本/时间。需修改配置的行进入新的续接批次，不覆写原项目或原确认快照。

在 `AgentConfig` 增加可空 `template_id` 和有schema版本的 `template_state_json`：逐字段基线/接受/审阅版本/本店覆盖、槽位与额外绑定来源。有效Agent按 `(store_id,template_id)` 部分唯一；独立Agent为空且保持原行为。`AgentConfigVersion` 增加可空模板来源快照，供已发布运行版本追溯，不引入运行时继承。

草稿元数据只说明草稿接受了哪些模板值；已发布版本的来源随发布冻结。普通保存也可修改模板管理字段，差异比较据实际值检测本店修改；客户端不能直接伪造 template_state_json。普通发布应记录当时真实模板来源/偏离字段。

### 11.2 接口族草案

| 操作 | 建议接口 |
|---|---|
| 列表、新建、查看、修改模板草稿 | GET/POST `/v1/agents/templates`；GET/PATCH `/{template_id}` |
| 查看历史、发布、归档 | GET `/{template_id}/versions`；POST `/{template_id}/publish`、`/archive`、`/restore` |
| 从已有Agent提取草稿 | POST `/v1/agents/templates/from-agent`，明确源Agent及已发布版本或draft_revision |
| 预览新建/关联/更新/回退 | POST `/{template_id}/application-previews`，明确目标版本、店铺、字段和映射 |
| 确认准确计划 | POST `/v1/agents/template-batches`，preview_id＋confirmation＋Idempotency-Key |
| 查批次/项目、推进一项 | GET `/v1/agents/template-batches/{id}`；POST `/{id}/advance` |
| 失败重试、取消 | POST `/{id}/retry-failed`、`/{id}/cancel`；需要修改快照时先重新预览 |
| 脱离模板 | POST `/v1/agents/{id}/detach-template`，精确revision |

静态 templates/template-batches 路由置于通用 `/{agent_id}` 之前。接口使用现有响应封装、权限、分页、CSRF与错误风格。模式及完整字段约束在用户批准设计后的实施计划/API同步时细化，不增加可执行脚本参数。

### 11.3 目录组织

后端统一放 `src/backend/app/agents/management/templates/`，按 models、schemas、service、diff、batch、router 等实际职责拆分；共用既有配置与发布校验。RAG、工具、记忆、路由器实现保持原目录，不复制一套“模板Agent运行框架”。

前端模板页位于现有 Agent 管理下，复用模型/七段提示词/工具组件；应用向导和差异审阅独立组件，避免继续把全部逻辑堆进现有page。集中测试仍只放 `src/tests/`。

## 12. 回退、兼容及验收

### 12.1 回退与旧Agent兼容

老Agent不做批量自动迁移、不自动关联、不变启停。新增字段为空时与现在一致。模板V2效果不合适时选择V1生成逆向差异，仍逐店确认；发布产生新的Agent版本，不重写旧版本/编号。不恢复已经删除/撤销审批的知识文件，不回滚业务数据和会话。

第一期回退就是同一差异应用流程选择旧模板版本，不另建独立回滚引擎。模板归档可阻止后续批次，不能代替回滚已发布实例。

### 12.2 验收清单

- AC-01：一次模板应用到多家有权限店铺，重复确认/网络重试不重复创建；同名不误覆盖。
- AC-02：七段结构、职责、已配置模型、全部已注册工具可复用；实际配置来源及版本可追溯。
- AC-03：模板发布不改变现有运行；保存草稿不更新运行版本；发布/启用是准确确认的独立动作。
- AC-04：覆盖三方差异全部组合、本店覆盖、恢复跟随、仅更新部分字段、已有未发布草稿的显式包含。
- AC-05：知识只映射本店文件；缺必需/未审批/归档/删除/后续撤销均正确处理；手工额外绑定保留。
- AC-06：逐店原子提交；模型失败、revision冲突、权限撤销、租约过期、迟到执行、同店并发、断网及取消不产生半份或重复配置。
- AC-07：关闭页面后批次不丢失，进行中项可核对、待处理项可继续；只有失败行重试，不误称后台自动跑完。
- AC-08：既有独立Agent管理、发布、同店多Agent路由、@tool调用、RAG、记忆、调试及工作台回归；零真实买家发送。
- AC-09：现有管理员/Agent/知识/工具权限沿用，跨店/批次越权与CSRF负例通过，日志不泄露完整私密配置。
- AC-10：模板历史/归档/解除关联/选择旧版本逆向更新可用；结构迁移往返与旧Agent兼容在隔离数据库验证。

集中测试建议覆盖后端差异纯函数、PostgreSQL唯一约束/事务/租约、前端多店向导/冲突审阅/迟到响应，以及沿用当前全量回归。正式IR/TR/RR和机器证据随未来真实实施产生，本轮不虚构功能测试结果。

## 13. 用户确认范围与后续步骤

用户已决定的两点：模板＋批量应用；先看差异、选择店铺再更新，不能自动实时同步。

需要随本提案确认的设计建议：一模板一店一有效实例；新建默认草稿停用；管理员维护模板/有权限人员应用；字段级保留本店修改；知识按槽位本店映射；首期前端自动推进并可恢复，关闭页面暂停后续；不新增变量引擎和跨店知识共享。

文档批准后再生成分步实施计划，确定接口schema、可逆迁移和行为测试，并按用户当时授权开发/本地验证；本轮不实施、不开关、不部署。预计是配置管理的一项中等规模完整功能，不是对Agent运行框架再次重写。

文档检查：独立实施者检查结论为“nothing important left”；此结论只说明提案已足以编写实施计划，不代表用户已批准设计或已完成功能验证。
