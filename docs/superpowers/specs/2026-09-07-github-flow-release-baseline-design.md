## 1. 目标

在工作区根目录 `E:\develop\CRM智能聊天系统` 建立唯一 Git 仓库，把产品代码、架构文档、测试报告、共享记忆文档和开发工具纳入同一条可追溯历史；从本次基线开始，后续开发统一采用 GitHub Flow。

本设计同时冻结一个可验证的 MVP 预发布基线，固定代码提交、数据库迁移、配置版本、评测数据及结果摘要，并在 Docker 可用时记录容器镜像的内容寻址摘要。

### 3.1 纳入版本控制

- `CRM智能聊天系统/` 中的源代码、迁移、测试、部署配置、配置示例和模型资产清单。

### 3.2 排除版本控制

- 所有 `.env` 和 `.env.*`，仅允许提交 `.env.example`。
- 私钥、证书私钥、Token 导出、凭证池及本地安全配置。
- 模型权重格式，包括 `*.bin`、`*.safetensors`、`*.pt`、`*.pth`、`*.onnx`、`*.gguf`；模型说明、许可证和 `model-manifest.json` 继续跟踪。

- `.worktrees/`，避免后续 Git worktree 被父仓库再次纳入。

根 `.gitignore` 是仓库级权威规则；产品子目录现有 `.gitignore` 保留，作为就近说明和纵深保护。

## 4. GitHub Flow

### 4.1 长期分支

唯一长期分支为 `main`。`main` 必须始终可构建、可测试，并只通过已验证的合并提交发生变化。

仓库首次建立存在一个明确例外：设计规格作为 bootstrap 提交直接进入 `main`，因为仓库和分支尚不存在。其余基线工作在 `docs/release-baseline-20260907` 短期分支完成。

### 4.2 短期分支

- 功能：`feature/{任务编号}-{简短主题}`
- 修复：`fix/{缺陷编号}-{简短主题}`
- 文档和治理：`docs/{任务编号或主题}-{简短主题}`
- 紧急修复：`hotfix/{缺陷编号}-{简短主题}`

分支必须从最新 `main` 创建，一个分支只处理一个可审阅目标。推荐使用 `.worktrees/{分支名安全化目录}` 隔离并行工作。

### 4.3 提交和合并

提交消息使用 Conventional Commits：`feat:`、`fix:`、`docs:`、`test:`、`build:`、`ci:`、`chore:`。正文记录任务编号、验证结果和风险。

有 GitHub 远程后，所有短期分支必须通过 Pull Request 合并，至少要求 CI 通过、无密钥或大文件误提交、文档和实施记录同步。默认采用 squash merge，合并后删除远程和本地短期分支。

本轮因没有远程，允许在完成同等检查后执行一次本地 squash merge，并在实施记录中登记该 bootstrap 例外。后续不得把该例外扩展为日常直接提交 `main`。

## 5. GitHub 仓库治理文件

- 根 `.gitattributes` 固定文本规范，Markdown、YAML、JSON、Python 和 TypeScript 使用 LF；PowerShell 脚本保留项目要求的 CRLF，二进制文件不做文本转换。
- `.github/pull_request_template.md` 强制填写需求范围、变更、验证、文档同步、安全检查和风险。
- `.github/workflows/ci.yml` 对 Pull Request 和 `main` push 执行后端 Ruff、格式检查、mypy、pytest，以及前端 lint、typecheck、test、build。
- 根 `AGENTS.md` 增加 GitHub Flow 强制规则，使后续 Agent 在开始修改前确认分支、工作区状态和基线；禁止提交密钥、大模型权重和生成目录。
- `共享记忆文档/Git与GitHub Flow开发规范.md` 面向团队说明日常命令、分支命名、PR、合并、回滚、标签和首次远程配置方式。

CI 不声称替代真实 PostgreSQL、真实模型、真实平台或性能门禁；这些门禁继续引用测试工程师权威报告。

## 6. 发布基线

### 6.1 标识

- 应用版本：`0.1.0`
- 基线标签：`v0.1.0-mvp.20260907`
- 基线性质：MVP 预发布工程基线，不代表生产放行
- 数据库迁移：`023_marketing_review_idempotency`

标签为带注释标签，最终指向本地 squash 合并后的 `main` 提交。固定提交通过 `git rev-list -n 1 v0.1.0-mvp.20260907` 唯一解析，不在同一提交的文件中写入会产生自引用循环的提交 SHA。

### 6.2 机器可读清单

创建 `release/baselines/v0.1.0-mvp.20260907.json`，至少包含：

- schema 版本、应用版本、基线标签、生成时间和生产放行状态。
- Alembic head 与迁移文件 SHA-256。
- 受控配置文件路径及 SHA-256，包括 `.env.example`、Python/Node 版本文件、锁文件、Dockerfile 和 Compose 文件；不读取或散列 `.env`。
- 评测数据、清单、结果文件、模型、Prompt、DLP 策略、运行 ID 和 SHA-256。
- 每个应用镜像的标签、Docker image ID、RepoDigest 和构建输入摘要。
- 未完成门禁和证据路径。

清单只记录相对路径和低敏元数据。所有文件摘要由脚本或 `Get-FileHash -Algorithm SHA256` 从实际文件生成，禁止手填未经核验的值。

### 6.3 镜像摘要语义

- 本地构建成功后记录 `docker image inspect` 返回的 `Id`，字段名固定为 `image_id`。
- 只有镜像推送到内容寻址仓库并获得 `RepoDigests` 后，才能填写 `repo_digest`。本地镜像没有 RepoDigest 时使用 JSON `null`，不得填入镜像 ID 或 Dockerfile 摘要。
- Docker 未恢复或构建失败时，基线清单记录 `image_status=unavailable`、失败原因和构建输入 SHA-256；此时 G0 的“镜像摘要”子项保持未通过，整体基线状态为“部分完成”，不能创建宣称完整生产发布的标签。
- 若源代码和文档已冻结但镜像仍不可用，可创建上述预发布标签；正式生产版本仍必须在镜像 RepoDigest、备份恢复和其他生产门禁齐备后另行创建新的 SemVer 标签。

## 9. 安全与失败处理

- 首次全量暂存前执行忽略规则验证，确认 `.env`、模型权重、虚拟环境、依赖和缓存均被忽略。
- 对候选跟踪文件执行大文件清单和敏感文件名检查；检查输出只显示路径和规则，不显示密钥内容。
- 如果发现疑似密钥文件进入候选集，停止提交，修正忽略规则后重新验证。
- 如果 Git 初始化或提交失败，不删除现有文件、不重置工作区，保留可恢复状态并报告失败。
- 如果 Docker 启动或构建需要额外系统权限或网络访问，使用明确授权；失败不阻塞源代码基线，但必须降低 G0 和实施记录状态。

## 10. 验收标准

1. 根目录是 `main` 为默认分支的 Git 仓库，工作区根能解析为仓库顶层。
2. `.env`、权重、`.venv`、`node_modules`、缓存和测试临时目录全部未被跟踪，配置示例和模型清单仍被跟踪。
3. GitHub Flow 规范、PR 模板和 CI 工作流存在，命令与项目实际目录一致。
4. Alembic head、配置文件、评测数据和结果 SHA-256 由实际文件复算并进入机器可读清单。
5. Docker 可用时记录本地 image ID，并严格区分 RepoDigest；不可用时如实记录，不宣称镜像门禁通过。
6. README、架构 v1.5、生产放行检查表 v1.1、两个索引和两份缺失文档完成同步。
7. 后端与前端质量检查按当前可用环境执行；Docker/真实外部依赖未执行项明确说明。
8. 基线分支经验证后本地 squash 合并到 `main`，创建带注释标签 `v0.1.0-mvp.20260907`；仓库无未说明的已跟踪变更。
