# 动态多 Agent 重写设计（已确认，实施中）

## 目标与现状

目标是让运营人员在 Agent 管理页创建并发布多个店铺 Agent，自选项目已配置的模型、编辑七段式系统提示词、绑定已审批知识文件及可调用工具。模型按 Agent 描述选择一个或多个 Agent；每个 Agent 根据自己配置的工具说明选择零个或多个能力，授权只读调用可自动执行，写入建议须人工确认，最后汇总为一段供坐席审核的回答。新 Agent 发布后进入当前店铺的动态注册表，无需改代码或重启。

当前 `app.agent`、`app.agent_management`、`app.tools` 分散；`agent_configs` 约束同店仅一个启用 Agent，模型/Prompt 只读，`tool_routing.py` 使用固定正则；会话只取最近最多 10 条消息，RAG 的 6000 token 限额不是总上下文预算。通用文件导入与显式绑定检索已经实现；旧 Agent FAQ 专用回退仍在正式路径。重写须保留现有工作台、知识库、人工发送和店铺安全能力。

## 已确认产品决定

1. Agent 可以由使用者动态创建、配置、启用；同店允许多个启用。当前店铺所有已启用 Agent 都是路由候选，不按预设类型或数量排除；模型依据职责描述判断是否选用。每个 Agent 实际可执行的能力仍受服务端权限约束。
2. 路由模型依据该店铺所有已启用 Agent 的名称、职责描述与服务范围，语义选择一个或多个 Agent，不用固定词形正则选 Agent，也不按固定数量裁掉候选。混合问题由多个 Agent 分别处理，再汇总成一段回答。模型通过结构化 function call 返回选中的 Agent ID 与子问题；服务端校验店铺、状态和权限。
3. 每个 Agent 配置的全部工具都进入候选目录，不设置固定数量上限；目录同时标明本次会话可用性、读写级别、名称、适用条件、描述、参数/结果 Schema。工具实现统一使用 `langchain_core.tools.tool` 的 `@tool` 装饰器，复用现有 Pydantic 参数契约；Provider 将这些定义转换为原生 function-calling Schema。模型可选择零个或多个工具，服务端逐项校验并执行。只读工具获授权后可自动执行；写工具即使被模型选中，也仅形成待人工确认的动作，不能由模型直接执行或发送 TikTok 消息。可信订单/客户 ID 由服务端注入，不接受模型编造。知识检索同样以 `@tool` 暴露，但严格限定该 Agent 绑定文件。转人工是受控决策。
4. 七个可编辑、必填的系统提示词段落依次为：身份与职责边界；服务范围（做什么/不做什么）；工具使用规则（读宽写严）；升级触发条件（可观测信号）；语言与输出格式；合规红线；澄清策略与异常兜底。发布形成不可变版本，调试/运行引用精确版本。平台安全规则独立于用户编辑文本执行。
5. Agent RAG 仅检索该 Agent 显式绑定、当前有效且获内部审批的同店知识文件。未绑定文件时不回退旧 FAQ，不隐式使用店铺默认知识集；仅使用本次获授权的已绑定工具，知识不足时澄清或转人工。移除的是 Agent 内旧 FAQ 专用回答/检索路径；知识库 FAQ 数据、管理、导入功能保留。
6. 记忆只在同一店铺、同一会话、同一用户内使用，不跨会话或跨用户。同一会话关闭后再打开，恢复此前已验证的记忆；被删除或权限变化的会话不得恢复。
7. 所有输出仍是人工辅助建议。公开自动回复、平台消息和高风险写入不因重写开放；现有授权、CSRF、幂等、DLP、审计和失败关闭不降低。

## 模块分工

代码统一收敛到 `src/backend/app/agents/`：`management/` 管版本配置与状态；`orchestration/` 管模型路由、子 Agent 并发和汇总；`runtime/` 管工作流、状态机、上下文预算与冻结快照；`tools/` 管 Agent 工具目录、模型选择和可信执行适配；`rag/` 管 Agent 绑定文件查询；`prompts/` 管七段式版本和渲染；`memory/` 管会话内摘要/事实的隔离读写与生命周期；`safety/` 管输入、输出、注入和敏感信息；`providers/` 管模型适配。通用文件上传、MinerU 解析、分块、向量入库继续由 `app.knowledge_base` 维护；工作台共用工具契约不复制实现。移动期间保留短期导入兼容层，迁完调用方后删除。

## 一次运行的数据流

1. 服务端校验店铺、会话、触发消息、买家身份与运行开关；按触发消息水位冻结快照：配置/Prompt 版本、工具白名单、知识文件及版本、会话记忆 revision、权限和截止时间。新到消息进入下一次运行。
2. 上下文组装器以结构化字段提供当前问题、近期消息、已验证会话摘要、关键事实、工具证据和知识引用。关键金额、币种、时间、状态、政策原句保留原值与来源；压缩只能改可压缩摘要。个人标识只传必要的低敏投影。总输入上限由所选模型上下文窗口减去输出保留和安全余量计算；优先削减旧历史和低相关检索，关键事实放不下则澄清/人工复核。
3. 路由模型通过 function call 返回 `agent_id + 子问题` 列表；该店铺所有已启用 Agent 均可被选择。服务端重查同店启用状态、配置版本、工具和知识授权。零匹配走澄清；多匹配并行执行、共享总截止时间，互不共享私有工作记忆。若目录超过模型/Provider 单次请求容量，分批覆盖所有候选并合并选择结果，不静默截断。
4. 每个子 Agent 仅看到自己的七段式提示词和配置的完整工具目录及当前授权状态。模型原生 function calling 选择零个或多个工具；服务端解析 `tool_call_id/name/arguments`，校验 Schema、权限与可信对象，执行可自动执行的只读工具，再把对应工具结果回送模型，直至输出回答或到达总截止时间。重复同一无效调用应收敛并留下原因码，不设固定调用次数上限。写工具转人工确认，工具/RAG 内容是数据，不能升级为系统指令。无知识且工具不支持的问题不凭模型常识断言店铺政策。
5. 子 Agent 输出草稿、引用、工具事实引用、不确定项和审核标志。汇总器只读这些结果及证据，输出一段回答；冲突、失效引用或缺少必要证据时明确无法确认。确定性校验、DLP 和独立安全复核通过后才展示给坐席；发送仍须原人工确认链路。
6. 成功/失败/超时均写脱敏运行记录；记忆写入在回答校验后作为独立候选流程，不让模型直接持久化。记录运行时所用快照版本与 hash，不记录完整 Prompt、客户正文或原始工具响应。

## 状态、记忆与安全契约

- 配置状态：`draft → enabled ↔ paused → archived`。发布的配置不可变；修改生成新版本。既有 `enabled/disabled` 迁移映射需保持旧 API 在过渡期可用。当前店铺所有已发布且启用的 Agent 进入路由注册表，执行权限与工具风险在服务端另行校验。
- 运行状态与业务动作分开：既有 `running/succeeded/failed/timeout` 对外兼容，内部增加 `queued/snapshot_frozen/routing/executing/aggregating/validating` 阶段及 `review_ready/clarification_required/cancelled` 终态原因。主运行关联子 Agent 运行；状态转换须原子、幂等，超时能收敛，不能永远停在 running。
- 会话记忆三层：本次运行临时工作记忆、当前会话结构化摘要、带消息/工具/文件来源的关键事实。后两层持久化时同时绑定 `store_id + conversation_id + customer_id`，版本化并带验证状态；策略/知识仍在知识库，不写成记忆。读路径只取有效 revision，写路径只接受通过来源与安全校验的候选；关闭会话只冻结写入，重开同一会话恢复，删除会话/用户同步失效并清理派生记忆。订单/物流等时效事实必须在新运行中重新读取或标明旧时间。
- 七段式业务提示词可编辑，但平台指令、工具权限和真实发送开关由服务端固定规则控制。用户消息、RAG、工具自由文本、记忆摘要与其他 Agent 输出一律按不可信来源处理；注入检测只是纵深措施，不能替代权限检查。敏感信息使用按来源和字段分类的允许/脱敏/人工复核规则，区分合法 SKU/政策编号与地址、凭证、个人资料；输入、记忆候选及最终输出均检查，日志只存固定原因码。
- 首期无自主执行写工具、无跨用户或跨会话长期记忆、无额外微服务/插件平台、无隐式全店知识检索。候选数量不设业务硬上限，但模型上下文、Provider 接口容量与整轮超时仍是必须可观测的技术边界；容量不足时分批覆盖或明确失败，不能遗漏候选后假装完整回答。

## 验收与发布边界

行为测试须覆盖：多 Agent 语义路由与汇总、同店动态启用、工具零/单/多选及误选拒绝、无绑定文件的工具/澄清、文件审批撤销、关键事实原值、预算溢出、会话关闭重开恢复、跨用户/跨店拒绝、并发消息快照、记忆污染、文档/工具注入、敏感数据、子 Agent 超时与冲突、取消收敛、零平台发送。隔离 PostgreSQL/pgvector、前端契约/浏览器、版本化 AI eval 和 staging 真实模型/只读工具验收分别保留证据。完整 MVP 的安全首输出与总耗时 P99 < 5 秒是既有长期门禁；多 Agent 链路未经现场测量不得宣称达标或放行 production。

## 实现依赖与边界

`langchain-core` 当前已由 `langgraph` 间接锁定；实施时在 `pyproject.toml` 显式声明直接依赖，使用其 `@tool` 和工具 Schema 转换能力。现有 DeepSeek Provider 通过 OpenAI SDK 调用 Chat Completions，需新增原生 `tools/tool_choice/tool_calls` 多轮适配；工具调用轮次与最终 JSON 回答分开处理。DeepSeek 思考模式下连续工具轮次须按官方协议回传必要的推理状态。其他可配置模型 Provider 也须通过 function-calling 能力校验，未适配的模型不能发布为具备工具能力的 Agent。参考：[LangChain 工具参考](https://reference.langchain.com/python/langchain-core/tools)、[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)。
