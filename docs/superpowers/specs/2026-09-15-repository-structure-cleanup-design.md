# 仓库子智能体目录压缩清理设计

状态：待用户复核  
日期：2026-09-15  
目标分支：`docs/repository-structure-cleanup`

## 1. 目标

取消“一级目录即项目成员/子智能体”的仓库组织方式，删除以下六个一级目录：

- `全栈开发工程师/`
- `AI agent 开发工程师/`
- `共享记忆文档/`
- `开发工具/`
- `架构师/`
- `测试工程师/`

目录中的文件不原样换目录保存。有效内容必须先去重、合并、改写为少量面向用途的当前文档；过期版本、重复报告、角色说明、逐任务流水账和外部 Skill 副本直接删除。Git 历史与发布标签承担历史全文追溯职责。

## 2. 当前规模与问题

六个目录合计约 441 个文件，其中 424 个受 Git 跟踪，正文约 7.06 万行。主要问题是：

1. 项目事实按负责人分散，而不是按产品、接口、架构、测试和运维用途组织。
2. 架构与 AI 规范以“基础文档 + 多份增量说明”串联，阅读当前状态必须追溯多个版本。
3. 每次实施和复测都生成独立 Markdown，形成大量重复环境、范围和结论描述。
4. `开发工具/skills/` 保存通用外部 Skill 副本，与产品运行无关，并增加维护和审计成本。
5. 多份 `AGENTS.md` 互相引用角色目录，导致删除任一角色目录都会产生规则断链。
6. 测试证据、测试程序、测试报告和发布清单混放，机器需要的不可变证据与人读文档边界不清。

## 3. 清理边界

本次只调整仓库组织和文档治理，不改变：

- 前后端、AI Agent、数据库迁移和第三方平台接入的运行行为；
- 公开 HTTP/SSE 接口、配置键、权限和生产安全边界；
- `CRM智能聊天系统/` 下的正式产品实现；
- 已发布 Git 标签和历史提交；
- 模型权重、`.env`、真实凭证和现有辅助 worktree；
- 当前限定发布范围：TikTok 人工辅助 v0.1，三平台完整 MVP 仍未完成。

本次不以减少磁盘空间为主要验收目标。本地缓存、模型权重和旧 worktree 清理由独立任务处理，避免与受版本控制的结构迁移混杂。

## 4. 目标结构

```text
仓库根目录/
├─ .github/                         GitHub 工作流、CODEOWNERS、PR 模板
├─ CRM智能聊天系统/                唯一产品工程目录
│  ├─ backend/
│  ├─ frontend/
│  ├─ deploy/
│  └─ tests/
├─ docs/
│  ├─ README.md                     文档导航与事实优先级
│  ├─ product.md                    产品目标、范围和验收标准
│  ├─ api.md                        当前有效管理端接口
│  ├─ architecture.md               当前完整系统架构
│  ├─ ai.md                         当前 AI、RAG、工具和安全契约
│  ├─ development.md                编码、Git 和交付规范
│  ├─ deployment.md                 TikTok、DeepSeek、staging 运行边界
│  ├─ release-gates.md              当前生产门禁及证据入口
│  ├─ test-status.md                当前测试结论和未关闭缺陷矩阵
│  ├─ open-work.md                  尚未完成的实施事项
│  └─ history.md                    压缩后的关键项目时间线
├─ release/
│  ├─ baselines/                    机器可读发布基线
│  └─ evidence/                     发布基线必须长期存在的低敏机器证据
└─ AGENTS.md                        唯一项目级协作与安全规则
```

现有 `docs/superpowers/` 设计和计划文件暂时保留；它们属于已经批准方案的设计依据，不属于子智能体目录。本次完成后可另行评估是否压缩。

## 5. 内容压缩规则

### 5.1 产品、接口与开发规范

- PRD、MVP 范围、验收标准和任务拆解合并为 `docs/product.md`。
- 只保留当前仍有效的产品目标和 TikTok v0.1/完整 MVP 两级范围；已完成的人天排期不再逐项复制。
- 管理端接口文档压缩为 `docs/api.md`。当前已实现接口优先，早期草案只在仍表达未实现产品目标时保留，并明确标为规划项。
- 代码编写手册、GitHub Flow 规范和仍有实际约束力的测试命名要求合并为 `docs/development.md`。
- 页面原型若已被当前前端实现取代则删除；仍用于产品验收时只保留必要截图或入口说明，不继续保存一份独立、可运行的历史 HTML。

### 5.2 架构与 ADR

- `ARCH-001` v1.0～v1.5 合并为一份可独立阅读的 `docs/architecture.md`，不得保留“继承上一版本未变更内容”式依赖。
- 数据库初版与 BGE 增量合并到当前架构的数据章节；当前数据库迁移和代码是结构事实的最终权威来源。
- ADR-001～ADR-007 不按原文件直接搬运。仍有效的决策按主题压缩进架构、AI、部署和发布门禁文档，并保留决策编号、状态、日期、核心原因和不可突破的边界。
- 已废弃或仅用于编号纠偏的决策写入 `docs/history.md` 一行摘要，不保留全文。
- v1.0 生产检查表由 v1.1 当前状态取代；只把当前适用门禁压缩进 `docs/release-gates.md`。

### 5.3 AI 规范与计划

- AI-001～AI-005 的当前生效内容合并为 `docs/ai.md`，覆盖模型适配、RAG、工具执行、结构化声明、翻译营销和失败关闭规则。
- AI-002、AI-005 的多版本增量链必须先归并成完整当前契约，再删除全部原版本。
- BGE 模型固定 Revision、运行文件哈希与下载校验方式写入 `docs/deployment.md`；机器值仍以 `deploy/models/model-manifest.json` 为准。
- AI-006 已由 ADR-005 和现有实现承接，仅在历史时间线记录，不保留评审请求全文。
- PLAN-001/PLAN-002 只提炼尚未完成、仍阻断发布的事项到 `docs/open-work.md`；已完成步骤不迁移。

### 5.4 实施记录

- `共享记忆文档/实施记录/` 不建立镜像归档目录。
- 从实施记录中提取关键里程碑、重要安全边界变化、发布基线和遗留风险，写入 `docs/history.md`。
- 每条时间线最多包含日期、任务/决策编号、结果、关联提交或发布标签、遗留风险，不复制测试过程和修改文件清单。
- 原实施记录及其索引全部从当前工作树删除；历史全文继续存在于 Git 历史和已有标签。
- 后续不再要求每次修改生成单独实施记录。重要架构变化使用 ADR，用户可见变化使用变更说明，发布状态使用 release baseline。

### 5.5 测试报告与证据

- 以测试主题为单位读取报告链，只保留最新正式结论、未关闭缺陷和适用环境，汇总到 `docs/test-status.md`。
- `docs/test-status.md` 使用稳定矩阵：模块、门禁、当前结论、证据标识、未关闭缺陷、最后验证日期。
- 重复复测报告、已经被后续报告完全取代的报告和报告索引全部删除，不迁入新的报告目录。
- 发布基线或模型清单直接引用的证据必须保持机器可验证。必要的 JSON、JSONL、manifest 和哈希证据迁入 `release/evidence/`，并同步更新机器清单路径与摘要。
- 独立验证脚本先与 `CRM智能聊天系统/backend/tests/`、`backend/scripts/` 的现有覆盖进行对照。重复脚本删除；仍具备唯一生产门禁能力的逻辑合并到现有校验脚本，或保留为一个角色无关的 `backend/scripts/verify_bge_production_gate.py`。
- 证据目录中的 `__pycache__` 等忽略文件不属于迁移对象。

### 5.6 开发工具与角色规则

- `开发工具/skills/` 的外部通用 Skill 副本全部删除，不迁移到新目录。
- 删除六个角色目录中的 `AGENTS.md`，以及根规范中的“目录即员工”、角色分工和实施记录强制要求。
- 根 `AGENTS.md` 改为唯一规范，只保留安全、代码质量、测试、文档同步和 GitHub Flow 要求。
- `.github/CODEOWNERS` 从角色目录所有权改为产品代码、文档和发布资产所有权。
- PR 模板不再要求角色实施记录和测试工程师目录，改为要求按风险更新 `docs/` 或 `release/`。

## 6. 路径兼容与引用更新

迁移和删除必须在同一分支完成。至少更新以下引用源：

- 根目录与产品目录 `AGENTS.md`；
- `.github/CODEOWNERS`、PR 模板和工作流；
- 产品 `README.md`、模型 README、staging/production 部署说明；
- `deploy/models/model-manifest.json`；
- `release/baselines/*.json`；
- `docs/superpowers/` 中仍作为当前操作依据的设计和计划；
- 代码、测试或脚本中硬编码的六个旧目录路径。

历史文档中的角色名称只有在该历史文档仍保留时才改写；Git 历史中的旧路径不做重写。不得使用历史重写、强制推送或修改已有发布标签来隐藏旧结构。

## 7. 实施顺序

1. 冻结并导出六个目录的文件、引用和发布清单依赖清单。
2. 先生成十一份压缩文档草稿，并逐条标记内容来源。
3. 对架构、接口、AI 安全和发布门禁进行一致性复核，解决互相冲突的历史表述。
4. 将发布必需的低敏机器证据归并到 `release/evidence/`，重新计算并登记 SHA-256。
5. 合并或删除测试脚本，确保唯一生产门禁能力仍可执行。
6. 更新 AGENTS、GitHub、README、模型清单、发布基线和部署文档引用。
7. 执行旧路径零引用检查，但允许 Git 历史中保留旧路径。
8. 删除六个子智能体目录。
9. 运行文档、JSON、发布清单、后端和前端验证。
10. 生成一次性的结构迁移说明；不按已废弃规则再创建新的角色实施记录。

## 8. 验收标准

### 8.1 结构验收

- 六个子智能体一级目录全部不存在。
- 根目录只保留一个 `AGENTS.md`；产品目录如需局部规则，只能描述产品工程约束，不得重新创建角色身份。
- 六个目录中的 424 个跟踪文件不能以原文件名和原内容批量出现在新目录。
- 长期维护的压缩文档不超过十五份；机器证据和既有 `docs/superpowers/` 文件不计入该数量。

### 8.2 内容验收

- 当前产品范围、公开接口、架构、安全边界、生产门禁和未完成事项均能从 `docs/README.md` 一跳到达。
- 压缩文档不存在“继承上一版本”“参见已删除目录才能理解”等断链表达。
- TikTok v0.1 与三平台完整 MVP 的边界保持不变。
- 自动回复、营销、高风险写入和真实平台门禁不得因文档压缩被描述为已放行。

### 8.3 可追溯与机器验收

- 所有保留的机器证据都有用途、来源提交、SHA-256 和引用方。
- 发布基线、模型清单及其测试使用新路径后仍可解析并通过完整性检查。
- Git 工作树中对六个旧目录路径的非历史引用为零。
- JSON、JSONL、manifest 和 Markdown 链接检查通过。

### 8.4 产品回归

- 后端测试、前端 lint/typecheck/test/build 与清理前基线相比无新增失败。
- 结构清理不产生数据库迁移、不改变运行配置默认值、不增加产品依赖。
- 删除的项目 Skill 不属于运行依赖，依赖清单净变化为零。

## 9. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 压缩时遗漏仍有效的安全门禁 | 从 ADR、接口增量、最新测试结论和代码配置交叉核对；默认采用更严格边界 |
| 测试报告删除后无法追溯 | 保留 Git 历史、已有发布标签、机器清单和压缩后的证据标识 |
| 发布基线路径或哈希失效 | 迁移证据后同步更新路径和 SHA-256，并运行解析及完整性测试 |
| 增量架构合并后出现矛盾 | 当前代码、已接受 ADR 和最新正式测试结论依次作为事实依据 |
| 一次删除量过大难以审阅 | 提交拆成“压缩文档”“机器证据与脚本”“引用修复”“删除旧目录”四个逻辑批次 |
| 误删本地密钥或模型 | 不使用 `git clean -fdX`，不触碰 `.env`、模型权重和无关 worktree |

## 10. 回滚策略

全部变更发生在独立短期分支，不重写历史。任一阶段发现遗漏时，停止删除并从 `origin/main` 或原路径提交恢复所需文件。合并后若需整体回滚，使用 `git revert` 撤销清理提交；不使用 `git reset --hard` 或强制推送。
