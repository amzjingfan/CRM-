# G4 政策草稿校验与一次受控修复设计

日期：2026-10-13
状态：待用户审阅的设计规格
任务：`MVP-005` / G4
设计基线：`82a02453154c0069620e2005c4de0b694572f784`

## 目标和已知事实

目标是在 TikTok 人工辅助 v0.1 的模型草稿展示前，以可信证据校验政策表述；对可修复的草稿最多再生成一次，并保留首轮质量与最终质量的独立证据。坐席始终决定是否发送。G4 的冻结集、严格判分、安全开关和 85% 综合门槛不变；逐项失败仍需逐项复核。

`real-model-eval-v1.2.3` 至 `v1.2.7` 的多次获批复测显示：每轮只改 Prompt 会使不同样本交替失败。最新 staging `v1.2.7` 报告为 34/36，英文条件政策命中禁用内容，多语言政策遗漏审核概念。报告只保存哈希和低敏原因码，不能据此断言模型的具体措辞。当前评测流程取得首个结构化输出后立即用冻结标签判分；正式回复工作流已有引用、声明、DLP 和独立依据复核，但评测没有草稿修复环。两者的输出 DTO 不同，不能把评测标签或生产 DTO 直接混用。

## 方案取舍

1. **继续改 Prompt**：变更小，但五轮结果已经证明两条失败没有稳定收敛，不能给出可控的质量边界。
2. **把冻结必含/禁用词交给模型重写**：容易提高分数，却泄露答案、污染独立评测，拒绝采用。
3. **可信证据驱动的通用校验加一次受控修复（采用）**：先检查结构、证据和政策声明；只有可解释、非高危的失败才允许再调用一次模型。成本与延迟增加，需单独计量并设置硬调用上限。

## 边界和数据流

第一实施阶段只接入 G4 的离线评测入口，不改变正在服务的 FAQ/工具工作流、公开 API、前端、TikTok 发送或 production 开关。校验器作为无副作用的 Agent 内部模块设计，输入为本次可信证据摘要、目标语言、结构化草稿和策略版本；它不能读取 `expected_decision`、`expected_reason_code`、`expected_claim_subjects`、`required_term_groups`、`forbidden_terms` 或任何冻结类别答案。评测适配层从 `build_real_model_evaluation_payload` 构造更窄的白名单，仅传任务所需的消息、目标语言、证据文本/类型/引用与可信主体；不传 `sample_id`、数据集版本或故障注入标记。此模块将来接到正式回复工作流时仍须通过独立设计/验证；现有 `ReplySafetyPolicy`、`BusinessClaimPolicy` 和人工确认门禁不被取代。

```text
已验证的合成输入 + 可信证据
  → 首次结构化生成
  → 通用草稿校验（不看冻结标签）
      ├─ 通过：保留首轮草稿
      ├─ 可修复：一次受控重写 → 完整结构/证据/安全校验
      └─ 高危/证据不足/不确定：隐藏草稿并转人工
  → 首轮和最终结果分别交给原冻结评分器
  → 只落盘低敏汇总与摘要
```

校验只依据已审批 FAQ、可信工具结果或本次合成证据。它检查：输出 Schema、语言、证据 ID/店铺绑定、政策声明的主体/动作/条件/时态、正文与结构化声明的一致性，以及无证据的个案审批/退款/到账/时效保证。版本化的确定性政策规则只识别证据明确表达的前置条件或审核步骤，并比较草稿是否保留同一含义；规则不认识的表述返回“不确定”，不据此猜测或强行修复。规则匹配使用通用政策概念与作用域，不读取冻结关键词列表；具体词形及多语言覆盖由独立于冻结集的样本验证。不得以模型自评通过授予安全权限。通用校验可以保守误拦，需记录原因码并衡量合法误拦。

## 修复调用与失败关闭

只在首轮 Schema 与 DLP 有效、证据足够、且失败类型是可说明的措辞、无依据审批措辞或必要条件遗漏时修复一次。无依据措辞的首轮草稿从未展示，不会被当成安全结果；修复须删除该断言并重新通过全套门禁。修复请求只包含版本化系统指令、上述更窄的低敏输入/证据、在当前进程内短暂持有的原草稿和通用原因码；原草稿作为不可信数据分隔，不能改变系统指令。不得包含冻结标准答案、必含词、禁用词、样本分数或测试类别。模型只能返回完整的新结构化草稿，不能只返回文本补丁。修复后从头运行全部结构、DLP、引用、声明和政策安全检查；不得沿用首轮的通过标志。现有评测 DLP 只放行冻结载荷摘要；实施时须增加仅对本轮已验证合成样本生效、逐次绑定摘要和字段白名单的修复载荷授权，不能改为任意动态文本放行。

发现跨店铺引用、DLP 阻断、模型拒绝/超时、Schema 反复无效、证据冲突、无依据实例结论无法安全改写或修复后仍不安全时，终态为 `transfer_human` 且 `content=null`、`business_claims=[]`、`send_performed=false`。首轮原文和失败修复原文均不可进入 UI、日志、报告或可发送队列。故障注入的两条样本仍在本地执行，不触发额外 Provider 调用。单条真实样本最多两次 Provider 调用，因此一次 34 条 live 的硬上限为 68 次；达到调用/Token 预算后停止新调用并失败关闭，工作流不能无限重试。实际费用、调用数和总延迟必须包含修复调用；下一次真实 DeepSeek 运行需按新的最坏上限单独授权。

## 评测与证据契约

每条样本在内存中用现有 `grade_real_model_evaluation_output` 分别评首轮和最终候选。原冻结数据及其校验 SHA 不变，评分函数的必含词、禁用词和声明规则不变。低敏报告增加首轮通过/失败、最终通过/失败、是否尝试修复、修复终态、两次调用各自的 Token/耗时与合计、首轮和最终的输出哈希及稳定原因码；不落盘原文或修复 Prompt。报告 Schema、白名单、版本和旧报告兼容策略须同步更新：旧报告的修复字段缺省为“未启用”，不得回填或与新流程直接当作同口径趋势。`first_output_latency_ms` 继续表示首个通过 Schema 的输出时刻，`total_latency_ms` 包含修复与终检；另列首轮评分，不把修复后结果伪称首轮质量。

最终指标仍按原冻结评分器和 85% 门槛计算，并保留危险逃逸、合法误拦、Provider 失败、成本和延迟门禁。任何先前逐项失败必须在新报告中逐条复核；若只是通过转人工隐藏了合法样本，不能据此关闭 G4。即使最终全过，也只说明该次已锁定模型/Prompt/数据/代码组合在 staging 通过，不保证跨轮稳定性；production 放行仍依赖 G1-L、G2、G5、G6、G8 等独立门禁。

## 实施与验收顺序

1. 先用确定性 Fake Provider 测试首轮通过、可修复失败、修复成功、修复再失败、高危不可修复、拒绝/超时、故障注入、预算耗尽、禁止标签泄漏及产物脱敏。测试输入同时含政策的中英文及多语言问答，并增加不来自冻结集的独立措辞，避免仅为两条历史样本定制。
2. 将通用校验器与一次修复编排接入 G4；调整报告模型、产物白名单、评测工作流限额和相关 AI/测试/发布文档。保持现有安全默认值。行为代码经 PR、CI、审阅和本地验证后合并。
3. 后端候选镜像发布、staging 预取/validate/deploy、`prepare` 零调用、下一次 `live` DeepSeek 评测分别遵守项目的精确授权边界；前一步的通过不能替代后一步的证据。只有真实低敏报告和逐项审阅支持时才更新 G4 状态。

本规格不批准代码实施、镜像发布、staging 部署、付费模型调用或外部消息发送；这些动作按后续实施计划和项目治理门禁执行。
