# 逐条客服回复、流式审阅与物流通知

用户已确认：逐条问题逐条处理；单条多问题可分批；坐席看到生成中草稿，复核后才可发送；买家端交付也在本次实现但仅在消息审阅栏预演，不做真实买家测试；物流文字只需最新节点，文字成功后才发对应原生物流卡片；订单出现新物流节点后主动通知对应买家，不要求先订阅。

## 本次完成标准

- 每次运行绑定原始买家消息，正在审阅的答复不能被后续消息或过期流覆盖。单问题直接短答，多项独立问题由模型输出有序文本段，不按正则拆题。
- 原生模型真正流式返回，坐席审阅栏显示生成中的文本段；模型工具参数、推理字段和未授权资料不显示。生成中不能使用、翻译或发送；复核成功后由最终纯文本段替换，失败清空未复核草稿并显示具体可读原因。保留店铺隔离、取消、原绝对deadline和真实用量。
- 普通物流问答默认只输出最新节点、时间和必要订单定位信息，不在正文堆完整轨迹。卡片保存对应授权订单/包裹引用，复用现有TrackingCard及原生发送实现。文本与卡片可以在审阅栏并列预览，顺序固定为文字后卡片。
- 交付按不可变计划逐项执行。文字失败或结果未知时不发卡片；卡片失败重试不能重发已成功文字；幂等、部分成功、unknown与恢复可观察。坐席一次审阅确认覆盖准确的有序文字/卡片计划，不伪造人工确认。
- 买家端根据实际平台能力交付完整可理解、已复核短段。当前已验证TikTok发送契约为202606整条TEXT/LOGISTICS_CARD POST，未验证同一气泡逐字追加；使用逐段消息交付，不能把SSE或拆字符模拟称为TikTok原生token流。当前仅审阅栏模拟，不真实外发。
- 物流更新工具列入Agent工具分类，使用@tool和明确参数说明；工具绑定不能绕过发送授权。店铺启用的物流更新策略识别新节点→去重→生成买家语言最新状态通知→复核→有序交付。首次接管旧订单只建基线，避免批量补发历史；同节点不重复，乱序旧节点不通知，多个新节点合并为最新情况。
- 通知复用现有jobs/模块化单体，无新增服务或事件总线。全局开关及店铺策略默认关闭。没有授权会话、买家/店铺核验失败、发送窗口或scope不满足时不发送。结果不确定先对账，不盲重试。真实启用仍需明确批准；本次所有外发测试使用本地替身。

## 已确认的平台资料

官方[Send Message](https://partner.tiktokshop.com/docv2/page/send-message)当前为202606，TEXT最多2000字符，支持LOGISTICS_CARD；既有项目使用同一路径。随包技能OAS仍以202309为基线，存在覆盖缺口，不据此降级接口。

官方[增强物流说明](https://partner.tiktokshop.com/docv2/page/8syhoy40)描述202604跨境轨迹与抓取频率要求，并把Tracking webhook列为路线图，不能把路线图当作已开放事件。首期接收已有订单/物流同步中的已验证观察；补偿拉取遵守来源适用频率，不实现未经确认的高频增强物流轮询，不声称carrier更新即刻必达。

## 范围边界

本轮开发与验证不向真实买家发送，不启用公开自动回复、不修改生产或全局自动回复开关。实现通知和分段交付代码不等于开启自动发送。外部卖家/买家资料只在已授权测试范围使用；其余本地测试均合成数据。
