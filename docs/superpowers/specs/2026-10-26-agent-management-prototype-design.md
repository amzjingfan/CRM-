# Agent 管理原型落地设计

## 目标与依据

按用户提供的 `Agent管理-CRM交互原型-v3.html` 实现 Agent 管理页：店铺切换、横向 Agent 卡片、基础设置、模型与提示词、工具能力、知识库文件绑定、脱敏运行记录、新建 Agent 和预览调试。保持 CRM 六项主导航及既有店铺权限边界。

## 已确认边界

- 用户指定绑定知识库模块**导入的文件**，不是 FAQ，并追加要求文件检索真实进入 Agent RAG。绑定关系按 Agent 和店铺持久保存；文件必须属于该店铺且未归档、未删除。绑定非空时只检索这些文件的当前有效、已就绪且经人工批准供内部复核的版本；无绑定时沿用既有 FAQ 检索。
- 文件解析复核与用于 Agent 的内容审批是两个独立门禁。新增版本级内部审批与审计；替换版本必须重新审批。未审批、解析待复核、归档、删除、非当前版本和跨店文件均不得进入检索。
- Agent 调用 RAG 的 Embedding、数据库 Dense/词法召回、候选融合和 Rerank 共用单次可配置总超时；超时记录固定错误码并失败关闭，不继续生成无来源答复。
- 新建与编辑的名称、用途、服务/经营类型、工具白名单、受控回复画像及文件绑定走现有 Agent 管理 API。经营类仅保留内部配置，不可启用客服运行。
- 模型和版本化系统 Prompt 由服务端发布配置控制。页面展示真实运行模型与只读策略摘要；原型中的模型切换仅在当前页面模拟选择，不写入服务端。
- 原型自动发送开关和预览只模拟页面交互；不调用模型，不发送 TikTok 消息，不写入运行日志。真实发送仍走现有人工确认链路。
- 运行记录来自现有脱敏日志 API，仅展示授权店铺/Agent 的记录，不显示正文或完整 Prompt。

## 方案选择

现有 `agent_configs.knowledge_scope` 已承载受控回复画像，因此在该 JSON 中增加 `agent_type` 与 `file_ids`，通过强类型请求字段及店铺范围查询校验，避免仅为绑定增加迁移。文件版本增加审批字段及向量/词法索引迁移；文件检索端口返回与现有 FAQ 检索兼容的安全引用，并在工作流沿用结构化生成和独立安全复核。前端用独立样式作用域复用原型布局，所有可保存项回读 API 结果。未采用独立文件绑定表（当前无文件级关联查询）；未将原型 JavaScript 的静态店铺和示例数据接入正式页。

## 验收

1. 两个店铺的 Agent、文件和日志切换后不串数据；迟到响应不能覆盖当前店铺。
2. 创建默认停用，重复编码反馈明确；配置保存、状态切换、工具与文件绑定刷新后仍在。经营类不能启用客服运行。
3. 绑定拒绝跨店铺、归档、已删除或不存在的文件；未审批文件可绑定但不能被检索。版本批准后同店 Agent 能引用其分块；替换、归档、删除或撤销审批立即停止使用该版本。
4. 原型五个页签、弹窗和预览交互可用；预览无网络模型/平台调用。模型/Prompt/自动发送不产生后端运行配置变化。
5. Embedding、SQL 检索或 Rerank 任一阶段超出总预算时形成脱敏失败终态，不调用后续生成；无绑定的 FAQ 路径不回退。
6. 前后端类型、契约、浏览器交互及受影响后端测试通过；现有知识库和 Agent 流程不回退。
