# K1 跨境电商知识来源与范围治理 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to execute this plan task-by-task, only when the execution context permits delegation. This plan itself does not authorize execution. All tasks use checkboxes for tracking; formal review/approval remains with the named human owner.

**Goal:** 建立可审计的八领域知识覆盖目录、来源和使用权登记、首批 TK 市场/来源名单与准入清单，使后续 K2/K3 只能消费有明确来源与有效审批的内容。

**Architecture:** 治理文档留在项目共享记忆作为服务建设元数据，绝不把这些项目内部文档送入知识库语料。内容单元以“领域 × 平台 × 市场 × 语言 × 读者 × 空间 × 店铺范围”标识，`company_shared` 的店铺范围为空，`shop_private` 必须绑定稳定店铺代号；来源和内容版本分开登记；覆盖状态从证据推导，不靠栏目存在推断。高风险及冲突均需人工结论。

**Tech Stack:** Markdown 文档、Git 审阅、PowerShell 只读检查；不新增产品依赖、模型、数据库或网络采集。

**Spec:** `架构师/ARCH-001-KB-公司级跨境电商知识服务设计-v1.0.md` 第 1、4、6、7 节；总路线 `docs/superpowers/plans/2026-09-14-cross-border-knowledge-service-roadmap.md`。

## Global Constraints

- 本计划只产生治理规则、元数据清单与评审证据；不导入真实内容、抓取网页、连 TK 店铺、编写产品代码或开启检索。
- 不把本项目 PRD、代码、接口、实施记录、测试材料、日志、内部聊天或凭证列为候选知识来源。
- 未有明确合法使用依据的第三方内容不得登记为“可发布”；平台页面只保存必要的元数据、链接和合规快照方案，不在 Git 大段复制正文。
- 不写真实店铺 Token、客户订单、地址、客户对话正文、原始内部报告或模型权重；店铺只用低敏内部代号。
- 覆盖状态固定为 `资料待获取`、`待审批`、`已生效`、`已过期`、`不适用`；只有有效来源、许可、当前版本审批和 QA 评测均满足时才可标 `已生效`。
- 用户于 2026-09-14 指定首批 TK 市场为 US；仍须由产品/平台负责人核对现有授权店铺与 US 的关系、实际 Scope 和可同步数据类型，不得凭预期 Scope 填值。
- 用户指定架构师Agent统筹来源与内容治理；涉及平台协议、税务、法律和高风险业务事实时仍须相应有权人员出具结论，架构统筹不自动授予内容复制或跨系统使用权。
- 每项变更在 `docs/*` 短期分支执行；提交前 `git diff --check`，经 PR、评审和文档索引同步，不直接改 main。

**Interfaces:** 产出 K2/K3 需要的元数据字段和准入判定；不修改现有接口文档或生产 schema。

- [ ] **Step 1: 确认源材料和基线**。在隔离分支运行 `git status --short --branch`，读取上述设计与 ADR、当前 PRD/接口/任务/团队职责；如对知识审批语义有冲突，交架构师处理后再继续。
- [ ] **Step 2: 写治理模型**。规定 `coverage_cell_id` 由领域、平台、市场、语言、读者、空间、条件性店铺范围组成；`shop_private` 必须有稳定店铺代号，`company_shared` 的该维度为空。`source_id` 单独指向发布主体、来源 URL/受控对象键、来源类别、使用权依据、抓取/收到时间与原文更新时间；`content_version_id` 记录内容哈希、适用起止、风险、审核人/时间、当前状态和复核日期。字段说明必须标清必填/可空、权威位置、低敏日志限制。
- [ ] **Step 3: 写准入判定表**。明确“来源许可不足、适用市场未知、授权已失效、内容未逐版本批准、冲突未解决、高风险未复核、向量索引未就绪”各自不能成为 `已生效` 的原因；A/B/C/D 是内容形态而非权限豁免。撤销以权威状态立即生效，索引清理异步进行。
- [ ] **Step 4: 检查结构与差异**。运行 `Test-Path -LiteralPath '架构师/DATA-001-KB-公司级知识来源与覆盖治理-v1.0.md'` 与 `git diff --check`；前者必须为 `True`，后者退出 0。人工逐项核对所有元数据字段、项目文档排除规则和 ADR-005 不降级。
- [ ] **Step 5: 提交治理模型**。只暂存此文档，提交 `docs: define cross-border knowledge source governance`；若正式评审未通过，状态写“评审中”而不写“已确认”。

### Task 2: 建立八领域覆盖矩阵与责任人

**Files:**
- Create: `共享记忆文档/公司级跨境电商知识覆盖矩阵.md`
- Read: `共享记忆文档/项目团队职责说明.md`
- Read: `共享记忆文档/智能客服平台 — 产品需求文档（PRD）V2.0.md`

**Interfaces:** K1 覆盖单元清单供 K3 评测和管理面状态使用；本文件是项目治理台账，不属于 RAG 语料。

- [ ] **Step 1: 建立固定一级领域**。逐行列出平台开店与运营、商品与选品、定价促销与营销、支付风控与订单、仓储物流与清关、售后退换与争议、客服沟通与服务流程、市场税务与合规，共八项；每项至少有一条 `资料待获取` 或 `不适用` 现状，不允许空分类被标为覆盖。
- [ ] **Step 2: 加入单元列**。每行包含 `coverage_cell_id`、领域、平台、市场、语言、读者、空间、条件性店铺范围、A/B/C/D 内容形态、状态、来源引用、内容负责人、风险级别、复核到期日、评测集引用和未覆盖原因。首批市场写 `US（用户指定；授权关系待核验）` 并保持 `资料待获取` 或 `待审批`，不得写成通用有效规则。
- [ ] **Step 3: 明确覆盖判定**。矩阵首页说明：目录广度与实际资料覆盖率分开统计；无来源或无批准时有效覆盖数为 0；店铺私有单元不能转成公司共享覆盖；不同市场/语言不得互相冒充。按八领域及高风险分组汇总待获取数和已生效数。
- [ ] **Step 4: 逐项检查**。运行 `Select-String -LiteralPath '共享记忆文档/公司级跨境电商知识覆盖矩阵.md' -Pattern '平台开店与运营','商品与选品','定价促销与营销','支付风控与订单','仓储物流与清关','售后退换与争议','客服沟通与服务流程','市场税务与合规'`；应出现八个领域。人工核对每行的负责人/复核日期和“已生效”证据链；再运行 `git diff --check`。
- [ ] **Step 5: 提交矩阵**。只暂存矩阵，提交 `docs: establish cross-border knowledge coverage matrix`。

### Task 3: 登记首批 TK 市场与合法来源

**Files:**
- Create: `共享记忆文档/公司级知识来源登记与许可清单.md`
- Modify: `共享记忆文档/公司级跨境电商知识覆盖矩阵.md`

**Interfaces:** 产品负责人确认首批市场/读者/真实业务问题；平台负责人提供已获授权数据范围；内容负责人提供可验证来源和许可；QA 只使用已批准内容制定评测样本。

- [ ] **Step 1: 获取书面选择**。记录用户指定的 US 首批市场、物流/履约、退换退款、商品信息/规格三个试点场景及架构师Agent治理统筹；由产品负责人核对市场确属现有目标店铺，并确认具体问题、目标读者和高风险领域专业复核人。若实际店铺授权关系或使用权结论无法确认，保留 K1 `部分完成`，不要自拟同步范围。
- [ ] **Step 2: 建来源清单**。对每个候选来源记录 `source_id`、发布主体、官方/商家授权/人工维护类别、精确 URL 或受控对象标识、平台、市场、语言、版本/更新时间、适用生效区间、使用许可或授权凭据的位置、可内部检索/可引用的限制、内容负责人、复核日和当前状态。凭据正文仅留在获批系统，不进 Git。
- [ ] **Step 3: 做权利与风险审查**。逐个确认官方条款或授权范围、是否允许保存快照与内部片段引用；政策、税务、法律、支付和承诺类来源标高风险。未知权利一律 `待审批`，被拒绝或禁止再分发的来源不发布、不复制正文。登记来源冲突关系及人工处置人。
- [ ] **Step 4: 映射到矩阵**。首批三个业务场景分别指向来源与覆盖单元；当缺少版本批准或独立评测时状态仍为 `待审批`，不可提前改为 `已生效`。平台中立的通用知识单元与 TK 官方规则分开记。
- [ ] **Step 5: 审阅与提交**。产品、平台/内容负责人签署首批市场和每条来源的使用结论；运行 `git diff --check`，只提交脱敏登记与矩阵变化，提交 `docs: register authorized initial knowledge sources`。若缺任一签署，保留未完成状态及具体待办，不声称 K1 出口通过。

- Modify: `架构师/DATA-001-KB-公司级知识来源与覆盖治理-v1.0.md`

**Interfaces:** 对 K2 的权威查询过滤和 K3 的异常状态给出可测试规则；不对买家生成法律/税务结论。

- [ ] **Step 1: 写状态迁移矩阵**。分别列 `draft → reviewed → published/pending → ready`、版本更改、授权撤销、来源过期、索引失败、来源冲突；每个事件说明操作人、权威状态、是否允许检索、审计事件和恢复条件。
- [ ] **Step 2: 写冲突处理**。已登记相反规则时不得靠向量分数选赢家；标记受影响市场与版本，暂停发布或返回 `conflict`，交内容负责人裁定。说明系统不承诺自动发现所有语义矛盾，并提供人工补录路径。
- [ ] **Step 3: 写高风险复核规则**。明确政策/税务/法律/风控类最短复核周期由内容负责人按来源更新频率批准，不能写一个无依据的全域固定期限；到期未复核即不再作为正式证据返回。
- [ ] **Step 4: 核对旧安全约束**。核对 ADR-005 的 `approved_for_internal_review`、`automatic_delivery_allowed=false` 与本状态模型没有冲突；如需新的“可公开自动回复”语义，只记未来 ADR/测试需求，本阶段不启用。
- [ ] **Step 5: 运行 `git diff --check`，人工检查各异常是否有拒绝/人工处理出口；提交 `docs: define knowledge expiry and conflict controls`。**

## K1 完成判定与下一步

“八领域目录已建”与“八领域资料已上线”是不同结论。K1 通过只说明范围、首批来源权利和治理门禁可追溯；实际内容进入正式检索还需要 K2/K3 实施、逐版本审批和 QA 评测。若首批 TK 市场或合法来源未定，仍可交付治理模型和空白矩阵，但 K1 状态必须是 `部分完成`，K3/K4 不得用虚构内容代替真实联调。

KB-G0 ADR 一经批准，架构师按 [总路线](2026-09-14-cross-border-knowledge-service-roadmap.md) 形成独立 K2 代码级计划；K3 等首批合法样本，K4 等真实 TK Scope，K5 等第二系统被正式选定。任何计划执行前重新读取 `共享记忆文档/` 和 `共享记忆文档/代码编写手册.md`，并在受控分支上先写失败测试再实现产品代码。
