# 公司级跨境电商知识服务实施路线

> 状态：计划草案；2026-09-14。用户已确认 `架构师/ARCH-001-KB-公司级跨境电商知识服务设计-v1.0.md` 的方向，但项目级架构评审、ADR、首批市场、资料权利和正式任务编号尚未完成。本文件是 K1～K5 的总路线，不授权编码、真实店铺同步或生产放行。每个软件子项目必须另有可逐项执行的详细计划。

## 1. 目标与交付边界

建设公司内部多个系统共用的跨境电商知识服务，领域目录覆盖平台运营、商品、定价营销、订单支付、仓储物流、售后争议、客服流程、税务合规八类。首个真实平台接入为 TikTok Shop（TK）；CRM 是首个消费系统，第二个实际内部系统用于验证跨系统复用。知识服务只返回受权、有效、可追溯的证据；回答生成、业务动作和对买家发送由消费系统负责。

项目 PRD、代码、接口、测试、日志和实施记录只作为建设依据，不作为知识语料。客户当前订单、物流、退款等实例事实走可信业务 API，不从 RAG 历史文档推断。公司共享知识和店铺私有知识分开授权；旧 CRM FAQ 链路在对照验证前不下线。v0.1 对外仍只有 TK 人工辅助，绝不因知识获批推导出自动发给买家的权限。

当前实现有 CRM 外键绑定的 `knowledge_documents` / `knowledge_chunks`，且 BGE 的 `0.52` Dense 门禁只在 FAQ 集上校准。K2 不得把公司共享知识塞入伪店铺；K3 不得直接沿用该分数为全领域放行阈值。沿用 PostgreSQL/pgvector、MinIO、本地 BGE-M3 与 bge-reranker-large 作为基线，新增 Docling 等组件均需独立许可、资源和格式评测后决定。

G0 与 K1 的资料梳理可并行；K2 编码必须等 G0；K3 可在 K2 契约冻结后分批推进，但正式内容发布要等 K1 来源批准；K4 真店铺联调要等 K2/K3 安全与质量门禁；K5 可在 K2/K3 契约稳定后与 K4 并行，但只有实际第二系统验收通过才算“多系统共用已验证”。

## 3. K2～K5 的工作项与验收切片

以下编号是本路线的工作项，不是已分配的项目任务编号。各项实施前仍需独立的代码级计划与失败先行测试，不能直接凭本表动手修改生产系统。

| 工作项 | 主责 | 可验收交付 | 最低验证证据 |
| --- | --- | --- | --- |
| K2-01 身份与数据契约 | 架构师、全栈 | ADR 固定服务身份、空间/店铺授权判定、数据所有权、内部 API DTO 与错误码 | 产品/架构/安全评审签署；非法请求不能凭正文 `shop_id` 提权 |
| K2-02 独立服务与模型 | 全栈 | 可独立启动的知识服务、专属表/迁移与备份边界；版本、审批、审计、当前权威状态 | 新服务不引用 CRM `stores/users` 外键；迁移升降级与逐版本审批测试通过 |
| K2-03 检索证据 API | 全栈、AI | 受控 `POST /internal/v1/knowledge/search` 只返回证据与四态，不负责生成和业务动作 | 认证、授权、跨店、撤销、过期、损坏元数据、服务不可用均有负向契约测试 |
| K2-04 旧 FAQ 兼容 | 全栈、AI | CRM 适配器、可关闭的新检索路径、旧 FAQ 映射和影子/双读对照 | 旧链路不下线；店铺隔离、审批和建议语义逐项回归并演练回滚 |
| K3-01 格式和解析基准 | 全栈、AI | 用 K1 批准的真实样本比较纯文本/表格/PDF/Office 的解析保真、成本与风险 | 样本权利、表格字段、页码、版本与 OCR 需求有报告；新增解析依赖经许可/安全/显存审查 |
| K3-02 受控采集与管理 | 全栈 | 上传、官方/授权页面快照与待审队列、来源和版本差异、撤销与同步失败状态 | 未授权来源只到草稿；去重、脱敏、幂等、超限、恶意文件和失败恢复测试通过 |
| K3-03 索引与检索 | AI | BGE-M3 切片与索引 Worker、pgvector/词法混合召回、RRF、重排、引用和冲突状态 | 只索引获批当前版本；内容哈希幂等、权威再过滤、模型故障失败关闭测试通过 |
| K3-04 独立评测 | 测试工程师，AI 配合 | 分领域/平台/市场/语言冻结评测集、负样本、阈值与目标负载报告 | Recall@5、排序、无答案拒判、引用合法率、越权零命中和目标 GPU 延迟均达签署门槛 |
| K4-01 TK 能力核验 | 全栈、产品 | 真实店铺、市场、获批 Scope、官方 API 版本/限流和可用数据类型清单 | 授权和官方契约的低敏证据；未获权限的能力明确标“不支持” |
| K4-02 TK 静态资料同步 | 全栈 | 只同步 Scope 内商品/店铺规则等适合知识库的静态资料；游标、幂等、撤销与授权失效处理 | 真实店铺有限样本对账、重放、限流、跨店负样本和撤权后不可检索 |
| K4-03 CRM 人工建议 | AI、全栈 | CRM 可信上下文调用证据 API，建议附来源/版本并保持人工确认 | 无证据、冲突、失败均转人工；`automatic_delivery_allowed=false` 在端到端链路可见 |
| K4-04 实店验收 | 测试工程师 | 真实授权、检索、建议和人工审核的独立报告 | 仅核准功能灰度；生产 G0～G8 及发布开关另行通过 |
| K5-01 第二系统选定 | 产品、架构师 | 实际系统名称、负责人、使用场景、身份方式、允许空间和店铺范围 | 真实负责人签署，不以模拟客户端充数 |
| K5-02 独立消费与审计 | 第二系统负责人 | 通过知识 API 的适配器与可追踪审计；无 CRM 数据表或 JWT 假身份依赖 | 正常检索、拒绝、失效、故障转人工/待核实和跨系统审计测试 |
| K5-03 复用验收 | 测试工程师 | 第二系统的正式端到端报告与运行交接 | 两个消费系统在各自权限内取得证据，跨系统和跨店隔离零越权；再声明“多系统已验证” |

## 4. 软件子项目的详细计划写入时点

本设计跨数据治理、服务底座、RAG、平台同步和消费系统五个不同责任域。避免用一份预设接口或虚构 TK Scope 的巨型清单指导编码，后四个软件子项目分别形成详细计划，且每份都要列确切文件、接口 DTO、失败先行测试、执行命令、回滚和提交粒度：

1. **K2 计划**：G0 ADR 固定应用身份、空间授权、数据所有权、服务部署和内部 API DTO 后编写；包含新服务 schema/迁移、权限、版本与审计、证据接口、兼容适配器及双链路回归。按 `共享记忆文档/代码编写手册.md` 和 TDD 实施。
2. **K3 计划**：K1 样本格式、权利和首批市场确定，K2 数据/接口契约稳定后编写；分别覆盖解析/索引和检索评测，不把候选开源平台作为默认运行依赖。
3. **K4 计划**：确认实际 TK 店铺、地区、获批 Scope 与官方 API 契约后编写；只规划已获权限的数据类型，包含限流、游标、幂等、撤销、失败重试、脱敏证据和 CRM 人工建议。
4. **K5 计划**：第二个实际内部系统及其负责人、身份机制、可访问知识空间确定后编写；禁止以 Mock 第二客户端代替真实复用验收。

每个计划在本仓库 `docs/superpowers/plans/` 单独落档，实施前重读共享记忆文档与代码手册；任务编号由项目管理分配后同步 `共享记忆文档/开发任务拆解（按人天分配）.md`。目前仅 K1 已有可逐项执行的详细计划，K2～K5 上述条目是阶段路线，不代表代码级计划或实施完成。

## 5. 横向验收与发布策略

- **安全**：测试矩阵至少覆盖未授权应用、跨店铺、草稿、审批撤销、过期、版本漂移、损坏元数据、权限服务不可用。前六类不得返回证据；不可判定权限或模型/索引故障必须失败关闭。权威版本判断发生在查询时，不能只信向量切片副本。
- **内容**：每个生效内容单元保留来源、许可、平台/市场/语言/店铺、时间、哈希、审批和责任人；高风险政策和来源冲突返回待人工确认，不由检索分数裁决。八领域目录可以先建立，但“已覆盖”只能用于有真实有效资料且通过评测的单元。
- **质量**：测试工程师按领域、平台、市场、语言冻结有答案/无答案和冲突样本，分别报告 Recall@5、排序、拒答与引用合法率；阈值由真实语料报告校准后写入配置，不复制现有 FAQ 的 `0.52`。
- **性能**：在目标 Compose/GPU、真实文档规模及授权并发下分别测检索与 CRM 建议端到端延迟、显存和失败恢复；现有 8 GB GPU 的 FAQ 报告不作为新服务容量证明。
- **切流与回滚**：先影子/双读对照，再小范围内部灰度，后按批准的消费系统切流；每一步有关闭新检索的开关与旧 FAQ 保持可用的演练。旧数据只迁移合格版本，未经许可或审批者不自动转正式可检索。
- **发布**：遵循现有 G0～G8、ADR-005 与 ADR-006；任何内容通过审核均不提升 CRM 的自动发送权限。正式测试结论放 `测试工程师/`，共享记忆仅索引和项目级状态。

## 6. 近期执行顺序与风险

第一步执行 K1 详细计划，同时安排 G0 正式架构评审；随后编写并评审 K2 代码级计划，接着分批做 K3，满足质量门禁后接 K4；第二个系统明确后推进 K5。首批 TK 市场、来源许可、真实店铺 Scope、第二系统名称与性能目标尚非已确认事实，不能在代码或验收材料中自行补值。若产品选定的市场资料受限，K1 保持明确的“未覆盖”状态，K2 可仅做不含真实语料的底座验证，K3/K4 正式放行暂停。

本路线是增量项目，不替代原 CRM MVP 排期、现有 FAQ 安全链路或生产门禁。人天与日期须在 K1 样本规模、ADR 和 TK 授权证据确定后由项目负责人重估，不以未经验证的时间表作承诺。
