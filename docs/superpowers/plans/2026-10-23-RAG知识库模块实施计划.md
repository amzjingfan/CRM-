# RAG知识库模块实施计划 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在现有 CRM 知识库完成通用文件上传、MinerU 本地解析、清洗、真实分块、BGE-M3 向量化与 PostgreSQL `pgvector` 入库，并在 UI 中处理整版本待复核和显式替换。

**Architecture:** 保留现有 FAQ 表、导入 Worker 和 Agent 检索契约；为通用文件建立独立的版本、单元和向量表。FastAPI 受理与审核，私有 MinIO 保存源文件，独立 MinerU Worker 完成解析/清洗，复用内部 BGE Embeddings 服务；只有全部单元可靠或修订后才整版本写入向量并切换有效版本。

**Tech Stack:** Python 3.11、FastAPI、SQLAlchemy/Alembic、MinerU 4.x、MinIO、PostgreSQL 16 + pgvector、BGE-M3、Next.js/TypeScript、Docker Compose。

**Spec:** `docs/superpowers/specs/2026-10-23-rag-document-ingestion-design.md`

## Global Constraints

- **纠正后的决策优先：**任何关键内容识别不可靠，整个新版本 `review_required`，该版本向量数为 0；不得先把合格页入库。
- 当前有效旧版本在替换版本 `ready` 前保持；新版本的向量写入和 `active_version` 切换在同一数据库事务完成。
- 不接入 Agent 检索/Rerank，不改变既有 FAQ 800/80、审批与 `knowledge_chunks`；前端检索参数明确标注本期不生效。
- 店铺授权、`knowledge.manage/view`、CSRF、幂等、审计、DLP 和失败关闭不放宽；文件正文不进入日志或发布证据。
- 新文件 20 MiB、PDF 最多 100 页、图片最多 25 MP、解析超时 10 分钟、最多 2000 chunks；超限给稳定错误码。数值是本期入口资源上限，可由配置收紧，不能由客户端提高。
- 解析器精确锁定 MinerU 4.x 已验证版本与镜像摘要；默认 CPU 优先、单并发。模型服务无 CUDA 时启动选 CPU，运行中故障经失败状态、受控重启和重试恢复。
- 测试源码/fixture 只在 `src/tests/`，普通测试输出只在 `src/tests/.artifacts/`；不提交真实文件、凭据或模型权重。
- 只手动直接部署 **staging**，不调用 GitHub Actions；production 和 Agent 检索保持关闭。验收百分比是诊断指标，硬门禁是关键事实正确或待复核，不能将失败试验改写成通过。

## Review Focus

1. 同店同名不同内容但未选择替换：拒绝冲突，不新建暗中覆盖的版本（Task 2/7 的 API 与浏览器测试）。
2. 一个 PDF 页 OCR 不可靠：整版本待复核且 0 新向量，旧版本不变（Task 4/6 的集成测试）。
3. 审核最后一页时并发重试：只有一个 Worker 认领与一个版本切换，无重复向量（Task 6/7 的并发测试）。
4. XLSX/PDF 表格中金额、SKU、否定词：清洗和表格行组不丢列头或改写事实（Task 4/5 的样本测试）。
5. GPU 在运行中不可用：任务留可重试状态，CPU 重启后从同一快照完成，不伪造 ready（Task 6/9 的故障演练）。
