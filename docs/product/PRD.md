## **1\.2 项目背景**

随着跨境电商业务规模扩大，客户服务已从单一的「售后应答」演进为涵盖售前咨询、主动营销、数据洞察与多渠道获客的综合运营体系。当前团队已具备基础 AI 客服能力（知识库报价查询、用户识别、订单跳转、敏感内容过滤、人工审核通道），但在智能体架构、行业专属问答、主动触达、WhatsApp 接入成本等方面仍存在明显短板。

本项目旨在借鉴多客（Duoke）的 Multi\-Agent 智能架构与自进化能力，以及乐聊（ChatPlusAI）的官方 API 直连与合规稳定性，打造一套具备行业专属智能、主动运营触达、多渠道获客与低成本消息通道的 CRM 智能聊天系统。同时构建面向电商零售行业的 AI Agent 多智能体协同平台，为 Amazon、TikTok 等主流电商平台提供全链路智能导购服务。

## **1\.3 项目目标**

- 借鉴多客 Multi\-Agent 架构，构建服务/经营/增长三类 Agent 协同体系

- 借鉴乐聊官方 API 直连与风控机制，确保消息到达率与合规性

- 实现行业专属智能问答，意图识别准确率 ≥95%

- 建立主动运营触达体系，降低差评率、提升复购率

- 攻关 WhatsApp 低成本接入方案，消息成本降低 90\-95%

- 构建 AI Agent 多智能体协同平台，日均处理 3 万\+ 对话，服务 5000\+ 日活用户

- 完成从 LangGraph 单体编排到 A2A 协议分布式微服务 Agent 集群的架构演进

# **4\. 新增核心功能需求**

## **4\.1 对外客服：精准行业问答**

需求描述：当前通用大模型在回答物流、报价等行业问题时，存在泛化输出、缺乏专业深度的问题。需要构建行业专属知识库与精调模型，让 AI 回复具备专业深度和行业准确性。

**功能规格：**

- 物流问答模块：对接主流物流商 API，实时查询运费、时效、禁运品类目，生成精准报价

- 报价引擎：基于产品 SKU、重量、目的地、运输方式等多维度自动计算报价

- 知识库分层：按 A层（原始数据）/B层（业务规则）/C层（决策逻辑）/D层（案例库）四层组织

- 意图识别优化：采用 RAG \+ 微调结合，目标意图识别准确率 ≥95%

- 答复质量护栏：置信度低于阈值时自动转人工，禁止编造信息

- 多语言支持：支持 130\+ 语种实时互译，覆盖东南亚、拉美主流语种

## **4\.2 对内数据解析：结构化信息提取**

需求描述：客户在聊天过程中会自然提供手机号、地址、邮编等信息。需要 AI 自动识别并提取这些结构化数据，写入 CRM 客户档案，减少人工录入。

**功能规格：**

- 实体提取引擎：自动识别手机号、地址、邮编、邮箱、公司名称等结构化字段

- 多语言支持：支持中英日韩及东南亚语种的地址解析

- 数据写入：提取结果自动写入 CRM 客户档案，支持人工确认/修正

- 去重与合并：基于手机号/邮箱生成去重指纹，重复客户自动合并

- 数据脱敏：敏感信息在日志和展示层自动脱敏处理

## **4\.3 主动运营触达**

需求描述：借鉴多客增长 Agent 的主动营销理念和乐聊的 5 分钟黄金窗口挖回机制，构建覆盖全客户生命周期的主动触达体系。

|**触达场景**|**触发条件**|**动作**|**时效要求**|

|好评催发|签收后 24h|自动发送邀评邮件|延迟 24h|
|弃单挖回|取消/退款申请|5分钟内自动触发挖回话术|≤5分钟|
|中差评挖回|中差评出现|5分钟内自动触发挖回流程|≤5分钟|

|定时关怀|定时任务触发|定时邮件推送|定时|

# **5\. WhatsApp 接入成本优化**

WhatsApp 官方 Business API 按消息计费，单价约 0\.01 美元/条。当日均消息量达到万级时，月度消息成本可达 3000 美元以上。

|**技术方案**|**原理**|**优势**|**风险**|
|---|---|---|---|
|浏览器插件|在 WhatsApp Web 页面注入自动化脚本|开发快、成本低|依赖页面结构，升级后可能失效|
|窗口代理|用 Puppeteer/Playwright 控制浏览器窗口|可控性强、支持多窗口|资源消耗较高|
|协议层方案|直接对接 Web 协议（如 Baileys 库）|最轻量、性能最优|协议变更风险、封号风险|
|**难点**|**描述**|**拟解决方案**||
|多窗口上下文记忆|多个客户会话并行时保持独立上下文|每个窗口绑定独立 Session，Redis 缓存对话历史||
|用户 ID 匹配|将 WhatsApp 联系人与 CRM 客户档案关联|基于手机号建立映射表，支持手动绑定||
|消息实时同步|确保消息不丢失、不重复|WebSocket 监听 \+ 消息去重队列||
|网页 OCR 信息提取|从页面元素中提取结构化信息|DOM 解析优先，图片内容降级用 OCR||
|封号风险控制|避免触发 WhatsApp 反作弊检测|消息频率控制、人类行为模拟、多账号轮转||

|---|---|---|

|集成层|外部系统对接|平台 API、WhatsApp、TikTok、飞书、BI|
|数据层|存储与缓存|PostgreSQL、Redis、MinIO|

## **7\.2 智能体架构设计**

|**Agent 类型**|**职责**|**典型场景**|
|---|---|---|
|服务 Agent|客户服务与售后处理|物流查询、报价回复、问题诊断、转人工|
|经营 Agent|风险预警与数据分析|异常检测、绩效统计、经营参谋|
|增长 Agent|主动营销与转化推动|催付、挖回、好评催发、潜客跟进|

三类 Agent 通过统一的消息总线协同工作。服务 Agent 在接待过程中发现营销机会时，自动触发增长 Agent 介入；经营 Agent 持续监控全局指标，发现异常时向服务/增长 Agent 发出调整指令。

# **8\. 电商 AI Agent 多智能体协同平台**

本章定义面向电商零售行业的 AI Agent 多智能体协同平台，为 Amazon、TikTok 等主流电商平台提供全链路智能导购服务。系统支持流式交互、多轮对话记忆，日均处理用户对话 3 万\+，服务覆盖 5000\+ 日活用户。

## **8\.1 平台定位与业务目标**

平台定位为电商零售行业的智能导购中枢，通过多智能体协同实现从「用户进入」到「完成购买」再到「售后服务」的全链路自动化。区别于传统客服系统的被动应答模式，本平台强调主动导购、个性化推荐与跨 Agent 协同决策能力。

|**目标维度**|**量化指标**|**说明**|
|---|---|---|
|对话处理能力|日均 30,000\+ 对话|支持高并发流式交互，P99 延迟 \< 3 秒|
|用户覆盖|5,000\+ 日活用户|覆盖 Amazon、TikTok 等多平台用户群|
|导购转化率|≥15%|从咨询到下单的整体转化率|
|售后自助率|≥70%|AI 独立解决售后问题的比例|
|用户满意度|≥4\.5/5\.0|对话结束后用户评分|
|复购引导率|≥20%|通过主动推荐促成二次购买的比例|

## **8\.2 全链路智能导购服务**

**8\.2\.1 商品推荐 Agent**

负责基于用户画像、浏览行为和历史购买数据，主动推荐匹配商品。核心能力包括：

- 用户画像构建：整合平台订单数据、浏览轨迹、搜索关键词，构建 360 度用户画像

- 协同过滤推荐：基于相似用户购买行为进行商品推荐

- 场景化推荐：根据用户当前对话上下文进行场景化推荐

- 库存与价格联动：实时关联商品库存状态和价格变动

- 多平台商品池：统一管理 Amazon、TikTok 等多平台的商品目录与 SKU 映射

**8\.2\.2 售前咨询 Agent**

负责处理用户购买前的产品咨询、规格对比、使用场景解答等问题。核心能力包括：

- 产品知识库问答：基于商品详情页、用户评价、FAQ 等构建产品知识库

- 多轮对比分析：支持用户多轮追问，自动生成对比表格

- 尺码/规格推荐：基于用户提供的数据或使用场景，推荐合适的尺码或规格

- 竞品对比引导：当用户提及竞品时，客观对比并突出自身产品优势

- 多语言实时翻译：支持 130\+ 语种实时互译

**8\.2\.3 下单购买 Agent**

负责引导用户完成从选购到支付的全流程。核心能力包括：

- 购物车管理：自动添加商品、修改数量、计算运费和税费

- 优惠券/折扣匹配：自动识别并应用可用的优惠券和促销活动

- 地址智能填充：基于历史收货地址和用户口述，自动填充收货信息

- 支付方式引导：根据用户所在地区推荐最优支付方式

- 订单确认与追踪：下单后自动推送订单确认信息，提供实时物流追踪

**8\.2\.4 售后知识讲解 Agent**

负责处理商品使用指导、退换货、维修等售后问题。核心能力包括：

- 使用指南推送：根据用户购买的商品，自动推送图文/视频使用教程

- 故障诊断引导：通过多轮对话引导用户描述问题，匹配解决方案库

- 退换货流程自动化：自动判断退换货资格，生成退换货标签，跟踪退款进度

- 保修查询：根据订单信息自动查询保修状态和维修网点

- 评价引导：问题解决后自动引导用户留下正面评价

## **8\.3 流式交互与多轮对话记忆**

**8\.3\.1 流式交互设计**

|**技术要素**|**实现方案**|**性能指标**|
|---|---|---|
|流式输出|Server\-Sent Events \(SSE\) / WebSocket|首 Token 延迟 \< 500ms|
|增量渲染|前端逐字渲染 \+ 打字机效果|视觉流畅度 \> 30fps|
|中断恢复|会话断线后自动重连并恢复上下文|重连成功率 \> 99\.5%|
|并行处理|多个 Agent 并行推理，结果流式合并|端到端延迟 \< 3s|
|背压控制|下游消费不及时自动降速|无消息丢失|

**8\.3\.2 多轮对话记忆架构**

多轮对话记忆是实现连贯导购体验的核心能力。采用三层记忆架构：

|**记忆层**|**存储内容**|**生命周期**|**存储介质**|
|---|---|---|---|
|短期记忆（Working Memory）|当前会话的对话上下文、Agent 中间推理状态|单次会话|Redis（TTL 30min）|
|中期记忆（Session Memory）|用户近期多次会话的摘要、偏好变化|7 天滚动窗口|Redis \+ PostgreSQL|
|长期记忆（Profile Memory）|用户画像、历史购买偏好、尺码记录|永久（支持用户删除）|PostgreSQL \+ pgvector|

- 记忆压缩：当短期记忆超过 Token 上限时，自动摘要压缩，保留关键信息

- 记忆检索：基于向量相似度从长期记忆中检索相关上下文，注入当前对话

- 记忆更新：每轮对话结束后自动更新用户画像和偏好数据

- 隐私合规：用户可随时查看和删除个人记忆数据，符合 GDPR 要求

## **8\.4 架构演进：从 LangGraph 到 A2A 协议**

**8\.4\.1 一代架构：LangGraph 单体编排**

项目初期采用 LangGraph 作为智能体编排引擎，以有向图的方式定义 Agent 之间的调用关系和状态流转。该架构适合快速验证业务逻辑，但在规模化运营中暴露出以下瓶颈：

|**瓶颈**|**具体表现**|**影响**|
|---|---|---|
|单点瓶颈|所有 Agent 共享同一进程，高并发时互相阻塞|吞吐量受限，无法线性扩展|
|状态耦合|Agent 间通过共享内存传递状态|调试困难，故障扩散快|
|扩展性差|新增 Agent 需修改图结构并重新部署全量服务|迭代速度慢|
|监控困难|缺乏标准化的 Agent 间通信协议|链路追踪和性能分析困难|

**8\.4\.2 二代架构：A2A 协议分布式微服务 Agent 集群**

为突破单体架构的瓶颈，系统升级至基于 A2A（Agent\-to\-Agent）协议的分布式微服务 Agent 集群架构。核心设计原则：

- Agent 即服务（AaaS）：每个 Agent 独立部署为微服务，拥有独立的计算资源和数据存储

- 标准化通信协议：定义统一的 A2A 消息格式（JSON Schema），支持同步调用和异步事件

- 服务注册与发现：Agent 启动时自动注册到服务注册中心，支持动态扩缩容

- 分布式状态管理：使用 Redis Cluster 管理跨 Agent 的共享状态

- 链路追踪：每个 Agent 调用自动注入 Trace ID，支持全链路性能分析

**8\.4\.3 A2A 协议规范**

|**协议字段**|**类型**|**说明**|
|---|---|---|
|agent\_id|string|发起调用的 Agent 唯一标识|
|target\_agent|string|目标 Agent 唯一标识|
|message\_type|enum|request / response / event / error|
|payload|object|业务数据载荷（JSON Schema 约束）|
|trace\_id|string|全链路追踪 ID|
|timestamp|ISO 8601|消息创建时间戳|
|ttl\_ms|integer|消息生存时间（毫秒）|
|priority|enum|high / normal / low|

**8\.4\.4 架构对比**

|**对比维度**|**一代（LangGraph）**|**二代（A2A 协议）**|
|---|---|---|
|部署模式|单体进程|分布式微服务集群|
|Agent 间通信|共享内存|标准化 A2A 协议（HTTP/gRPC）|
|扩展方式|整体扩容|单 Agent 独立扩缩容|
|故障隔离|无隔离，级联故障|熔断 \+ 降级，故障隔离|
|监控能力|基础日志|全链路 Trace \+ Metrics \+ Alerting|
|新增 Agent|修改图结构 \+ 全量部署|独立开发 \+ 注册即用|
|适用阶段|MVP 验证（0\-3 个月）|规模化运营（3 个月\+）|
