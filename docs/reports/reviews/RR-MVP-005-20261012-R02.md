# 审查范围、依据与重点风险

审查 G4 源码读取方式的局部修复。R01 的评测模式、费用授权、合成数据和 production 边界继续有效。

# 发现、级别、位置和证据

- 现场失败日志定位在 checkout 的 `git fetch`；取消时预检和 `live` 未开始。改用现有 staging 只读作业采用的 GitHub API 模式，有明确的 30 秒单请求超时。
- `github.token` 只在 Runner 环境传入；API 回复的 commit SHA 和六个文件的 Git blob SHA 逐项验证。冻结集另受 SHA-256 与数据清单校验，运行 backend 文件仍与来源 SHA-256 比对。
- 若 API、摘要或运行镜像不匹配，工作流在 Provider 步骤前失败；`live` 的独立授权条件和开关不变。未发现本轮修复需要返工的问题。

# 已验证与未验证内容

已验证本机真实 GitHub API 获取及摘要、脚本语法、旧现场运行的失败步骤。未验证修复后的 staging API 访问、低敏 artifact 或真实模型质量。

# 结论和返修条件

批准合并此有限范围的源码获取修复，再执行 `prepare`。若 staging API 仍失败，应诊断网络和最小权限，不得跳过校验或运行 `live`。G4 仍未通过。
