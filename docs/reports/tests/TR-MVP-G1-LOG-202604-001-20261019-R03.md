# 测试范围与方法

用户指出当前授权店铺有 FedEx 和 USPS 订单；所提供的 FedEx 筛选截图显示可用订单，先前 CBT 筛选截图为 0 单。截图不入库，且本轮没有独立操作 Seller Center 的物流详情。官方[通用 Get Tracking](https://partner.tiktokshop.com/docv2/page/get-tracking)提供 `GET /fulfillment/202309/orders/{order_id}/tracking`，与[CBT 首程增强接口](https://partner.tiktokshop.com/docv2/page/8syhoy40)的能力范围不同。

在唯一已连接、具有 `seller.logistics` Scope 的 staging TikTok 渠道中，通过官方订单搜索完整分页 4 页，用截图订单号的末 4 位作唯一匹配，再用官方订单详情核对同一订单且存在跟踪单号。随后从运行中 backend 容器使用现有签名、Token、`shop_cipher` 与只读 HTTP 客户端，仅向通用 `202309` 路径发送一次 GET，临时将本进程读取重试上限设为 1。输出只保留固定布尔值、业务码和轨迹条数；未保存订单、运单、买家、店铺标识、请求签名、Token、平台响应正文或请求 ID。命令为一次性容器标准输入脚本，未改运行服务、数据库或仓库源码。

# 现场结果

官方订单搜索中末 4 位匹配恰好 1 笔，订单详情匹配且有跟踪单号。通用 `202309` 跟踪请求返回平台业务码 `0`，`data.tracking` 为列表，包含 **11 条轨迹**。低敏输出及运行后端摘要见[证据清单](../../../release/evidence/staging/crm-staging-g1l-generic-fedex-20261019.json)。这证明该店铺一笔截图标记为 FedEx 的真实订单可通过 TikTok 通用物流接口取得轨迹。

本次未逐条对比 Seller Center 的时间、状态或承运商轨迹；USPS 尚未调用。现有 `TikTokReadClient.get_tracking` 只实现 `202604` 增强路径，通用路径通过一次性只读探针验证，尚未接入项目正式适配器。不能把探针成功扩大为 CRM 物流功能已上线。

# 门禁与后续

本轮**没有调用** `202604`，没有 CBT 首程样本，也没有首程动作码成功证据；因此本报告对增强接口仍为 `BLOCKED`。探针完成后，用户将 v0.1 G1-L 验收范围明确改为通用 `202309` 真实轨迹成功，CBT 增强项不再是 G1-L/G8 前置。本报告保留范围变更前的原始结果，不把 11 条普通轨迹当成 CBT 首程通过；G1-L 的新口径结论见后续独立测试记录。通用适配器仍需契约测试与正式运行核对；增强 `202604` 待合格 CBT 包裹或官方适用性说明。
