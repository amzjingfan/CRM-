# 测试范围、环境与方法

`TEST_LAYOUT=centralized`。从 staging backend 容器中的 `TikTokReadClient.search_orders` 对唯一 connected 的 TikTok 渠道分页查询，数据库事务设为只读；另对首页官方订单搜索响应仅统计白名单 `shipping_type`、`fulfillment_type`。命令通过 SSH 手动在运行容器中执行，输出只保留总数、状态及类别计数，不保存订单号、包裹号、店铺标识或原始响应。先核对运行镜像不可变摘要和 OCI revision。

# 结果与证据

分页读完 325 笔可见订单，最新创建日期为 2026-09-30（UTC）；当前状态仅有 `IN_TRANSIT` 1 笔、`DELIVERED` 1 笔，其余为完成或取消。首页 100 笔中 `shipping_type=TIKTOK` 78、`SELLER` 22，`fulfillment_type=FULFILLMENT_BY_SELLER` 100。这些字段不能单独证明 CBT 首程资格。低敏原始汇总见[本次清单](../../../release/evidence/staging/crm-staging-g1l-order-inventory-20261019.json)。

此前五笔不同 TikTok 配送订单调用 `202604` 均返回业务码 `11007009`，见[2026-10-09 现场诊断](../../../release/evidence/staging/crm-staging-g1-live-diagnostics-20261009.json)。本次没有重新调用该接口，因此不消耗同订单的查询频率，也没有新的真实成功证据。

# 缺陷、未执行项与结论

[官方说明](https://partner.tiktokshop.com/docv2/page/8syhoy40)把增强接口定位为 CBT 包裹首程轨迹，并规定每订单 8 小时一次查询。现有订单清单没有确认首程扫描及平台适用性的证据；不能对任意 `TIKTOK` 配送订单重复尝试后宣称通过。G1-L 本轮为 `PARTIAL`，任务继续等待合格包裹或平台适用性说明，G8/production 不放行。取得前提后，对单笔已确认合格的包裹执行一次 `202604` 只读查询，核对包裹数、首程动作码、时间与 Seller Center，保存低敏成功或明确失败证据。
