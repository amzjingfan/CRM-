# 实施目标与范围

修复 G4 `prepare` 首次现场运行卡在全仓 `git fetch` 的入口问题。保持 R01 的冻结数据、运行镜像和零调用守卫，不扩大评测范围。

# 实际变更及原因

运行 [#38200077151](https://github.com/CP11-gh/CRM/actions/runs/38200077151) 在 `actions/checkout` 的 `git fetch --depth=1` 停留约 3 分 46 秒，未进入预检，经受控取消。将全仓 checkout 改为与现有 staging 只读工作流一致的 GitHub Contents API 精确提交读取：先核对 commit SHA，再下载六个必需文件，逐个核对 Git blob SHA，随后沿用 R01 的冻结数据 SHA、运行镜像摘要和文件 SHA 检查。每次 API 请求限时 30 秒。

# 关键决定与偏差

现场日志只能证明 Git fetch 卡住，不能断言具体网络设备或 GitHub 服务原因。改用已在项目现有工作流使用的内容 API，不改变后端评测脚本或运行容器。准备运行在 checkout 阶段取消，Provider 调用为零，未生成准备 artifact。

# 数据、配置、接口、迁移或 Prompt 影响

仅 CI 源码读取方式和部署说明变化；没有服务配置、接口、数据、迁移或 Prompt 变化。GitHub token 只传给 Runner 步骤环境，不写日志或 artifact。

# 验证交接

本地执行修复后的精确读取步骤，六个文件均通过 commit/blob 核验，冻结 JSONL SHA-256 与已批准值一致。PowerShell/YAML 解析和现场失败范围见 R02 TR；修复后的 staging `prepare` 仍待合并后执行。

# 限制、风险与回滚

GitHub Contents API 或 staging Runner 对 API 的连通性仍需现场验证；任何读取、摘要、配置不符均在模型调用前失败。可 revert 本提交回退读取方式，但原 checkout 卡住风险仍在。G4 保持未通过。
