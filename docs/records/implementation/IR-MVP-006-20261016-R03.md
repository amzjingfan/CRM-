# 实施目标与范围

用户批准在 staging Runner 增加只读 `check_only` 与另行精确批准的 `provision` 入口，并运行一次零业务写入检查。本 R03 记录源码准备；现场执行结果单独留证。未获准实际创建 50 个账号或会话。

# 变更

- 新增 `prepare-staging-sse-fixture.yml`，限定 main 精确提交、四个 Git Blob 校验、正在运行的 backend 不可变摘要、受限部署文件与容器数据库指纹、专用 Runner 和私有仓库外路径。
- `check_only` 用运行镜像的一次性只读容器检查最小权限与已有 G5 夹具，仅输出固定类别；不发送 DeepSeek/TikTok 请求，不修改服务。
- `provision` 另需模式及精确确认值，先通过相同的只读检查，再将 R02 的 50 账号准备工具写出的凭证直接保存在 Runner 私有目录；结果不确定时保留 manifest，禁止盲目重试。
- 独立审查发现后端镜像无 Git 时原有路径校验会使 `provision` 在写入前失败；增设仅接受固定只读源码挂载和独立私有可写挂载的 `/proc/self/mountinfo` 分支，保留原 Git checkout 校验及 POSIX、权限、数据库指纹门禁。
- 受保护配置文件路径直接由各执行步骤读取 staging Secret，不经 `GITHUB_OUTPUT` 传递，避免被工作流的 Secret 输出过滤拦截。
- Runner 私有目录只要已有任意材料即拒绝新一轮 `check_only`/`provision`，防止不同 run ID 绕过未知提交的 manifest 对账；已有材料只能按独立清理流程处理。
- `check_only` 失败时仅记录固定 `failure_stage` 类别，不回显脚本的原始 stdout；之后继续报错，不能误报预检通过。
- 增加只读失败关闭、工作流顺序及隔离 PostgreSQL 测试；部署说明标明现场授权与清理边界。

# 边界与恢复

工作流代码和 `check_only` 不构成账号创建授权。现场 `provision`、知识审批、真实模型并发、配置切换及 production 均未执行。若工作流预检失败，检查固定阶段并修复后重新验证；不得绕过数据库指纹或运行摘要检查。G5 保持 `DOING`。
