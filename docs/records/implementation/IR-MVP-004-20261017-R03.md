# 实施目标与范围

在已有真实入站和受控买家会话的基础上，准备工作台自动获取新消息和 staging 单会话人工发送。范围仅含普通文本、现有店铺授权与人工二次确认；production、自动回复和高风险动作未开启。

# 实际变更及原因

- 工作台在标签页可见时每 5 秒查询会话列表及当前会话最新消息，按消息 ID 合并，保留已加载历史、选中会话和草稿；后台刷新失败保留现状并在下一轮重试。
- TikTok 写客户端升级至[官方 202606 Send Message](https://partner.tiktokshop.com/docv2/page/send-message-202606) 契约，明确 `sender_role=CUSTOMER_SERVICE`，继续保持单次调用及 `unknown` 对账策略。
- staging 真实发送配置要求一个数字平台会话 ID；详情只向匹配会话暴露 `send_mode=real`，服务层在调用工具前拒绝其他会话，平台客户端在 HTTP 请求前再次拒绝。
- staging 门禁新增单会话人工发送覆盖层，只让 backend 开启普通文本写入。参数、合并 Compose 和运行容器均核对目标及能力；worker/jobs/agent-worker、高风险写入和自动回复保持关闭。
- 更新 API、系统、部署、任务与发布门禁事实；没有新增服务、迁移、数据模型或 Prompt。

# 关键决定与偏差

用户已确认继续实施人工互发，但项目治理仍要求向外部买家发送**具体正文**前单独确认。因此本轮只交付源代码和部署门禁，不声称真实出站完成。现有 staging 的受控消息从真实 TikTok Webhook 验签并入库，低敏只读聚合见[预检证据](../../../release/evidence/staging/crm-staging-tiktok-inbound-preflight-20261017.json)。

# 数据、配置、接口、迁移或 Prompt 影响

新增可选配置 `TIKTOK_MESSAGE_WRITE_ALLOWED_CONVERSATION_ID`，staging 开启真实写入时必填；通过门禁参数注入，不写入仓库 env 或证据。TikTok 外部写 API 版本改为 202606，工作台自身 API 路径和数据库结构不变。

# 验证交接

本地完整后端、浏览器、静态检查和构建结果见 R03 TR；RR 覆盖目标范围与失败关闭。后续从合入 main 的精确 SHA 手动构建私有后端和前端镜像，先验证 staging 合并配置与运行态，再进行单次真实发送和平台对账。GitHub Actions 不参与部署。

# 限制、风险与回滚

本轮没有部署新镜像，没有启用真实发送，也没有向买家发送内容；G3 仍在实施中。运行窗口若出现平台结果不确定，保持 `unknown` 并停止重发。恢复时用同一受审镜像重新部署 Webhook 只读加翻译模式，核对写开关为 false、三个健康端点和固定出口。
