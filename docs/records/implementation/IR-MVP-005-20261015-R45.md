# 实际变更与原因

用户批准的一次 [R44 canary #38678589702](https://github.com/CP11-gh/CRM/actions/runs/38678589702) 在约两秒内以固定 `CANARY_SETUP_FAILED` 结束，没有可安全上传的报告；请求是否发出无法证明，本次授权未重用。按用户确认的有界零调用设计，[PR #204](https://github.com/CP11-gh/CRM/pull/204) 在既有 G4 工作流加入 `check_only` 模式，合入 main `e1db76513ac14ce0a6ea8fdbe033623981efe82b`。

新模式沿用精确 main SHA、冻结输入 SHA-256、运行后端不可变摘要和源码一致性核对，将本地 settings、数据集、运行安全约束与 SDK 客户端构造结果归类为固定失败阶段。它不进入 Provider 生成路径，`provider_calls=0`，不保存配置值、Prompt、模型正文、请求 ID 或原始异常。审查中发现畸形 URL 会在分类前抛错、共享前检会抢先拦截无效设置，均经红绿回归修复；付费 `canary` 和 `live` 保留原严格前检及单独确认。

# 现场结果与边界

从上述 main 运行的[零调用检查 #38681595434](https://github.com/CP11-gh/CRM/actions/runs/38681595434) 已上传[固定低敏报告](../../../release/evidence/ai/crm-staging-g4-r45-check-only-38681595434.json)：`check_result=rejected`、`failure_stage=settings_validation`、`provider_calls=0`、`request_hook_seen=false`。源码核对表明 canary 容器调用启用 `LLM_LIVE_EVAL`，却未像现有 live 步骤传入五项获批计价配置；`Settings` 在这一条件下要求有效计价配置。这是与现场阶段相符的代码原因，修复后仍需零调用复核才能确认。

运行服务、TikTok 发送开关、冻结评测集、G4 评分门槛和生产环境均未改变。真实单样本生成、R41 的 34 次超时与完整 G4 质量仍未验证；G4 `PARTIAL`、production No-Go。任何付费重试需新的精确授权。
