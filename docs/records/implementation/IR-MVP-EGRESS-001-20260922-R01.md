# 实施目标与范围

为 TikTok OAuth、真实只读与人工普通消息建立单一、失败关闭的固定出口，使 staging 的 TikTok 服务端请求只经 `38.55.145.52`，同时保持既有 split-ingress、GitLab、公司容器和非 TikTok 出站不变。production 只建立可复用配置契约，不创建账号、密钥、服务器配置或实际部署。

# 实际变更及原因

- Settings 增加 `TIKTOK_EGRESS_PROXY_URL` 校验；真实能力只接受无凭据的 `socks5h`，staging/production 精确固定为 `socks5h://tiktok-egress:1080`。
- OAuth token/shop、TikTok 只读和人工消息统一使用专用 HTTPX 工厂，显式代理且 `trust_env=False`；代理缺失或失败时不构造直连回退。
- backend 镜像增加最小 `openssh-client` 与 `httpx[socks]` 依赖；Rootless Compose 增加只加入专用网络、不发布端口、只读根、能力清空和 `no-new-privileges` 的 helper。
- helper 显式使用容器 `0:0`，在 Rootless UID 映射下读取宿主机 `crmdeploy` 所有的 `0600` 私钥；backend、worker、jobs 继续使用镜像默认非 root 用户且不得挂载密钥。
- 新增 `crm-egress` 公网账号安装器，限制为 publickey-only、local forwarding、精确三个 `PermitOpen` 目标；既有账号任何漂移先失败，不先修改密码、账号或授权文件。
- 新增低敏出口验证器；staging 门禁固定四层 Compose 顺序，并按基础依赖 → helper → 出口验证 → 迁移/check heads → 应用 → 公网健康执行。回滚保留候选 helper，只切换应用 RepoDigest。

# 关键决定与偏差

- 入口 `crm-tunnel` 与出口 `crm-egress` 不复用账号、密钥、权限或转发方向。
- `checkip.amazonaws.com:443` 只用于发布门禁，业务目标仍只有两个 TikTok 官方域名。
- 原规格要求现场验证后合并，但不可变镜像工作流只从 merged main 发布。按用户批准计划采用两阶段集成：实现分支在 `VERIFYING` 合并，live staging 通过后再以证据分支进入 `DONE`。
- 整分支审查发现 helper 运行用户、出口验证顺序、既有账号写前漂移、OpenSSH `User`/`Group` pattern-list、备份路径信任和回滚失败处理等阻断问题；均经 RED→GREEN 修复。安装器现在对既有账号只读比对全部账号、密钥与 SSHD 状态，只有全新状态才写入；新增 drop-in 前保存 root-only 精确备份，恢复失败时保留备份但仍清理本次身份，任一清理失败都报告非零并保留对应状态。PR 首轮 CI 发现的两份测试文件格式差异已机械修复并完成同范围复验；当前最终实现与当前事实文档绑定为 `4c8d08c4728dad5e85f6bd2d0e83751a084ccace`。

# 数据、配置、接口、迁移或 Prompt 影响

- 新增非秘密配置 `TIKTOK_EGRESS_PROXY_URL`、`TIKTOK_EGRESS_SECRET_DIR`、`TIKTOK_EGRESS_IMAGE`；staging 声明出口为 `38.55.145.52`。
- 新增 Compose overlay、SSH 安装器与发布验证 JSON 字段；没有数据库 schema、迁移、公共 HTTP API、Prompt、模型、权限或租户边界变化。
- backend 运行镜像新增 OpenSSH client 和 SOCKS transport 依赖；目标服务器仍禁止 build，发布必须使用 merged-main RepoDigest。

# 限制、风险与回滚

- production 未部署、未选择出口拓扑，也未取得发布批准。
- 应用异常时只切回已验证的上一应用 RepoDigest，helper 保持候选镜像；出口异常时保持真实能力关闭并停止候选应用，不删除数据、卷、入口隧道或公司负载。
