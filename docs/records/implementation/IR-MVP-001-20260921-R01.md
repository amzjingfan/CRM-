# 实际变更及原因

- 在业务服务器受限文件 `/home/crmdeploy/config/crm-staging.env` 中轮换 `POSTGRES_PASSWORD`、对应 `DATABASE_URL`、`MINIO_SECRET_KEY`、`JWT_SECRET_KEY`、`RETRIEVAL_MODEL_SERVICE_TOKEN`，并首次生成 `TIKTOK_CREDENTIAL_ENCRYPTION_KEY`。
- PostgreSQL 只接收由随机 salt、4096 次 PBKDF2-HMAC-SHA256 生成的 SCRAM verifier；明文口令只在 root shell 内存和容器 stdin 中短暂存在，不作为 argv、日志、Git 或证据字段。
- 只重建 Rootless `crm-staging` 项目的 PostgreSQL、MinIO 和应用容器；应用重建后重启 proxy 以刷新 Nginx 上游地址。系统 Docker、GitLab、其他公司容器、边缘 Nginx 配置和隧道配置不变。
- 停止并移除已退出的 `crm-staging-minio-init-1`，避免旧 MinIO 口令继续存在于该一次性容器的环境中。
- 成功轮换的 root-only 恢复副本保留在 `/var/backups/crm-staging/secrets/20260921T080357Z/crm-staging.env.before`，所有者/权限为 `root:root:0600`。
- 仓库只提交低敏运行手册、机器证据和 IR/TR/RR；实际密钥、密钥摘要、一次性脚本和 SSH 私钥均不提交。

# 关键决定与偏差

- Compose 会在 rootless `volumes: !override` 生效前插值 production 文件的 `TLS_CERT_DIR`；隔离 Compose 子进程使用已验证存在的 `/home/crmdeploy/config` 作为仅插值值，最终 proxy 仍只挂载 `nginx-tunnel.conf`。
- PostgreSQL 容器的 localhost HBA 为 trust，不能用于证明旧密码失效；最终正反例固定从 backend 容器经 `postgres:5432` 执行，并区分认证失败与网络/运行时失败。
- 首次执行在变更前因缺 `TLS_CERT_DIR` 被拦截并清理；第二次执行因 localhost trust 产生旧密码假阳性，自动回滚后又以受限恢复脚本回写旧 SCRAM verifier、验证 backend 网络认证并刷新 proxy，三个健康端点恢复 200；修正并复审后第三次执行成功。
- 两份失败尝试的 root-only 重复恢复副本仍保留。删除请求被治理门禁拒绝；后续必须建立独立 `MAINT-CLEANUP-*` 和精确批次，不在本任务绕过。
