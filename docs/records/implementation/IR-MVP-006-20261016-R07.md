# 目标与原因

用户要求继续 G5，并批准对 R06 现场 50 次认证拒绝做一次有界只读诊断。R06 从 main `7e12314` 运行的 staging 工作流 #38858709981 成功核对源码、运行镜像、数据库和私有文件，但只读 `preflight` 返回 `auth_rejected=50`、运行 `CHAT_QUERY_LIMIT=10`、Access Token 有效期 120 分钟，门禁如期失败；`provision` skipped，Provider 0。令牌自创建到这次预检约 68 分钟，不能仅据拒绝推断已过期。

# 本次实现

- 现有 staging Runner 增加 `diagnose_auth` 只读模式，沿用精确 main SHA、Git Blob、运行镜像、数据库指纹与唯一私有凭证文件保护；原 `provision` 精确确认保持不变。
- 从运行 backend 只计算 JWT 签名密钥的 SHA-256，并读取白名单 JWT 算法；在受限一次性容器内比较签发配置与运行配置是否一致，不输出密钥或哈希。受限容器只检查现有凭证池第一枚令牌的签名、必需声明和过期类别，并发出一次 `/v1/auth/me` GET；该请求禁用环境代理。
- 输出限于固定令牌类别、签名配置是否匹配、HTTP 状态类别、请求数及 `provider_calls=0`；不输出令牌、用户、响应正文或原始异常。模型、SSE、业务写入和生产服务均不触及。
- 同步测试策略、发布门禁现状与 staging 运行说明。该诊断只帮助定位 R06 失败，既不更新凭证也不提高限流。

# 恢复与下一步

源码合并后只能从精确 main 在 staging 执行一次获批的只读诊断，再按结果判断凭证签发配置、过期或身份读取问题。不得重跑 `provision`；若需改动私有凭证或运行配置，另形成有界变更和现场授权。G5 仍为 `DOING`，production No-Go。
