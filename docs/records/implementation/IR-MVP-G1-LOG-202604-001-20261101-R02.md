# 实施目标与范围

修复跨境 CBT 增强物流轨迹被本地模型误判为平台错误的问题。原订单和买家核对、八小时每单限频及通用轨迹回退保持。

# 实际变更及原因

只读实测的 `202604` 成功响应含一个包裹和 16 条节点，其中早期节点的 `tracking_no` 为空字符串。旧模型要求每条节点的单号至少一个字符，导致整份平台成功响应转为 502。现允许节点单号为空，保留该节点；工作台将空单号转为 `null`，不借用包裹或其他节点的单号。增加平台解析和侧栏回归测试。

# 关键决定与偏差

TK app 旧现场只证明通用 `202309` 取得 CBT 承运商的 14 条节点。本轮独立只读探针首次证明增强 `202604` 对另两笔合格 CBT 订单返回 HTTP 200/业务码 0；早期另一笔增强失败的具体平台码未获归因，不宣称全部 CBT 订单均可成功。

# 数据、配置、接口、迁移或 Prompt 影响

无数据库、密钥、Scope、发送开关或迁移变化。工作台增强物流响应中的早期节点运单号可为 `null`；其他必需字段继续按原模型校验。

# 验证交接

本地单元、全量后端、隔离 PostgreSQL 回归及最终 subject SHA 定点复验见关联 TR。staging 现场独立订单验收与部署证据将另记新 TR。

# 限制、风险与回滚

平台每单八小时频控不可为测试重复查询。现有前端按可空单号展示；部署后只读检查新订单和页面。失败时恢复旧后端不可变摘要，保留数据库业务增量。
