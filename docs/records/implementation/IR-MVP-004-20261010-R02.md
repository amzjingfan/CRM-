# 实施目标与范围

把 R01 已合入的人工发送中断后失败关闭补丁部署到 staging，保持现有 G2 真实只读与 Webhook 模式，继续关闭真实普通消息写入。本轮不尝试 G3 真实发送或对账。

# 实际变更及原因

- 经用户对单个私有 backend 镜像的精确授权，从 main `6e975148650bfd8e6cb0b7980b86554345caf5d0` 发布 `crm-backend@sha256:0a07365ef1c266b67bc42e77e73b074118911cb54841f504160503e03f8f77e5`。
- 复用当前 frontend 与 retrieval 的不可变摘要，按六角色预取、G2 模式 validate、G2 模式 deploy 的顺序执行 staging 门禁；没有发布其他镜像。
- 只读现场观察再次确认运行 backend 为候选摘要，公网健康和固定出口通过。全过程与 artifact 摘要见[低敏部署证据](../../../release/evidence/staging/crm-staging-g3-backend-rollout-20261010.json)。

# 关键决定与偏差

# 数据、配置、接口、迁移或 Prompt 影响

无新增源码、接口、数据库迁移文件或 Prompt。部署工作流执行既有 `alembic upgrade head` 和 `current --check-heads`，证据为 `heads_applied`；运行镜像变化仅在 staging。production 未改。

R01 的隔离 PostgreSQL 和完整后端回归是代码验证；本轮预取、预检、部署、只读观察及独立公网探测见 R02 TR。此次部署源 SHA 为 `6e975148650bfd8e6cb0b7980b86554345caf5d0`，证据尾 SHA 在 PR 门禁时读取。
