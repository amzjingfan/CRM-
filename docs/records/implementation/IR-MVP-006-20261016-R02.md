# 实施目标与范围

用户确认先交付 staging 专用的 50 个隔离 CRM 测试身份准备工具、确定性测试和清理方案；现场创建账号、会话及仓库外凭证池前另行确认。本轮仅修改仓库代码和文档，不向 staging 写数据，不调用 DeepSeek，也不改变运行服务。

# 变更

- 增加 `prepare_sse_staging_fixture.py`：显式 `--execute`、`APP_ENV=staging`、仅 Linux 私有目录、仓库外独占新文件和独立核对的 staging 数据库 DSN 指纹，全部通过后才进入写事务。
- 单次事务准备一个标记的隔离店铺、最小 `workspace.view` 角色、50 个不同 CRM 用户、50 组 synthetic 客户/会话/入站消息、禁用工具的 Agent 配置及一条低敏审计；只将短时 Access Token、CSRF、会话与精确清理 manifest 写到仓库外私有文件。
- 逐层 flush 处理 PostgreSQL 外键顺序。文件写入失败时数据库回滚；文件已写而提交结果不确定时保留唯一 manifest，要求按 run/store ID 对账，不自动重试或删除。
- 扩充确定性与隔离 PostgreSQL 测试；部署说明和测试策略补现场前置条件与独立清理计划。

# 边界与剩余门禁

此工具只解决身份与会话前置条件。隔离店铺没有已审批且向量化的 FAQ，也没有订单工具；这些会话无法保证 SSE 安全 `delta`。在获批现场创建并通过 R01 的只读预检后，仍需依现有知识审批流程准备可检索的合成 FAQ，单独验证一条真实模型输出，再考虑 G5 50 并发、P99、断连、队列和资源。G5 仍为 `DOING`，production No-Go。

无迁移、公共 API、Prompt、模型或运行配置变更。回滚本次源码采用撤销候选提交；若将来实际创建数据，按部署说明先精确禁用身份，再另立 `MAINT-CLEANUP-*` 批次。
