# 实际变更及原因

PR #79/#80 在保留锁文件和运行行为的前提下将候选及上一版检索镜像拆层，四个受授权的私有镜像已发布。Runner 2.336.0 自动升级下载超时导致作业无法领取，按官方包 SHA-256 核对后恢复为 2.337.0，保留 Runner 注册。低并发 `docker pull` 仍在 GHCR 数据节点发生 TCP 重置。PR #83 在 `3b091055908a4fd374dc95518dfd31d8d8960a47` 加入检索 OCI 内容的分段续传、清单/层 SHA-256 核对、Rootless 导入和最终 RepoDigest 核对。可恢复缓存避免大层每次断连后从零下载；工作流继续严格核对调度源码。

候选与上一版检索的 OCI 内容在本机下载并逐层校验，经内网传输到 staging 受限缓存后再次核对；正式预取 `36699523917` 从缓存核对并导入，六摘要全部通过，未修改活动服务。受控将 staging 环境文件的检索摘要切到候选，先保留 `0600` 原文件副本。`validate`、候选 `deploy`、上一版 `rollback` 和候选再次 `deploy` 依次成功。切返后活动后端、前端和检索均为候选摘要，11 个容器运行，迁移头 `024`，三个公网健康端点 200，固定 TikTok 出口 `38.55.145.52`。环境文件只变更该镜像摘要，Docker 原配置哈希与 daemon ID 保持原值。低敏精确摘要、运行编号与 artifact SHA-256 见 `release/evidence/staging/crm-staging-mvp008-g0-20260930.json`。
