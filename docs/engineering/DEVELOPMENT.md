# 开发与协作规范

## 开始前

1. 从 `docs/README.md` 选择与任务有关的产品、接口、架构、AI、部署和门禁文档。
2. 执行 `git status --short --branch`，确认工作区和基线；不要覆盖他人的未提交修改。
3. 明确目标模块、需求边界、依赖、验收标准和安全风险。
4. 行为或安全边界不清晰时先形成决定，不靠实现细节猜测产品规则。

## 代码规则

- Python 使用明确类型、Pydantic 边界模型和结构化异常；TypeScript 开启严格类型，避免 `any` 和隐式数据契约。
- 名称表达业务含义；中文注释说明业务原因、失败策略和安全边界，不逐行翻译代码。
- 路由只处理协议和依赖注入，业务规则放服务层，外部平台放适配器，数据库访问不越层。
- 时间统一存 UTC，金额使用 Decimal/最小货币单位，标识符和分页参数在边界校验。
- 不静默吞错，不把第三方响应、密钥、Token、客户正文或完整模型输入写入日志。
- AI Agent 只能通过白名单工具读取或操作业务；工具层负责租户、权限、幂等、审计和字段过滤。

## 安全边界

- 所有查询和写入必须绑定店铺/租户；客户端传入的店铺 ID 不能替代服务端授权判断。
- 写操作按风险使用 CSRF、`Idempotency-Key`、状态机和审计。
- 真实凭证仅通过环境或密钥管理系统注入；仓库只保存脱敏 `src/config/.env.example`。
- 默认关闭真实平台、公开自动回复、自动营销和高风险写入；不得为了测试绕过生产检查。
- 外部结果不确定时失败关闭；可能已写入的平台调用进入 `unknown` 并对账。

## 测试

- 新功能和缺陷修复优先以行为测试驱动，覆盖正常路径、权限、隔离、幂等和失败关闭。
- `TEST_LAYOUT: centralized`：测试源码、测试专用 fixture/data、普通 eval 输入/结果和项目内临时测试输出只能新增到 `src/tests/`，禁止在产品模块下新增测试或 eval 根。临时输出只写入 `src/tests/.artifacts/`；正式 TR 和低敏发布证据依次保留在 `docs/reports/tests/` 与 `release/evidence/`。
- 文档/结构变更只运行与风险相称的检查；不要为静态 prose 或目录名称编写脆弱的源码 grep 测试。
- 单元测试不依赖真实密钥和网络；真实门禁使用明确开关、冻结数据集和低敏聚合证据。
- 不把历史测试结果描述为当前分支运行结果；未运行项在交付说明中明确列出。

## GitHub Flow

- 根目录是唯一 Git 仓库，`src/` 是唯一工程根。日常修改从最新 `main` 创建 `feature/*`、`fix/*`、`docs/*`、`hotfix/*` 短期分支，优先使用 `.worktrees/` 隔离。
- 一个分支只处理一个主题，小步提交；提交前缀使用 `feat:`、`fix:`、`docs:`、`test:`、`build:`、`ci:` 或 `chore:`。
- 通过 Pull Request 合并，完成 CI、人工审阅、文档同步和安全检查；默认 squash merge 并删除短期分支。
- 分支达到 `docs/governance/GOVERNANCE.md` 定义的合并就绪条件后，立即执行“完成即合并”；先合并并复核目标分支，再把任务标记为 `DONE`。
- 禁止强制推送和 `git reset --hard` 覆盖共享历史；已共享提交使用 `git revert` 回滚。
- 发布标签必须带注释并关联迁移、配置、冻结数据和 SHA-256；标签本身不等于生产放行。

## 提交边界

禁止提交 `.env`、真实密钥/Token、凭证池、模型权重、`.venv`、`node_modules`、缓存、日志、构建产物和测试临时目录。提交前至少检查差异、受影响测试、文档同步和敏感信息。
